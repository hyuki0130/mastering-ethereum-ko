# 14장. 이더리움 가상 머신

이더리움 프로토콜과 운영의 핵심에는 *이더리움 가상 머신*(Ethereum Virtual Machine), 줄여서 *EVM*이 있습니다. 이름에서 짐작할 수 있듯이, 이것은 마이크로소프트의 .NET 프레임워크 가상 머신이나 Java와 같은 바이트코드 컴파일 프로그래밍 언어의 인터프리터와 크게 다르지 않은 계산 엔진입니다. 이 장에서는 이더리움 상태 업데이트의 맥락에서 EVM의 명령어 집합, 구조, 동작을 자세히 살펴봅니다.

## EVM이란 무엇인가?

EVM은 스마트 컨트랙트 배포와 실행을 처리하는 이더리움의 부분입니다. 한 EOA에서 다른 EOA로의 단순한 가치 전송 트랜잭션은 실질적으로 EVM을 필요로 하지 않지만, 그 외의 모든 것은 EVM이 계산한 상태 업데이트를 포함합니다. 높은 수준에서 보면, 이더리움 블록체인에서 실행되는 EVM은 수백만 개의 실행 가능한 객체를 포함하는 전역 분산 컴퓨터로 생각할 수 있으며, 각 객체는 자체 영구 데이터 저장소를 가지고 있습니다.

EVM은 *준-튜링 완전*(quasi-Turing-complete) 상태 머신입니다: "준"이라는 말은 모든 실행 프로세스가 주어진 스마트 컨트랙트 실행에 사용 가능한 가스 양에 의해 유한한 수의 계산 단계로 제한되기 때문입니다. 이처럼 *정지 문제*(halting problem)가 "해결"되어(모든 프로그램 실행이 정지됨), 실행이 (우발적으로 또는 악의적으로) 영원히 실행되어 이더리움 플랫폼 전체를 멈추게 하는 상황을 방지합니다. 정지 문제에 대해서는 이후 섹션에서 더 자세히 살펴볼 것입니다.

EVM은 *스택 기반 아키텍처*를 가지며, 모든 메모리 내 값을 스택에 저장합니다. 주로 네이티브 해싱과 타원 곡선 연산을 용이하게 하기 위해 256비트의 워드 크기로 작동하며, 여러 주소 지정 가능한 데이터 구성 요소를 가지고 있습니다:

- 실행할 스마트 컨트랙트의 바이트코드가 로드된 불변 프로그램 코드 ROM
- 모든 위치가 명시적으로 0으로 초기화된 휘발성 메모리
- 단일 트랜잭션 기간 동안만 지속되는 임시 스토리지(이더리움 상태의 일부가 아님)
- 이더리움 상태의 일부인 영구 스토리지, 역시 0으로 초기화됨

실행 중에 사용 가능한 환경 변수와 데이터 집합도 있습니다. 이 장의 후반부에서 이를 더 자세히 살펴볼 것입니다.

## 기존 기술과의 비교

*가상 머신*이라는 용어는 종종 VirtualBox나 QEMU와 같은 하이퍼바이저에 의한 실제 컴퓨터의 가상화나 Linux의 KVM과 같은 전체 운영 체제 인스턴스의 가상화에 적용됩니다. 이들은 각각 실제 하드웨어와 시스템 콜 및 기타 커널 기능의 소프트웨어 추상화를 제공해야 합니다.

EVM은 훨씬 더 제한된 영역에서 작동합니다: 단지 계산 엔진일 뿐이며, 예를 들어 Java 가상 머신(JVM) 명세와 유사하게 계산과 스토리지의 추상화만 제공합니다. 높은 수준의 관점에서 JVM은 기본 호스트 OS나 하드웨어에 구애받지 않는 런타임 환경을 제공하여 다양한 시스템에서 호환성을 가능하게 하도록 설계되었습니다. Java나 Scala(JVM 사용)와 같은 고수준 프로그래밍 언어 또는 C#(.NET 사용)은 각각의 가상 머신의 바이트코드 명령어 집합으로 컴파일됩니다. 마찬가지로 EVM은 자체 바이트코드 명령어 집합(다음 섹션에서 설명)을 실행하며, Solidity, Vyper, Yul과 같은 고수준 스마트 컨트랙트 프로그래밍 언어가 이로 컴파일됩니다.

따라서 EVM은 스케줄링 기능이 없습니다. 실행 순서가 외부적으로 조직되기 때문입니다: 이더리움 클라이언트는 검증된 블록 트랜잭션을 통해 어떤 스마트 컨트랙트를 어떤 순서로 실행해야 하는지 결정합니다. 이런 의미에서 이더리움 세계 컴퓨터는 JavaScript처럼 단일 스레드입니다. EVM은 "시스템 인터페이스" 처리나 "하드웨어 지원"도 없습니다—인터페이스할 물리적 머신이 없습니다. 이더리움 세계 컴퓨터는 완전히 가상입니다.

## 다른 블록체인들은 무엇을 하고 있나?

EVM은 확실히 암호화폐 공간에서 가장 널리 사용되는 가상 머신입니다. 대부분의 대안적 L1 및 L2 블록체인은 기존의 모든 도구와 프레임워크와의 호환성을 유지하고 이더리움 커뮤니티에서 직접 프로젝트와 개발자를 끌어들이기 위해 EVM을 사용합니다.

그럼에도 불구하고, 최근 몇 년간 다양한 가상 머신이 등장했습니다: Solana VM, Wasm VM, Cairo VM, Move VM이 아마도 가장 유명하고 흥미로운 것들이며, 각각 고유한 장단점이 있습니다. 이들은 스마트 컨트랙트 개발에 대해 다른 접근 방식을 취합니다:

**커스텀 언어**

Cairo와 Move 같은 일부 플랫폼은 스마트 컨트랙트 작성을 위해 특별히 설계된 프로그래밍 언어를 만들었습니다. 이것은 이더리움이 자체 가상 머신인 EVM을 위해 Solidity와 Vyper를 사용하는 것과 유사합니다.

**표준 언어**

Solana나 WebAssembly(Wasm)를 사용하는 다른 플랫폼들은 개발자가 널리 사용되는 프로그래밍 언어로 스마트 컨트랙트를 작성할 수 있게 합니다. 예를 들어, 이러한 플랫폼들은 종종 스마트 컨트랙트 개발을 위해 Rust를 지원합니다.

이러한 대안적 가상 머신이 EVM과 다른 또 다른 영역은 트랜잭션의 *병렬화*입니다. 우리는 이미 EVM이 어떤 종류의 병렬화도 없이 트랜잭션을 순차적으로 처리한다고 말했습니다. 일부 프로젝트는 이 단점을 개선하려고 했습니다. 예를 들어, Solana VM과 Move VM 모두 트랜잭션의 병렬 실행을 처리할 수 있지만, 항상 가능한 것은 아닙니다—즉, 두 트랜잭션이 동일한 컨트랙트와 상호작용하여 동일한 스토리지 조각을 수정하면 병렬로 실행할 수 없습니다.

이러한 가상 머신 성능 개선 노력이 이더리움 외부에서만 이루어지는 것은 아닙니다. 실제로 많은 팀이 병렬화와 EVM 바이트코드에서 네이티브 머신 코드로의 *사전 컴파일*(AOT) 또는 *적시 컴파일*(JIT)과 같은 멋진 기능을 추가하여 EVM의 현재 한계를 극복하려고 노력하고 있습니다.

## EVM 명령어 집합(바이트코드 연산)

EVM 명령어 집합은 예상할 수 있는 대부분의 연산을 제공합니다:

- 산술 및 비트 논리 연산
- 실행 컨텍스트 조회
- 스택, 메모리, 스토리지 접근
- 제어 흐름 연산
- 로깅, 호출 및 기타 연산자

일반적인 바이트코드 연산 외에도 EVM은 계정 정보(예: 주소와 잔액)와 블록 정보(예: 블록 번호와 현재 가스 가격)에 접근할 수 있습니다.

사용 가능한 *옵코드*와 그 기능을 살펴보며 EVM을 더 자세히 탐구해 봅시다. 예상대로 모든 피연산자는 스택에서 가져오고, 결과(해당되는 경우)는 종종 스택의 맨 위에 다시 놓입니다.

사용 가능한 옵코드는 다음 범주로 나눌 수 있습니다:

### 산술 연산

산술 옵코드 명령어에는 다음이 포함됩니다:

```
ADD        //스택의 상위 두 항목을 더함
MUL        //스택의 상위 두 항목을 곱함
SUB        //스택의 상위 두 항목을 뺌
DIV        //정수 나눗셈
SDIV       //부호 있는 정수 나눗셈
MOD        //모듈로(나머지) 연산
SMOD       //부호 있는 모듈로 연산
ADDMOD     //임의의 수에 대한 덧셈 모듈로
MULMOD     //임의의 수에 대한 곱셈 모듈로
EXP        //지수 연산
SIGNEXTEND //2의 보수 부호 있는 정수의 길이 확장
SHA3       //메모리 블록의 Keccak-256 해시 계산
```

별도로 명시되지 않는 한 모든 산술은 2^256을 법으로 수행되며, 0의 0승인 0^0은 1로 취급됩니다.

### 스택 연산

스택, 메모리, 스토리지 관리 명령어에는 다음이 포함됩니다:

```
POP     //스택에서 최상위 항목 제거
MLOAD   //메모리에서 워드 로드
MSTORE  //메모리에 워드 저장
MSTORE8 //메모리에 바이트 저장
SLOAD   //스토리지에서 워드 로드
SSTORE  //스토리지에 워드 저장
TLOAD   //임시 스토리지에서 워드 로드
TSTORE  //임시 스토리지에 워드 저장
MSIZE   //활성 메모리의 바이트 크기 가져오기
PUSH0   //스택에 값 0 배치
PUSHx   //스택에 x 바이트 항목 배치, x는 1에서 32(전체 워드)까지의
        // 정수
DUPx    //x번째 스택 항목 복제, x는 1에서 16까지의 정수
SWAPx   //1번째와 (x+1)번째 스택 항목 교환, x는 1에서 16까지의 정수
```

### 프로세스 흐름 연산

제어 흐름 명령어에는 다음이 포함됩니다:

```
STOP      //실행 중지
JUMP      //프로그램 카운터를 임의의 값으로 설정
JUMPI     //조건부로 프로그램 카운터 변경
PC        //프로그램 카운터 값 가져오기(이 명령어에 해당하는 증가 전)
JUMPDEST  //점프를 위한 유효한 목적지 표시
```

### 시스템 연산

프로그램을 실행하는 시스템의 옵코드에는 다음이 포함됩니다:

```
LOGx          //x개의 토픽이 있는 로그 레코드 추가, x는 0에서 4까지의 정수
CREATE        //관련 코드를 가진 새 계정 생성
CALL          //다른 계정으로 메시지 호출, 즉 다른 계정의 코드 실행
CALLCODE      //다른 계정의 코드로 이 계정으로 메시지 호출
RETURN        //실행 중지하고 출력 데이터 반환
DELEGATECALL  //대안적 계정의 코드로 이 계정으로 메시지 호출하되,
              //sender와 value의 현재 값 유지
STATICCALL    //계정으로 정적 메시지 호출, 즉 어떤 계정의 상태도
              //변경할 수 없음
REVERT        //실행 중지, 상태 변경을 되돌리지만 데이터와 남은 가스 반환
INVALID       //지정된 무효 명령어
SELFDESTRUCT  //실행 중지하고, 컨트랙트가 생성된 동일 트랜잭션에서
              //실행되면 계정을 삭제 등록. 사용이 강력히 권장되지 않으며
              //옵코드는 더 이상 사용되지 않는 것으로 간주됨
```

### 논리 연산

비교 및 비트 논리를 위한 옵코드에는 다음이 포함됩니다:

```
LT     //미만 비교
GT     //초과 비교
SLT    //부호 있는 미만 비교
SGT    //부호 있는 초과 비교
EQ     //동등 비교
ISZERO //단순 NOT 연산자
AND    //비트 AND 연산
OR     //비트 OR 연산
XOR    //비트 XOR 연산
NOT    //비트 NOT 연산
BYTE   //전체 너비 256비트 워드에서 단일 바이트 검색
```

### 환경 연산

실행 환경 정보를 다루는 옵코드에는 다음이 포함됩니다:

```
GAS            //사용 가능한 가스 양 가져오기(이 명령어의 감소 후)
ADDRESS        //현재 실행 중인 계정의 주소 가져오기
BALANCE        //주어진 계정의 계정 잔액 가져오기
ORIGIN         //이 EVM 실행을 시작한 EOA의 주소 가져오기
CALLER         //이 실행에 직접 책임 있는 호출자의 주소 가져오기
CALLVALUE      //이 실행에 책임 있는 호출자가 입금한 이더 양 가져오기
CALLDATALOAD   //이 실행에 책임 있는 호출자가 보낸 입력 데이터 가져오기
CALLDATASIZE   //입력 데이터의 크기 가져오기
CALLDATACOPY   //입력 데이터를 메모리로 복사
CODESIZE       //현재 환경에서 실행 중인 코드의 크기 가져오기
CODECOPY       //현재 환경에서 실행 중인 코드를 메모리로 복사
GASPRICE       //원래 트랜잭션에서 지정한 가스 가격 가져오기
EXTCODESIZE    //계정 코드의 크기 가져오기
EXTCODECOPY    //계정 코드를 메모리로 복사
RETURNDATASIZE //현재 환경에서 이전 호출의 출력 데이터 크기 가져오기
RETURNDATACOPY //이전 호출의 데이터 출력을 메모리로 복사
```

### 블록 연산

현재 블록 정보에 접근하기 위한 옵코드에는 다음이 포함됩니다:

```
BLOCKHASH  //가장 최근에 완료된 256개 블록 중 하나의 해시 가져오기
COINBASE   //블록 보상을 위한 블록의 수혜자 주소 가져오기
TIMESTAMP  //블록의 타임스탬프 가져오기
NUMBER     //블록 번호 가져오기
PREVRANDAO //이전 블록의 RANDAO 믹스 가져오기. 이 옵코드는 The Merge
           //하드포크 이후 DIFFICULTY를 대체함
GASLIMIT   //블록의 가스 한도 가져오기
```

## 이더리움 상태

EVM의 역할은 이더리움 프로토콜에 의해 정의된 대로 스마트 컨트랙트 코드 실행의 결과로 유효한 상태 전이를 계산하여 이더리움 상태를 업데이트하는 것입니다. 이 측면은 이더리움을 *트랜잭션 기반 상태 머신*으로 설명하게 하는데, 이는 외부 행위자(즉, 계정 보유자와 검증자)가 트랜잭션을 생성, 수락, 정렬하여 상태 전이를 시작한다는 사실을 반영합니다. 이 시점에서 이더리움 상태가 무엇으로 구성되는지 고려하는 것이 유용합니다.

최상위 수준에서 우리는 이더리움 *월드 상태*를 가지고 있습니다. 월드 상태는 이더리움 주소(160비트 값)에서 계정으로의 매핑입니다. 하위 수준에서 각 이더리움 주소는 이더 잔액(계정이 소유한 wei 수로 저장됨), 논스(EOA인 경우 이 계정에서 성공적으로 전송된 트랜잭션 수 또는 컨트랙트 계정인 경우 생성된 컨트랙트 수를 나타냄), 계정의 스토리지(스마트 컨트랙트에서만 사용되는 영구 데이터 저장소), 계정의 프로그램 코드(역시 계정이 스마트 컨트랙트 계정인 경우에만 해당)로 구성된 계정을 나타냅니다. 전통적으로 EOA는 항상 코드가 없고 스토리지가 비어 있었습니다. 그러나 [EIP-7702](https://eips.ethereum.org/EIPS/eip-7702)(2025년 5월 Pectra 업그레이드에서 활성화)는 EOA가 스마트 컨트랙트에 코드 실행을 위임할 수 있게 함으로써 이 가정을 변경합니다. EOA가 위임에 동의하면, 그 코드 필드는 `0xef0100 || address` 형식의 23바이트 *위임 지정*으로 설정되며, 여기서 `address`는 대상 컨트랙트의 20바이트 주소입니다. `0xef` 바이트는 [EIP-3541](https://eips.ethereum.org/EIPS/eip-3541)에 따라 금지된 옵코드이므로, 이 지정이 배포 가능한 컨트랙트 코드와 혼동되지 않도록 합니다. EVM이 위임된 EOA에 대한 호출을 만나면, EOA의 컨텍스트에서 대상 주소의 코드를 로드하고 실행합니다. 이는 위임된 EOA에 대한 `EXTCODESIZE`가 23(위임 지정의 크기)을 반환하는 반면, 위임된 코드 내에서 실행되는 `CODESIZE`는 대상 컨트랙트 코드의 크기를 반환함을 의미합니다. EOA는 위임된 코드를 실행할 때 스토리지도 사용할 수 있지만, 프로토콜은 위임 컨트랙트 간 마이그레이션 시 충돌을 방지하기 위해 [ERC-7201](https://eips.ethereum.org/EIPS/eip-7201) 네임스페이스 스토리지 레이아웃 사용을 권장합니다. 중요한 것은 위임된 EOA도 여전히 트랜잭션을 시작할 수 있다는 것입니다—트랜잭션에 서명하고 보낼 수 있는 EOA로 남아 있지만, 이제 스마트 컨트랙트 기능을 갖추게 됩니다. 위임은 제로 주소(`0x0000000000000000000000000000000000000000`)에 위임하여 해제할 수 있습니다.

트랜잭션이 스마트 컨트랙트 코드 실행을 초래하면, 현재 생성 중인 블록과 처리 중인 특정 트랜잭션과 관련된 모든 필수 정보로 EVM이 인스턴스화됩니다. 특히 EVM의 프로그램 코드 ROM은 호출되는 컨트랙트 계정의 코드로 로드되고, 프로그램 카운터는 0으로 설정되며, 스토리지는 컨트랙트 계정의 스토리지에서 로드되고, 메모리는 모두 0으로 설정되며, 모든 블록 및 환경 변수가 설정됩니다. 핵심 변수는 이 실행을 위한 가스 공급량이며, 트랜잭션 시작 시 발신자가 지불한 가스 양으로 설정됩니다(자세한 내용은 "실행 중 가스 회계" 참조). 코드 실행이 진행됨에 따라 실행된 연산의 가스 비용에 따라 가스 공급량이 감소합니다. 어느 시점에서든 가스 공급량이 0 미만이 되면 *가스 부족*(OOG) 예외가 발생합니다: 실행이 즉시 중지되고 트랜잭션이 중단됩니다. 발신자의 논스가 증가하고 이더 잔액이 중지 지점까지 코드 실행에 사용된 리소스에 대해 블록 수혜자에게 지불하기 위해 감소하는 것 외에는 이더리움 상태에 어떤 변경도 적용되지 않습니다. 이 시점에서 EVM은 이더리움 월드 상태의 샌드박스 복사본에서 실행되는 것으로 생각할 수 있으며, 어떤 이유로든 실행이 완료되지 못하면 이 샌드박스 버전은 완전히 폐기됩니다. 그러나 실행이 성공적으로 완료되면, 호출된 컨트랙트의 스토리지 데이터 변경, 생성된 새 컨트랙트, 시작된 이더 잔액 전송을 포함하여 실제 월드 상태가 샌드박스 버전과 일치하도록 업데이트됩니다.

코드 실행은 재귀적 프로세스입니다. 컨트랙트는 다른 컨트랙트를 호출할 수 있으며, 각 호출은 호출의 새 대상을 중심으로 또 다른 EVM이 인스턴스화됩니다. 각 인스턴스화는 상위 레벨 EVM의 샌드박스에서 초기화된 샌드박스 월드 상태를 가집니다. 각 인스턴스화(컨텍스트)에는 가스 공급을 위한 지정된 양의 가스도 주어지며(물론 상위 레벨에 남아 있는 가스 양을 초과하지 않음) 따라서 실행을 완료하기에 너무 적은 가스가 주어져 예외로 인해 자체적으로 중지될 수 있습니다. 다시 말해, 이러한 경우 샌드박스 상태는 폐기되고 실행은 상위 레벨의 EVM으로 돌아갑니다.

## 이더리움 스테이트리스

현재(2025년 6월 기준) 모든 이더리움 노드가 새로운 블록의 정확성을 확인하기 위해 포함된 모든 트랜잭션을 재실행하여 마지막 상태—이전에 월드 상태라고 불렀던 것—를 계산하고 유지해야 하지만, 적어도 부분적으로라도 이를 없애려는 계획이 있습니다.

아이디어는 새 블록을 생성하고 게시하기 위해 여전히 상태에 접근해야 하는 서처와 빌더와 같은 제한된 행위자 집합을 가지고, 다른 모든 노드는 상태 없이도 해당 블록을 암호학적으로 검증할 수 있게 하는 것입니다. 이것을 *스테이트리스*(statelessness)라고 합니다.

스테이트리스는 핵심 프로토콜에 대한 일부 수정이 필요하기 때문에 이더리움 로드맵의 먼 미래에 있습니다:

**인슈어런드 제안자-빌더 분리(ePBS)**

트랜잭션으로 블록을 채우는 작업과 P2P 네트워크에 제안하는 작업의 분리. 첫 번째는 슈퍼 최적화된 블록을 만들 수 있는 서처와 빌더라는 고도로 전문화된 엔티티가 수행하고, 두 번째는 이더리움 검증자 노드가 수행합니다. 이것은 아직 프로토콜에 인슈어런드되지 않았지만 이미 메인넷의 현실입니다. 실제로 대부분의 이더리움 블록은 이미 매우 소수의 대형 빌더에 의해 구축되고 있습니다.

**버클 트리**

이더리움이 현재 상태를 저장하는 데 사용하는 데이터 구조인 머클-패트리샤 트라이의 대체. 이것은 상태의 정확성을 검증하는 데 필요한 암호학적 증명의 크기를 크게 줄이고 레거시 머클-패트리샤 트라이보다 검증을 더 빠르게 만듭니다.

> **참고**
>
> 버클 트리를 대체할 수 있는 다른 해시 기반 이진 트리가 테스트되고 있습니다. 핵심 아이디어는 빠르고 쉽게 검증할 수 있는 작은 증명을 만들 수 있는 상태를 위한 데이터 구조를 갖는 것입니다.

이 두 업그레이드의 조합은 블록을 생성하려는 더 강력한 하드웨어를 가진 대형 엔티티만 전체 상태를 저장하고 접근해야 하는 시나리오로 이어질 수 있습니다. 새 블록과 함께 그들은 *암호학적 증인*을 생성합니다: 블록에 포함한 트랜잭션을 기반으로 새 상태가 올바르게 계산되었음을 증명하는 최소한의 데이터 집합입니다.

다른 모든 노드(검증자 노드 포함)는 전체 상태의 해시인 *상태 루트*만 저장합니다. 새 블록을 받으면 관련 증인을 사용하여 정확성을 검증합니다.

이것은 전체 상태를 저장할 필요가 없고 모든 트랜잭션을 (EVM 내에서) 재실행할 필요도 없지만, 제3자를 신뢰할 필요 없이 모든 것이 올바른지 여전히 검증할 수 있기 때문에 이더리움 노드 실행을 매우 가볍게 만듭니다. 심지어 스마트폰에서도 노드를 실행할 수 있을 것입니다...

연구가 빠르게 진행되고 있지만, 메인넷에서 스테이트리스를 갖기까지 아마도 몇 년은 더 걸릴 것입니다.

## 머클-패트리샤 트라이

현재 이더리움 상태는 *수정된 머클-패트리샤 트라이*라는 매우 독특한 데이터 구조를 사용하여 저장됩니다. 이전 섹션에서 머클-패트리샤 트리(MPT라고 부르겠습니다)를 간략히 언급했지만, 같은 논리가 버클 트라이에도 적용되기 때문에 이것이 어떻게 작동하고 왜 그런지, 그리고 이더리움이 상태(그리고 그것만이 아닌...)를 저장하는 방법으로 어떻게 사용되는지 이해하는 것이 매우 중요합니다. MPT에 들어가기 전에 머클 트리에 대해 알아야 합니다. 왜냐하면 MPT가 그 위에 구축되기 때문입니다.

### 머클 트리

머클 트리는 1988년 Ralph Merkle이 더 나은 디지털 서명을 구축하려는 시도에서 발명한 매우 오래된 데이터 구조입니다. 전체 데이터베이스를 보내지 않고도 일부 데이터가 데이터베이스에 존재하고 변조되지 않았음을 검증해야 할 때 매우 효율적입니다.

데이터 모음에서 머클 트리를 만드는 것은 매우 쉽습니다. 데이터를 여러 청크로 분리한 다음, 해당 청크를 함께 해시하고 이 마지막 단계를 재귀적으로 반복하여 하나의 최종 청크만 얻습니다. 그 청크는 *머클 루트*를 나타냅니다: 트리를 만드는 데 사용된 모든 데이터의 일종의 디지털 지문입니다.

이진 머클 트리—가장 간단한 형태의 머클 트리—를 처음부터 만들어 좀 더 친숙해지도록 합시다. 우리는 8개의 데이터 청크로 시작합니다—영어로 된 다른 단어라고 생각할 수 있습니다. 각 청크를 특정 해시 함수를 사용하여 해시합니다—이더리움은 4장에서 이미 언급한 것처럼 Keccak-256 해시 함수를 사용합니다—그림 14-2에서 hash_1, hash_2 등으로 표시된 머클 트리의 리프를 얻습니다. 그런 다음 각 리프 쌍을 연결하고 다시 해시하여 hash_12, hash_34 등을 만듭니다. 우리의 머클 루트인 hash_12345678이라는 단일 최종 결과를 얻을 때까지 이 연결 및 해시 프로세스를 두 번 더 반복합니다.

![이진 머클 트리](../images/ch14/maet_1402.png)

**그림 14-2.** 이진 머클 트리

이제 데이터를 저장하기 위해 왜 머클 트리가 필요한지 물을 수 있습니다. 각 청크를 고전적인 데이터베이스에 저장하는 것보다 더 복잡하지 않나요?

대답은 예, 모든 청크를 키-값 또는 SQL 데이터베이스에 저장하는 것보다 훨씬 더 복잡합니다. 이런 종류의 데이터 구조를 사용하는 유일한 이유는 청크 중 하나가 전체 데이터 모음에 존재하고 조작되지 않았음을 증명하는 저렴한 암호학적 증명을 제공하는 데 정말 효율적이기 때문입니다. 실제로 데이터를 저장하기 위해 일반 데이터베이스를 사용하고 특정 청크가 있다는 증명을 제공하라는 요청을 받으면, 읽는 사람이 우리가 거짓말하지 않는다고 확신할 수 있도록 전체 데이터셋을 게시해야 합니다.

이전 예제를 사용하여 이것이 실제로 어떻게 작동하는지 봅시다. data_1이 데이터셋에 포함되어 있음을 증명하고 싶다고 합시다. 순진한 접근 방식은 data_1에서 data_8까지 전체 데이터셋을 제공하는 것입니다: 총 8개 항목. 머클 트리를 사용하면 hash_2, hash_34, hash_5678만 제공하면 됩니다. 그러면 누구나 자신만의 머클 루트를 계산하고 처음에 계산한 것(공개적으로 공유됨)과 비교할 수 있습니다. 일치하면 그림 14-3에서 볼 수 있듯이 data_1이 초기 데이터셋의 일부임을 완전히 확신할 수 있습니다.

![data_1이 트리에 포함되어 있음을 검증하기 위한 머클 증명](../images/ch14/maet_1403.png)

**그림 14-3.** data_1이 트리에 포함되어 있음을 검증하기 위한 머클 증명

> **팁**
>
> 머클 트리를 재구성하려면 다음 단계를 따를 수 있습니다:
>
> 1. data_1을 해시하여 hash_1을 얻습니다.
> 2. hash_1을 제공된 hash_2와 연결하고 해시하여 hash_12를 얻습니다.
> 3. hash_12를 제공된 hash_34와 연결하고 해시하여 hash_1234를 얻습니다.
> 4. hash_1234를 제공된 hash_5678과 연결하고 해시하여 최종 머클 루트를 얻습니다.

머클 트리 없이 순진한 접근 방식으로 필요한 8개 항목에 비해 3개 항목만 사용하고 있다는 점에 주목하세요. 그리고 이것은 단지 장난감 예제입니다—데이터가 많을 때 절감 효과는 훨씬 더 큽니다.

수학적 용어로 말하면, 그림 14-4에서 보여주듯이 머클 트리는 순진한 접근 방식의 선형 O(n)에 비해 O(log(n)) 복잡성을 제공합니다.

![머클 트리 복잡성 비교](../images/ch14/maet_1404.png)

**그림 14-4.** O(n) 선형 복잡성(위)과 O(log(n)) 복잡성(아래) 비교

이더리움 세계에서 이것은 주소의 잔액, 트랜잭션 결과, 특정 스마트 컨트랙트의 바이트코드에 관한 증명을 제공하는 것이 더 저렴하고 쉽다는 것을 의미합니다.

### 비트코인의 머클 트리

비트코인은 블록체인 기술에서 머클 트리 사용을 개척했습니다. 실제로 모든 비트코인 블록에는 동일한 블록에 포함된 모든 트랜잭션의 머클 루트가 포함되어 있어 전체 블록 헤더를 수정하지 않고는(PoW도 손상됨) 어느 것도 수정할 수 없습니다.

### 이더리움의 머클-패트리샤 트라이

이더리움은 동일한 개념을 자신에게 적용하되, 특정 요구에 맞게 일부 수정을 가했습니다. 머클 트리는 비트코인 트랜잭션처럼 절대 변경되지 않는 영구적인 데이터에 완벽하게 적합합니다. 그러나 이더리움 상태는 끊임없이 변경되므로, 머클 트리를 조정하여 데이터를 자주 변경하면서도 유용한 속성을 유지해야 합니다.

여기서 머클-패트리샤 트라이가 등장합니다. 이름은 머클 트리, Patricia(Practical Algorithm to Retrieve Information Coded in Alphanumeric), 그리고 *retrieval*에서 유래한 *trie*라는 단어의 결합에서 비롯되며, 이것이 무엇을 위해 최적화되어 있는지 상기시켜 줍니다.

본질적으로 머클-패트리샤 트라이는 각 노드에 16개의 자식을 가진 수정된 머클 트리입니다. 키가 주소이고 값이 각 주소에 대한 잔액, 논스, 코드(있는 경우)와 같은 계정 정보인 많은 키-값 항목이 있는 이더리움 상태와 같은 데이터에 적합합니다. 키 자체가 트리에서 올바른 위치에 도달하기 위해 따라야 하는 경로에 인코딩되기 때문입니다.

저장하려는 다음 키-값 항목이 있다고 합시다:

```
car → Schumacher
```

Car는 (0x) 6 3 6 1 7 2로 16진수 인코딩되므로, 그림 14-5에서 볼 수 있듯이 머클 루트에서 시작하여 여섯 번째 자식으로 내려간 다음 세 번째 자식으로 다시 내려가서 해당 키와 연결된 값—이 예에서는 Schumacher—을 읽을 수 있는 최종 값에 도달할 때까지 이 프로세스를 반복해야 합니다.

![머클-패트리샤 트라이 예제](../images/ch14/maet_1405.png)

**그림 14-5.** 머클-패트리샤 트라이에 키-값 항목 car --> Schumacher 인코딩

특히 이더리움은 네 가지 머클-패트리샤 트라이를 사용합니다:

**상태 트라이**

전체 상태를 저장

**트랜잭션 트라이**

블록에 포함된 모든 트랜잭션을 저장

**영수증 트라이**

블록에 포함된 모든 트랜잭션의 결과를 저장

**스토리지 트라이**

스마트 컨트랙트 데이터를 저장

모든 이더리움 블록 헤더에는 상태, 트랜잭션, 영수증 트라이 머클 루트가 포함되어 있으며, 모든 계정(상태 트라이에 포함됨)은 자체 스토리지 트라이 머클 루트를 저장합니다.

## EVM 구성 요소 심층 탐구

이 섹션에서는 EVM의 각 구성 요소가 어떻게 작동하는지 자세히 살펴볼 것입니다. 마지막으로 실제 예제를 통해 모든 것이 실제로 어떻게 작동하는지 살펴보겠습니다.

### 스택

스택은 *후입선출*(LIFO) 순서로 연산을 수행하는 매우 간단한 데이터 구조이며, 모든 항목은 32바이트 객체입니다. 동시에 최대 1,024개의 항목을 호스팅할 수 있습니다.

EVM은 그림 14-6에서 볼 수 있듯이 다양한 종류의 옵코드를 통해 스택에 항목을 푸시하고 팝할 수 있으며, 요소의 순서를 조작할 수 있습니다.

![EVM 스택 연산](../images/ch14/maet_1406.png)

**그림 14-6.** EVM 스택은 LIFO 순서의 연산을 따릅니다

### 메모리

EVM 메모리는 바이트 주소 지정이 가능한 데이터 구조입니다: 본질적으로 매우 긴 바이트 배열입니다. 실제로 메모리의 모든 바이트는 32바이트(256비트) 키를 사용하여 접근할 수 있으며, 이는 최대 2^256 바이트를 포함할 수 있음을 의미합니다. 휘발성이므로—즉, 실행이 끝나면 삭제됨—항상 0으로 초기화됩니다.

그림 14-7에서 보여주듯이 메모리에서 단일 바이트를 읽고 쓸 수 있지만, 대부분의 연산은 더 큰 데이터 청크, 일반적으로 32바이트 청크를 읽거나 쓰는 것을 요구합니다.

![EVM 메모리 연산](../images/ch14/maet_1407.png)

**그림 14-7.** EVM 메모리는 휘발성, 바이트 주소 지정 가능한 데이터 구조입니다

> **참고**
>
> 기술적으로 EVM에서 단일 바이트를 읽을 수 없습니다. 전체 32바이트 워드만 읽을 수 있습니다. 단일 바이트를 읽는 것과 동일한 결과를 얻으려면, EVM은 해당 바이트를 포함하는 전체 워드를 로드한 다음 선택한 바이트만 반환하기 위해 "잘라야" 합니다.

### 스토리지

EVM 스토리지는 키(종종 *슬롯*이라고 함)와 값이 각각 32바이트 길이인 키-값 데이터 구조입니다. 이것은 모든 스마트 컨트랙트의 영구 메모리입니다: 여기에 저장된 모든 값은 다양한 트랜잭션과 블록에 걸쳐 무기한 유지됩니다. 각 스마트 컨트랙트는 자신의 스토리지만 접근하고 수정할 수 있으며, 값이 포함되지 않은 슬롯에 접근하려고 하면 오류를 발생시키지 않고 항상 값 0을 반환합니다. 그림 14-8은 두 컨트랙트 스토리지의 매우 기본적인 표현을 보여줍니다.

![EVM 스토리지](../images/ch14/maet_1408.png)

**그림 14-8.** EVM 스토리지는 키-값 데이터 구조를 가진 영구 메모리입니다

[EIP-1153](https://oreil.ly/fRvKl)과 함께 추가된 *임시 스토리지*도 있으며, 일반 스토리지와 동일한 방식으로 작동하지만 트랜잭션 실행 후 완전히 폐기된다는 점만 다릅니다. 이런 이유로 일반 스토리지보다 사용하기가 훨씬 저렴합니다.

### Calldata

Calldata는 다음 *콜 프레임*(즉, 샌드박스 EVM 환경)에 대한 입력으로 전송된 바이트를 항상 포함하는 불변 데이터 구조입니다. 예를 들어, 컨트랙트 생성 트랜잭션에서 calldata는 배포될 컨트랙트의 바이트코드를 포함합니다. 단순한 ETH 전송과 같이 비어 있을 수도 있습니다.

또한 초기 calldata가 있습니다:

```

```

```
[02]            PUSH0
[03]            MSTORE
[04]            PUSH0
[05]            CALLDATALOAD
[06]            PUSH1            AB
[08]            EQ
[09]            PUSH0
[0a]            MLOAD
[0b]            SSTORE
[0c]            STOP
```

## Solidity를 EVM 바이트코드로 컴파일

우리는 이미 7장에서 Solidity를 탐구했습니다. 이제 EVM이 해석할 수 있는 EVM 바이트코드로 어떻게 컴파일되는지 살펴보겠습니다.

Solidity 소스 파일을 EVM 바이트코드로 컴파일하는 것은 여러 방법으로 수행할 수 있습니다. 2장에서 우리는 온라인 Remix 컴파일러를 사용했습니다. 이 장에서는 명령줄에서 `solc` 실행 파일을 사용할 것입니다. 컴퓨터에 Solidity를 설치하려면 [단계를 따르세요](https://oreil.ly/JW--z).

옵션 목록을 보려면 다음 명령을 실행하세요:

```bash
$ solc --help
```

Solidity 소스 파일의 원시 옵코드 스트림 생성은 `--opcodes` 명령줄 옵션으로 쉽게 수행할 수 있습니다. 이 옵코드 스트림은 일부 정보가 생략되어 있지만(`--asm` 옵션이 전체 정보를 생성함), 이 논의에는 충분합니다. 예를 들어, 예제 Solidity 파일 `Example.sol`을 컴파일하고 옵코드 출력을 `BytecodeDir`이라는 디렉토리로 보내는 것은 다음 명령으로 수행됩니다:

```bash
$ solc -o BytecodeDir --opcodes Example.sol
```

좀 더 사람이 읽기 쉬운 출력을 생성하려면 `--asm`을 사용할 수도 있습니다:

```bash
$ solc -o BytecodeDir --asm Example.sol
```

다음 명령은 예제 프로그램의 바이트코드 바이너리를 생성합니다:

```bash
$ solc -o BytecodeDir --bin Example.sol
```



여기서 `PUSH1` 다음에 값이 `0x80`인 원시 바이트가 옵니다. 이 EVM 명령어는 프로그램 코드에서 옵코드 다음에 오는 단일 바이트를(리터럴 값으로) 스택에 푸시합니다. 다음과 같이 최대 32바이트 크기의 값을 스택에 푸시할 수 있습니다:

```
PUSH32 0x436f6e67726174756c6174696f6e732120536f6f6e20746f206d617374657221
```

`example.opcode`의 두 번째 `PUSH1` 옵코드는 스택 맨 위에 `0x40`을 저장합니다(이미 있던 `0x80`을 한 슬롯 아래로 밀어냄).

다음은 메모리 저장 연산인 `MSTORE`로, 값을 EVM의 메모리에 저장합니다. 두 개의 인수를 받으며, 대부분의 EVM 연산과 마찬가지로 스택에서 가져옵니다. 각 인수에 대해 스택이 "팝"됩니다—즉, 스택의 맨 위 값이 제거되고, 스택의 다른 모든 값이 한 위치씩 위로 이동합니다. `MSTORE`의 첫 번째 인수는 저장할 값이 놓일 메모리의 워드 주소입니다. 이 프로그램에서는 스택 맨 위에 `0x40`이 있으므로, 스택에서 제거되어 메모리 주소로 사용됩니다. 두 번째 인수는 저장할 값이며, 여기서는 `0x80`입니다. `MSTORE` 연산이 실행된 후, 스택은 다시 비어 있지만, 메모리 위치 `0x40`에 값 `0x80`(10진수로 128)이 있습니다.

다음 옵코드는 `CALLVALUE`로, 이 실행을 시작한 메시지 호출과 함께 보낸 이더 양을 스택 맨 위에 푸시하는 환경 옵코드입니다.

우리는 프로그램 전체를 이런 방식으로 단계별로 진행하여 이 코드가 수행하는 저수준 상태 변경을 완전히 이해할 수 있지만, 이 단계에서는 도움이 되지 않을 것입니다. 이 장의 후반부에서 다시 돌아올 것입니다.

## 컨트랙트 배포 코드

이더리움 플랫폼에서 새 컨트랙트를 생성하고 배포할 때 사용되는 코드와 컨트랙트 자체의 코드 사이에는 중요하지만 미묘한 차이가 있습니다. 새 컨트랙트를 생성하려면 `to` 필드가 비어 있고(null) `data` 필드가 컨트랙트의 *초기화 코드*로 설정된 특별한 트랜잭션이 필요합니다. 이러한 컨트랙트 생성 트랜잭션이 처리될 때, 새 컨트랙트 계정의 코드는 트랜잭션의 `data` 필드에 있는 코드가 아닙니다. 대신, 트랜잭션의 `data` 필드에 있는 코드가 프로그램 코드 ROM에 로드된 상태로 EVM이 인스턴스화된 다음, 해당 배포 코드 실행의 출력이 새 컨트랙트 계정의 코드로 사용됩니다. 이것은 새 컨트랙트가 배포 시점의 이더리움 월드 상태를 사용하여 프로그래밍 방식으로 초기화될 수 있도록 하며, 컨트랙트의 스토리지에 값을 설정하고 이더를 보내거나 추가 새 컨트랙트를 생성하는 것도 가능합니다.

컨트랙트를 오프라인으로 컴파일할 때—예를 들어 명령줄에서 `solc`를 사용하여—*배포 바이트코드* 또는 *런타임 바이트코드*를 얻을 수 있습니다. 배포 바이트코드는 새 컨트랙트가 호출될 때 실제로 실행될 바이트코드(즉, 런타임 바이트코드)와 컨트랙트의 생성자를 기반으로 모든 것을 초기화하는 코드를 포함하여 새 컨트랙트 계정의 초기화의 모든 측면에 사용됩니다. 반면 런타임 바이트코드는 새 컨트랙트가 호출될 때 실행되는 정확한 바이트코드일 뿐 그 이상은 아닙니다; 배포 중에 컨트랙트를 초기화하는 데 필요한 바이트코드는 포함하지 않습니다.

이전 장에서 만든 간단한 `Faucet.sol` 컨트랙트를 예로 들어봅시다:

```solidity
// SPDX-License-Identifier: GPL-3.0
pragma solidity 0.8.27;

contract Faucet {
  // 요청하는 누구에게나 이더 제공
  function withdraw(uint256 _withdrawAmount, address payable _to) public {
    // 출금 금액 제한
    require(_withdrawAmount <= 1000000000000);
    // 요청한 주소로 금액 전송
    _to.transfer(_withdrawAmount);
  }

  // 이더를 받기 위한 함수. msg.data가 비어 있어야 함
  receive() external payable {}

  // msg.data가 비어 있지 않을 때 호출되는 폴백 함수
  fallback() external payable {}
}
```

배포 바이트코드를 얻으려면 `solc --bin Faucet.sol`을 실행합니다. 대신 런타임 바이트코드만 원한다면 `solc --bin-runtime Faucet.sol`을 실행합니다. 이 명령들의 출력을 비교하면 런타임 바이트코드가 배포 바이트코드의 부분 집합임을 알 수 있습니다. 다시 말해, 런타임 바이트코드는 배포 바이트코드 내에 완전히 포함되어 있습니다.

### 온체인에서 컨트랙트를 배포하는 CREATE 대 CREATE2

`CREATE`와 `CREATE2`는 온체인에서 새 컨트랙트를 배포할 수 있는 유일한 두 옵코드입니다. 주요 차이점은 새로 생성된 컨트랙트의 결과 주소와 관련이 있습니다. `CREATE`를 사용하면 목적지 주소가 다음과 같이 계산됩니다:

```
address = keccak256[rlp(sender_address ++ sender_nonce)][12:]
```

발신자 주소 뒤에 논스가 오는 RLP 인코딩의 Keccak-256 해시의 가장 오른쪽 20바이트입니다.

`CREATE2`는 2019년 Constantinople 하드포크에서 추가되어 개발자가 결과 주소가 발신자의 상태(즉, 논스)에 의존하지 않는 새 컨트랙트를 생성할 수 있게 했습니다. 실제로 `CREATE` 옵코드와 정확히 같은 방식으로 작동하지만, 목적지 주소는 다음과 같이 계산됩니다:

```
address = keccak256(0xff ++ sender_address ++ salt ++ keccak256(init_code))[12:]
```

여기서:

- `init_code`는 새 컨트랙트의 배포 바이트코드입니다.
- `salt`는 (스택에서 가져온) 32바이트 값입니다

## 바이트코드 디스어셈블

EVM 바이트코드를 디스어셈블하는 것은 고수준 Solidity가 EVM에서 어떻게 작동하는지 이해하는 좋은 방법입니다. 이를 수행하는 데 사용할 수 있는 몇 가지 디스어셈블러가 있습니다:

- [**Ethersplay**](https://oreil.ly/xW6fH)는 디스어셈블러인 Binary Ninja용 EVM 플러그인입니다. 참고로 플러그인을 사용하려면 Binary Ninja의 완전한 앱을 구매해야 합니다.
- [**Heimdall**](https://oreil.ly/klTJ3)은 바이트코드 분석과 검증되지 않은 컨트랙트에서 정보 추출을 전문으로 하는 고급 EVM 스마트 컨트랙트 툴킷입니다.

```
PUSH2 0x0020
JUMPI
```

우리가 본 것처럼 `PUSH1 0x04`는 스택 맨 위에 `0x04`를 놓으며, 그렇지 않으면 비어 있습니다. `CALLDATASIZE`는 트랜잭션과 함께 보낸 데이터(calldata로 알려진)의 바이트 크기를 가져와 해당 숫자를 스택에 푸시합니다. 이러한 연산이 실행된 후 스택은 다음과 같습니다:

```
스택
<tx의 calldata 길이>
0x4
```

다음 명령어는 "미만"의 약자인 `LT`입니다. `LT` 명령어는 스택 맨 위의 항목이 다음 항목보다 작은지 확인합니다. 우리의 경우 `CALLDATASIZE`의 결과가 4바이트보다 작은지 확인합니다.

왜 EVM은 트랜잭션의 calldata가 최소 4바이트인지 확인할까요? *함수 식별자*가 작동하는 방식 때문입니다. 각 Solidity 함수는 Keccak-256 해시의 처음 4바이트로 식별됩니다. 함수의 이름과 모든 인수를 `keccak256` 해시 함수에 넣으면 함수 식별자를 도출할 수 있습니다. 우리의 경우:

```
keccak256("withdraw(uint256,address)") = 0x00f714ce...
```

따라서 `withdraw(uint256,address)` 함수의 함수 식별자는 `0x00f714ce`입니다. 이것이 결과 해시의 처음 4바이트이기 때문입니다. 함수 식별자는 항상 4바이트 길이이므로, 컨트랙트에 보낸 트랜잭션의 전체 데이터 필드가 4바이트 미만이면 폴백 함수가 정의되지 않은 한 트랜잭션이 통신할 수 있는 함수가 없습니다. `Faucet.sol`에 이러한 폴백 함수를 구현했기 때문에, calldata의 길이가 4바이트 미만일 때 EVM은 이 함수로 점프합니다.

`LT`는 스택에서 상위 두 값을 팝하고, 트랜잭션의 데이터 필드가 4바이트 미만이면 1을 푸시합니다. 그렇지 않으면 0을 푸시합니다. 우리 예제에서는 컨트랙트에 보낸 트랜잭션의 데이터 필드가 4바이트 미만이라고 가정합시다.

`PUSH2 0x0020` 명령어는 스택에 바이트 `0x0020`을 푸시합니다. 이 명령어 후 스택은 다음과 같습니다:

```
스택
0x0020
0x1
```

다음 명령어는 "조건부 점프"를 의미하는 `JUMPI`입니다. 다음과 같이 작동합니다:

```
jumpi(label, cond) // "cond"가 참이면 "label"로 점프
```

우리의 경우 `label`은 `0x0020`이며, 이는 스마트 컨트랙트에서 폴백 함수가 있는 위치입니다. `cond` 인수는 앞서 `LT` 명령어의 결과인 1입니다. 이 전체 시퀀스를 말로 표현하면, 트랜잭션 데이터가 4바이트 미만이면 컨트랙트는 폴백 함수로 점프합니다.

`0x20`에서 두 개의 `JUMPDEST` 명령어 후에 `STOP` 명령어만 따릅니다. 폴백 함수를 선언했지만 비워 두었기 때문입니다. 그림 14-24에서 볼 수 있듯이, 폴백 함수를 구현하지 않았다면 컨트랙트는 대신 예외를 발생시켰을 것입니다.

![폴백 함수로 이어지는 JUMPI 명령어](../images/ch14/maet_1424.png)

**그림 14-24.** 폴백 함수로 이어지는 JUMPI 명령어

> **참고**
>
> Heimdall은 EVM이 실제로 오프셋 0x00에서 시작하는 것으로 해석하더라도 오프셋이 0x01에서 시작하는 것으로 바이트코드를 표현합니다. 이전 예에서 JUMPI 명령어는 조건이 참이면 오프셋 0x20으로 가라고 EVM에 지시하지만, 그래프에서 오프셋 0x20은 여기서 0x21로 표현됩니다. 경험상 그래프에서 찾으려면 EVM의 모든 오프셋에 1을 더하면 됩니다.

디스패처의 중앙 블록을 살펴봅시다. 4바이트보다 큰 길이의 calldata를 받았다고 가정하면, `JUMPI` 명령어는 폴백 함수로 점프하지 않습니다. 대신 코드 실행은 다음 명령어들로 진행됩니다:

```
PUSH0 0x0
CALLDATALOAD
PUSH1 0xe0
SHR
DUP1
PUSH3 0xf714ce
EQ
PUSH2 0X23
JUMPI
```

`PUSH0`은 스택에 0을 푸시하며, 이제 다시 비어 있습니다. `CALLDATALOAD`는 스마트 컨트랙트에 보낸 calldata 내의 인덱스를 인수로 받아 해당 인덱스에서 32바이트를 읽습니다:

```
calldataload(p) //바이트 위치 p에서 시작하는 32바이트의 calldata 로드
```

`PUSH0` 명령어에서 전달된 인덱스가 0이므로, `CALLDATALOAD`는 바이트 0에서 시작하는 32바이트의 calldata를 읽은 다음 스택 맨 위에 푸시합니다(원래 `0x0`을 팝한 후). `PUSH1 0xe0` 명령어 후 스택은 다음과 같습니다:

```
스택
0xe0
<바이트 0에서 시작하는 32바이트의 calldata>
```

`SHR`은 스택의 32바이트 값 요소에 대해 `0xe0` 비트(224비트, 28바이트)의 논리적 오른쪽 시프트를 수행합니다. calldata를 28바이트만큼 오른쪽으로 시프트함으로써 calldata의 처음 4바이트를 분리합니다. 실제로 오른쪽으로 시프트할 때 첫 번째 비트 앞의 모든 비트는 폐기되고, 새 비트는 0으로 설정됩니다. calldata의 처음 4바이트가 함수 식별자를 나타낸다는 것을 기억하세요.

### 논리적 비트 시프트 예제

예제로 이것을 더 잘 이해할 수 있습니다. 스택이 다음과 같다고 합시다:

```
스택
0x1234567890 // 5바이트 요소
```

처음 2바이트(즉, `0x1234`)만 얻고 싶습니다. EVM 옵코드만 사용하여 이를 달성하려면 다음을 수행할 수 있습니다:

```
PUSH1 0x18 // 이것은 16진수로 24를 나타내며, 24비트 = 3바이트
SHR
```

실제로 스택 항목을 3바이트만큼 오른쪽으로 시프트하면(각 바이트는 여기서 2개의 16진수 숫자로 표현됨을 기억하세요) 다음 항목을 얻습니다:

```
0x0000001234 | 4567890
```

`4567890` 부분은 폐기되고, 남은 것은:

```
스택
0x1234
```

모든 선행 0은 의미가 없으므로 무시할 수 있습니다.

---

새 스택은:

```
스택
<데이터에서 보낸 함수 식별자>
```

다음 명령어는 스택의 첫 번째 항목을 복제하는 `DUP1`입니다. 스택은 이제:

```
스택
<데이터에서 보낸 함수 식별자>
<데이터에서 보낸 함수 식별자>
```

이제 푸시 데이터 `0xf714ce`가 뒤따르는 `PUSH3` 명령어가 있습니다. 이 옵코드는 단순히 (푸시) 데이터를 스택에 푸시합니다. 이 옵코드 후 스택은 다음과 같습니다:

```
스택
0xf714ce
<데이터에서 보낸 함수 식별자>
<데이터에서 보낸 함수 식별자>
```

이제 `0xf714ce`가 익숙해 보이나요? `withdraw(uint256,address)` 함수의 함수 식별자가 무엇인지 기억하시나요? `0x00f714ce`입니다... 선행 0은 무시할 수 있으므로 같은 숫자임을 주목하세요.

다음 명령어인 `EQ`는 스택의 상위 두 항목을 팝하고 비교합니다. 이것이 디스패처가 주요 작업을 수행하는 곳입니다: 트랜잭션의 `msg.data` 필드에서 보낸 함수 식별자가 `withdraw(uint256,address)`의 것과 일치하는지 비교합니다. 같으면 `EQ`는 스택에 1을 푸시하며, 이는 궁극적으로 withdraw 함수로 점프하는 데 사용됩니다. 그렇지 않으면 `EQ`는 스택에 0을 푸시합니다.

컨트랙트에 보낸 트랜잭션이 실제로 `withdraw(uint256,address)`의 함수 식별자로 시작했다고 가정하면, 스택은 다음과 같이 됩니다:

```
스택
1
<데이터에서 보낸 함수 식별자> (이제 0x00f714ce로 알려짐)
```

다음으로 컨트랙트에서 `withdraw(uint256,address)` 함수가 있는 주소인 `PUSH2 0x23`이 있습니다. 이 명령어 후 스택은 다음과 같습니다:

```
스택
0x23
1
<msg.data에서 보낸 함수 식별자>
```

다음은 `JUMPI` 명령어이며, 다시 스택의 상위 두 요소를 인수로 받습니다. 이 경우 `JUMPI(0x23, 1)`이 있으며, 이는 EVM에 `withdraw(uint256,address)` 함수의 위치로 점프를 실행하라고 지시하고, 해당 함수의 코드 실행이 진행될 수 있습니다.

## 튜링 완전성과 가스

이미 언급했듯이 간단히 말해서 시스템이나 프로그래밍 언어는 어떤 프로그램이든 실행할 수 있으면 *튜링 완전*합니다. 그러나 이 기능에는 매우 중요한 주의 사항이 있습니다: 일부 프로그램은 실행하는 데 영원히 걸립니다. 중요한 측면은 프로그램을 보기만 해서는 실행에 영원히 걸릴지 여부를 알 수 없다는 것입니다. 실제로 프로그램 실행을 진행하고 완료될 때까지 기다려야 합니다. 물론, 실행에 영원히 걸린다면 알아내기 위해 영원히 기다려야 합니다. 이것을 *정지 문제*라고 하며, 해결되지 않으면 이더리움에 큰 문제가 될 것입니다.

정지 문제 때문에 이더리움 세계 컴퓨터는 절대 멈추지 않는 프로그램을 실행하도록 요청받을 위험이 있습니다. 이것은 우연히 또는 악의적으로 발생할 수 있습니다. 이더리움이 스케줄러 없이 단일 스레드 머신처럼 작동한다고 설명했으므로, 무한 루프에 갇히면 이더리움은 사용할 수 없게 됩니다.

그러나 가스를 사용하면 해결책이 있습니다: 미리 지정된 최대 계산량이 수행된 후에도 실행이 끝나지 않으면 EVM에 의해 프로그램 실행이 중지됩니다. 이것은 EVM을 준-튜링 완전 머신으로 만듭니다: 입력한 모든 프로그램을 실행할 수 있지만 프로그램이 특정 계산량 내에서 종료되는 경우에만 가능합니다. 그 한계는 이더리움에서 고정되어 있지 않습니다—최대치(*블록 가스 한도*라고 함)까지 지불하여 늘릴 수 있으며, 모든 사람이 시간이 지남에 따라 그 최대치를 늘리는 데 동의할 수 있습니다. 그럼에도 불구하고 어느 시점에서든 한계가 있으며, 실행하는 동안 너무 많은 가스를 소비하는 트랜잭션은 중지됩니다.

다음 섹션에서는 가스를 살펴보고 어떻게 작동하는지 자세히 살펴볼 것입니다.

### 가스란 무엇인가?

가스는 이더리움 블록체인에서 작업을 수행하는 데 필요한 계산 및 스토리지 리소스를 측정하는 이더리움의 단위입니다. 트랜잭션 수수료가 킬로바이트 단위의 트랜잭션 크기만 고려하는 비트코인과 달리, 이더리움은 트랜잭션과 스마트 컨트랙트 코드 실행에 의해 수행되는 모든 계산 단계를 고려해야 합니다.

트랜잭션이나 컨트랙트가 수행하는 각 연산에는 고정된 양의 가스가 소요됩니다. 이더리움 "Yellow Paper"의 몇 가지 예:

- 두 숫자를 더하는 데 3 가스
- Keccak-256 해시 계산에 30 가스 + 해시되는 256비트 데이터당 6 가스
- 트랜잭션 전송에 21,000 가스

가스는 이더리움의 중요한 구성 요소이며 이중 역할을 합니다: 이더의 (변동적인) 가격과 검증자가 수행하는 작업에 대한 보상 사이의 버퍼 역할과 DoS 공격에 대한 방어 역할입니다. 우발적이거나 악의적인 무한 루프 또는 네트워크의 기타 계산 낭비를 방지하기 위해, 각 트랜잭션의 개시자는 지불할 의향이 있는 계산량에 대한 한도를 설정해야 합니다. 따라서 가스 시스템은 공격자가 "스팸" 트랜잭션을 보내는 것을 억제합니다. 소비하는 계산, 대역폭, 스토리지 리소스에 비례하여 지불해야 하기 때문입니다.

### 실행 중 가스 회계

트랜잭션을 완료하기 위해 EVM이 필요할 때, 처음에는 트랜잭션의 가스 한도에 지정된 양과 동일한 가스 공급이 주어집니다. 실행되는 모든 옵코드에는 가스 비용이 있으므로 EVM이 프로그램을 단계별로 진행함에 따라 EVM의 가스 공급이 줄어듭니다. 각 연산 전에 EVM은 연산 실행에 대해 지불할 충분한 가스가 있는지 확인합니다. 충분한 가스가 없으면 실행이 중지되고 트랜잭션이 되돌려집니다.

EVM이 가스 부족 없이 성공적으로 실행을 완료하면, 사용된 가스 비용이 트랜잭션에 지정된 가스 가격을 기준으로 이더로 변환되어 검증자에게 트랜잭션 수수료로 지불됩니다:

```
검증자 수수료 = 가스 비용 × 가스 가격
```

가스 공급에 남아 있는 가스는 트랜잭션에 지정된 가스 가격을 기준으로 다시 이더로 변환되어 발신자에게 환불됩니다:

```
남은 가스 = 가스 한도 - 가스 비용
환불 이더 = 남은 가스 × 가스 가격
```

실행 중 트랜잭션이 "가스 부족"이 되면, 연산이 즉시 종료되고 OOG 예외가 발생합니다. 트랜잭션이 되돌려지고 상태에 대한 모든 변경이 롤백됩니다. 트랜잭션이 실패했지만, 검증자가 이미 그 시점까지 계산 작업을 수행했고 이에 대한 보상을 받아야 하므로 발신자에게 트랜잭션 수수료가 청구됩니다.

#### 가스 회계 고려 사항

EVM에 의해 수행될 수 있는 다양한 연산의 상대적 가스 비용은 공격으로부터 이더리움 블록체인을 최대한 보호하기 위해 신중하게 선택되었습니다. 계산 집약적인 연산은 더 많은 가스가 듭니다. 예를 들어 `SHA3` 함수를 실행하는 것은 `ADD` 연산(3 가스)보다 10배 더 비쌉니다(30 가스). 더 중요한 것은 `EXP`와 같은 일부 연산은 피연산자의 크기에 따라 추가 지불이 필요합니다. EVM 메모리 사용과 컨트랙트의 온체인 스토리지에 데이터를 저장하는 데도 가스 비용이 있습니다.

가스 비용을 실제 리소스 비용에 맞추는 것의 중요성은 2016년에 공격자가 비용의 불일치를 발견하고 악용했을 때 입증되었습니다. 이 공격은 계산적으로 매우 비싼 트랜잭션을 생성하여 이더리움 메인넷을 거의 멈추게 했습니다. 이 불일치는 상대적 가스 비용을 조정한 하드포크("Tangerine Whistle"이라는 코드명)에 의해 해결되었습니다.

#### 이더리움 미래의 가스 회계

가스 계량은 이더리움이 네트워크의 전체 트랜잭션 부하를 처리하는 방식의 매우 중요한 부분이었고 여전히 그렇습니다. 가스 비용이 특정 종류의 행동에 대한 핵심 인센티브임을 이해하는 것이 매우 중요합니다. 미래에는 다른 옵코드가 소비하는 가스 양에 일부 변경이 있을 수 있습니다.

예를 들어, EIP-4844 블롭 트랜잭션을 도입한 Cancun 업그레이드 전에는 모든 L2가 트랜잭션의 calldata 일부로 이더리움에 데이터를 게시했습니다. 해당 데이터는 이더리움의 모든 노드에 영원히 저장됩니다. 이제 L2가 블롭 트랜잭션을 통해 이더리움에 데이터를 게시하는 더 나은 방법이 있으므로, 미래에는 롤업이 블롭 트랜잭션을 사용하도록 장려하고 노드가 모든 데이터를 영원히 저장해야 하는 부담을 줄이기 위해 calldata가 지금보다 훨씬 더 비싸질 수 있습니다.

#### 가스 비용 대 가스 가격

*가스 비용*은 EVM에서 트랜잭션이 사용한 계산과 스토리지의 측정치인 반면, 가스 자체도 이더로 측정되는 *가격*이 있습니다. 트랜잭션을 수행할 때 발신자는 각 가스 단위에 대해 지불할 의향이 있는 가스 가격(이더로)을 지정하여 시장이 이더 가격과 계산 연산 비용(가스로 측정됨) 사이의 관계를 결정할 수 있게 합니다:

```
트랜잭션 수수료 = 총 사용 가스 × 지불한 가스 가격(이더로)
```

새 블록을 구성할 때 이더리움 네트워크의 검증자는 더 높은 가스 가격을 제안하는 것을 선택하여 대기 중인 트랜잭션 중에서 선택할 수 있습니다. 따라서 더 높은 가스 가격을 제안하면 검증자가 트랜잭션을 포함하고 더 빨리 확인하도록 인센티브를 제공합니다.

실제로 트랜잭션의 발신자는 사용될 것으로 예상되는 가스 양보다 높거나 같은 가스 한도를 설정합니다. 가스 한도가 소비된 가스 양보다 높게 설정되면, 검증자는 실제로 수행한 작업에 대해서만 보상을 받기 때문에 발신자는 초과 금액을 환불받습니다.

가스 비용과 가스 가격의 구분을 명확히 하는 것이 중요합니다. 요약하면:

- *가스 비용*은 특정 연산을 수행하는 데 필요한 가스 단위 수입니다.
- *가스 가격*은 트랜잭션을 이더리움 네트워크에 보낼 때 가스 단위당 지불할 의향이 있는 이더 양입니다.

> **팁**
>
> 가스에는 가격이 있지만, "소유"하거나 "사용"할 수 없습니다. 가스는 수행되는 계산 작업량의 수치로 EVM 내부에만 존재합니다. 발신자는 이더로 트랜잭션 수수료가 청구되며, 이는 EVM 회계를 위해 가스로 변환된 다음 다시 이더로 변환되어 검증자에게 트랜잭션 수수료로 지불됩니다.

#### 음의 가스 비용

이더리움은 컨트랙트 실행 중 사용된 가스의 일부를 환불하여 사용된 스토리지 변수의 삭제를 장려합니다. EVM에서 음의 가스 비용을 가진 연산은 하나뿐입니다: 스토리지 주소를 0이 아닌 값에서 0으로 변경하는 것(`SSTORE[x] = 0`)은 환불 가치가 있습니다. 환불 가스 양은 고정되어 있지 않고 이 연산 전후의 스토리지 슬롯 값에 따라 달라집니다. 환불 메커니즘의 악용을 피하기 위해 트랜잭션에 대한 최대 환불은 총 가스 비용 양의 5분의 1(내림)로 설정됩니다.

과거에는 음의 가스 비용을 가진 또 다른 연산이 있었습니다: `SELFDESTRUCT`. 컨트랙트 삭제(`SELFDESTRUCT`를 통해)는 24,000 가스 환불 가치가 있었습니다. 현재 `SELFDESTRUCT` 옵코드는 더 이상 사용되지 않으며, 더 이상 사용하지 않는 것이 권장됩니다.

> **팁**
>
> 가스 환불은 트랜잭션 끝에 적용됩니다. 따라서 트랜잭션이 실행 끝에 도달할 충분한 가스가 없으면 실패하고 환불이 주어지지 않습니다.

### 블록 가스 한도

블록 가스 한도는 블록의 모든 트랜잭션에 의해 소비될 수 있는 최대 가스 양입니다. 블록에 들어갈 수 있는 트랜잭션 수를 제한합니다.

예를 들어 가스 한도가 30,000, 30,000, 40,000, 50,000, 50,000으로 설정된 5개의 트랜잭션이 있다고 합시다. 블록 가스 한도가 180,000이면 해당 트랜잭션 중 4개가 블록에 들어갈 수 있고 5번째는 미래 블록을 기다려야 합니다. 앞서 논의한 바와 같이 검증자는 블록에 포함할 트랜잭션을 결정합니다. 다른 검증자는 다른 조합을 선택할 가능성이 높은데, 주로 네트워크에서 다른 순서로 트랜잭션을 받기 때문입니다.

검증자가 현재 블록 가스 한도보다 더 많은 가스를 필요로 하는 트랜잭션을 포함하려고 하면 블록이 네트워크에 의해 거부됩니다. 대부분의 이더리움 클라이언트는 "트랜잭션이 블록 가스 한도를 초과합니다"라는 경고를 표시하여 이러한 트랜잭션을 발행하지 못하게 합니다. [Etherscan](https://etherscan.io)에 따르면, 이 글을 쓰는 시점(2025년 6월)에 이더리움 메인넷의 블록 가스 한도는 3,600만 가스이며, 이는 약 1,428개의 기본—즉, ETH 전송—트랜잭션(각각 21,000 가스 소비)이 블록에 들어갈 수 있음을 의미합니다.

#### 누가 블록 가스 한도를 선택하나?

2021년 8월 5일 EIP-1559의 도입 전에는 채굴자(이더리움은 당시 PoW 기반 합의 알고리즘을 사용)가 블록 가스 한도에 투표할 수 있는 내장 메커니즘이 있어 후속 블록에서 용량을 늘리거나 줄일 수 있었습니다. 블록의 채굴자는 블록 가스 한도를 어느 방향으로든 1/1024(0.0976%) 비율로 조정하도록 투표할 수 있었습니다. 그 결과 네트워크의 필요에 따라 채굴자의 해시파워를 따라 조정 가능한 블록 크기가 생겼습니다.

이제 검증자는 *가스 목표*—즉, 블록이 평균적으로 얼마나 많은 가스를 소비해야 하는지—에 투표하며, 가스 한도는 목표의 두 배로 정의됩니다. 각 검증자가 준수해야 하는 1/1024 조정 계수는 이전과 동일하게 유지됩니다.

#### 왜 블록 가스 한도가 상승하지 않나?

검증자가 가스 목표에 투표할 수 있고 이것이 직접적으로 가스 한도로 변환된다면, 왜 블록 가스 한도가 3,000만 대신 10억으로 상승하지 않는지 궁금할 수 있습니다. 더 큰 블록 가스 한도는 더 많은 트랜잭션이 블록에 들어갈 수 있음을 의미하므로 최종 사용자에게 트랜잭션이 더 저렴해질 것입니다.

대답은 가스 한도를 올리면 네트워크의 탈중앙화와 관련된 몇 가지 단점이 있다는 것입니다. 실제로 더 큰 블록이 더 많은 트랜잭션을 포함할 수 있지만, 이는 블록을 제시간에 검증하기가 더 어려워진다는 것을 의미하며, 이로 인해 일반 하드웨어로 만든 이더리움 노드가 죽고 강력한 서버만 전체 블록을 검증할 수 있게 될 수 있습니다. 그뿐만 아니라 더 큰 블록은 더 큰 상태 성장을 의미합니다. 최종 결과는 이전과 같습니다: 대형 서버만 노드를 완전히 실행할 수 있게 됩니다.

역사적으로 그림 14-25에서 볼 수 있듯이 블록 가스 한도는 프로토콜 업그레이드 중에 한 번에 올랐습니다. 그리고 그 값은 일반적으로 모든 클라이언트가 트랜잭션 부하를 처리하고 블록을 제시간에 처리할 수 있다고 확신하는 수준에서 핵심 개발자가 제안한 수준으로 설정됩니다.

#### 왜 블록 가스 한도를 올리지 않나?

블록 가스 한도가 3년 이상 3,000만에서 "고정"된 것처럼 보이지만, PBS("이더리움 스테이트리스" 참조)를 통해 정교한 하드웨어를 가진 행위자가 블록을 빌드하고—빌더—제안자에게—검증자—P2P 네트워크에 게시하도록 보내면서, 실제 사용된 가스를 거의 일정하게 유지하면서 블록 가스 한도를 무한정 올리려는 인센티브가 있습니다.

실제로 EIP-1559에 따르면 블록 가스 목표가 실제 사용된 가스보다 훨씬 높으면 기본 수수료가 계속 감소하여 거의 모든 가스 수수료가 소각되는 대신(기본 수수료는 소각되어 해당 ETH를 공급에서 제거) 검증자에게 간다는 점까지 도달합니다.

따라서 검증자의 이점은 두 가지입니다:

- ETH 공급을 줄이고 소각하는 대신 가스 수수료를 자신이 보관할 수 있습니다.
- 필요할 때 많은 MEV 활동을 포착하는 더 큰 블록을 생성하여 더 많은 수수료를 받을 수 있습니다.

이것에 대해 궁금하다면 [James Prestwich의 기사](https://oreil.ly/EImcE)에서 더 읽어보세요.

## 구체적 구현

모든 이더리움 노드에는 이 장에서 설명한 EVM의 구체적인 구현이 있습니다. 다음은 가장 유명하고 많이 사용되는 것들의 목록입니다:

**Go-ethereum EVM**

Geth는 가장 많이 채택되고 가장 오래된 실행 클라이언트입니다. Go로 작성된 EVM의 완전한 구현을 포함합니다.

**Execution-spec EVM**

이더리움 재단은 이더리움 실행 클라이언트와 관련된 명세가 포함된 GitHub의 Python 저장소를 유지합니다. Python으로 작성된 완전한 EVM 구현이 있습니다.

**Revm**

Revm은 뛰어난 사용자 정의 가능성과 적응성 덕분에 일반 이더리움 클라이언트 외부에서 가장 많이 사용되는 EVM 구현 중 하나입니다.

**Evmone**

Evmone은 아마도 가장 빠른 EVM 구현입니다. C++로 작성되었으며 이더리움 재단의 Ipsilon 팀이 유지합니다.

**Besu EVM**

Besu는 Consensys가 유지하는 실행 클라이언트입니다. Java로 작성된 완전한 EVM 구현이 있습니다.

**Nethermind EVM**

Nethermind EVM은 C#으로 작성된 실행 클라이언트로 완전한 EVM 구현을 유지합니다.

## 가장 큰 EVM 업그레이드: EVM 객체 형식

*EVM 객체 형식*(EOF)은 2015년 탄생 이후 EVM에 대한 가장 큰 업그레이드입니다. 실제로 주로 가스 계량 측면이나 새로운 옵코드 도입에 초점을 맞춘 과거 EVM에 대한 수정이 있었지만, EVM은 Gavin Wood가 처음 만든 것과 거의 동일합니다.

EVM은 여전히 훌륭합니다. 오늘날 이더리움(및 기타 모든 EVM 호환 블록체인)에서 일어나는 모든 활동은 EVM 덕분에만 가능합니다. 완벽하지도 않으며, 최근 몇 년 동안 스마트 컨트랙트 개발자는 EVM의 다양한 측면을 다루고 제약을 극복하기 위한 몇 가지 트릭을 배워야 했습니다.

EOF는 배포 시 일회성 검증과 함께 EVM을 위한 확장 가능하고 버전화된 컨테이너 형식입니다. 이 섹션에서는 EVM의 모든 주요 제한 사항과 EOF가 이를 어떻게 극복하려고 하는지 살펴볼 것입니다.

> **참고**
>
> 이 책의 최종 수정(2025년 6월) 시점에서 EOF 업그레이드는 이더리움 커뮤니티 내 합의 부족으로 무기한 연기되었습니다. 현재 구현을 위한 명확한 일정이 없으며, 궁극적으로 채택되지 않을 수도 있습니다. 그럼에도 불구하고 이 섹션은 EOF가 EVM과 더 넓은 이더리움 생태계에 어떤 영향을 미칠 수 있는지 이해하는 데 가치가 있다고 생각합니다.

### Jumpdest 분석

레거시 EVM은 생성 시 온체인에 게시된 바이트코드를 검증하지 않습니다. 한편으로 이것은 원하는 컨트랙트를 게시할 수 있기 때문에 좋아 보일 수 있습니다: 존재하지 않는 옵코드가 포함된 바이트코드를 배포하거나 올바르게 실행하기 위해 가져야 하는 다음 즉시 값을 제공하지 않고 `PUSH` 연산 중간에 절단되거나 절대 터치되지 않는 코드를 추가할 수 있습니다. 이것은 실제로 많은 비효율성을 추가합니다. 실제로 EVM은 런타임에 모든 것을 확인해야 하므로 복잡성이 추가되고 전반적인 성능이 느려집니다. 다음은 EVM 바이트코드에 포함된 존재하지 않는 옵코드의 예입니다:

```
600C600052602060000C
```

다음은 사람이 읽을 수 있는 옵코드로 번역된 바이트코드입니다:

```
[00]            PUSH1            0C
[02]            PUSH1            00
[04]            MSTORE
[05]            PUSH1            20
[07]            PUSH1            00
[09]            NOT-EXISTING
```

옵코드 `0C`는 존재하지 않으며, EVM이 그 지점에 도달하면 패닉하고 조기 반환합니다. 이전 바이트코드의 두 번째 바이트도 `0C`이지만 EVM은 거기서 실패하지 않습니다. 차이점은 마지막 `0C` 바이트는 옵코드로 해석되고 유효하지 않으므로 실패하는 반면, 다른 하나는 첫 번째 `PUSH1` 옵코드의 즉시 값이므로 푸시 데이터로 해석된다는 것입니다.

이 런타임 검사의 핵심 부분은 *jumpdest 분석*입니다. 모든 클라이언트는 컨트랙트가 실행될 때마다 런타임에 이를 수행해야 합니다. jumpdest 분석과 레거시 EVM에서 왜 필요한지 이해하는 데 시간을 할애해 봅시다.

> **팁**
>
> 컨트랙트가 호출될 때마다 런타임에 jumpdest 분석을 수행할 필요가 없도록, 일부 이더리움 노드 구현은 모든 컨트랙트에 대해 jumpdest 맵을 저장합니다. 이 맵은 컨트랙트 배포 시 생성되어 노드의 데이터베이스에 저장됩니다.

레거시 EVM은 바이트코드의 제어 흐름을 관리하기 위해 동적 점프(`JUMP` 및 `JUMPI` 옵코드)만 있습니다. 이것은 단 두 개의 옵코드로 연산의 일반적인 흐름을 변경할 수 있기 때문에 매우 편리합니다. 단점은 동적 점프가 매우 비싸고 런타임에 깊은 검증이 필요하다는 것입니다. 대부분의 경우 점프가 동적일 필요가 없음에도 불구하고. 실제로 점프할 값은 종종 `JUMP` 옵코드 직전에 스택에 푸시됩니다. 다음은 간단한 예입니다:

```
…6009566006016101015b6001…
```

사람이 읽을 수 있는 옵코드로 번역:

```
[00]            PUSH1            09
[02]            JUMP
[03]            PUSH1            06
[05]            ADD
[06]            PUSH2            0101
[09]            JUMPDEST
[0a]            PUSH1            01
```

보시다시피 점프 목적지—즉, 점프할 오프셋 `0x09`—는 `JUMP` 옵코드 직전에 `PUSH1` 옵코드를 통해 스택에 푸시됩니다. EVM은 `0x09`를 스택에 푸시한 다음 이전에 푸시된 `0x09`를 입력으로 받아 해당 오프셋의 명령어로 실행을 이동하는 `JUMP` 옵코드를 실행합니다. `0x09`에서 `JUMPDEST` 옵코드가 발견되므로 유효한 점프 목적지로 간주되며 실행이 올바르게 계속될 수 있습니다.

유효하지 않은 목적지로 점프하지 않기 위해 런타임 검증이 필요합니다. 유효한 목적지는 푸시 데이터의 일부가 아닌 `JUMPDEST` 명령어만입니다. 이것은 이해하기 매우 중요합니다: 레거시 EVM은 코드와 데이터 사이에 적절한 분리가 없습니다. 따라서 일부 바이트코드에서 바이트 `0x5b`—`JUMPDEST` 옵코드—를 만나면 컨트랙트 전체를 분석하지 않고는 실제 `JUMPDEST` 옵코드인지 푸시 데이터의 일부인지 완전히 확신할 수 없습니다.

이 미묘한 차이를 보여주는 다음 예를 보세요:

```
…6009566006016101015b6001…
…6009566006016201015b6001…
```

이 두 바이트코드는 거의 동일해 보입니다; 실제로 1비트만 다릅니다. 그러나 그것만으로도 결과에 큰 차이를 만들 수 있습니다. 첫 번째 바이트코드는 이전 예에서 보여준 것과 동일합니다. 두 번째는 사람이 읽을 수 있는 형식으로 다음과 같습니다:

```
[00]            PUSH1            09
[02]            JUMP
[03]            PUSH1            06
[05]            ADD
[06]            PUSH3            01015b
[0a]            PUSH1            01
```

이 두 번째 코드를 실행하려고 하면 유효하지 않은 점프 목적지로 인해 실패합니다. 오프셋 `0x09`에 여전히 `JUMPDEST` 옵코드를 나타내는 `0x5b` 바이트가 있기 때문에 조금 이상해 보일 수 있습니다. 문제는 이 경우 `0x5b` 바이트가 푸시 데이터의 일부이므로 유효한 점프 목적지로 간주될 수 없다는 것입니다. 이것이 실행이 그 지점에서 실패하는 이유입니다.

Jumpdest 분석은 EVM이 컨트랙트를 실행할 때 유효하지 않은 점프 목적지를 감지하고 패닉할 수 있도록 어떤 점프 목적지가 유효하고 어떤 것이 유효하지 않은지 알기 위해 컨트랙트를 분석하는 프로세스입니다.

컨트랙트 A와 상호작용하는 트랜잭션을 보내고 있다고 합시다. EVM이 로드하면 즉시 jumpdest 분석을 수행하여 유효한 점프 목적지의 맵을 저장한 다음 트랜잭션의 실제 실행을 시작합니다:

```
…6009566006016101015b60016015566006016201015b6001…
```

사람이 읽을 수 있는 형식:

```
[00]            PUSH1            09
[02]            JUMP
[03]            PUSH1            06
[05]            ADD
[06]            PUSH2            0101
[09]            JUMPDEST
[0a]            PUSH1            01
[0c]            PUSH1            15
[0e]            JUMP
[0f]            PUSH1            06
[11]            ADD
[12]            PUSH3            01015b
[16]            PUSH1            01
```

EVM은 모든 바이트코드를 훑어보고 각 `0x5b` 바이트가 유효하거나 유효하지 않은 점프 목적지로 표시된 맵을 생성합니다. 그림 14-26에서 볼 수 있습니다.

### 기능 추가 및 폐기

옵코드나 특정 기능을 추가하거나 폐기하는 것은 보기만큼 쉽지 않습니다. `BLOBHASH`, `BLOBBASEFEE`, `BASEFEE` 등과 같은 다양한 옵코드가 추가되었지만, 구조화되지 않고 검증되지 않은 EVM의 바이트코드 때문에 이것은 항상 복잡합니다.

유효하지 않은 옵코드, 구체적으로 `0x0C`가 포함된 다음 예를 보세요. 이것이 이더리움 메인넷에 배포된 실제 컨트랙트라고 가정합니다:

```
600C600052602060000C
```

사람이 읽을 수 있는 형식:

```
[00]            PUSH1            0C
[02]            PUSH1            00
[04]            MSTORE
[05]            PUSH1            20
[07]            PUSH1            00
[09]            NOT-EXISTING
```

EVM 내에서 이 작은 바이트코드를 실행하려고 하면 존재하지 않는 옵코드에 도달했을 때 실패하는 것을 볼 수 있습니다.

미래 업그레이드가 새로운 옵코드인 `MAX` 옵코드를 추가한다고 합시다. 스택에서 두 항목을 가져와 더 큰 값이 포함된 항목을 반환합니다. 할당된 바이트는 `0x0C`입니다. 이전 바이트코드를 다시 고려해 보세요(기억하세요, 메인넷에 배포된 실제 컨트랙트라고 가정합니다):

```
[00]            PUSH1            0C
[02]            PUSH1            00
[04]            MSTORE
[05]            PUSH1            20
[07]            PUSH1            00
[09]            MAX
```

이제 이 바이트코드는 완전히 다른 결과를 가집니다. 실제로 더 이상 실패하지 않고 성공적으로 반환합니다. 이 컨트랙트가 (이전에는) 존재하지 않는 옵코드로 인해 항상 실패한다는 가정에 의존하는 컨트랙트가 있다면 문제가 발생할 수 있습니다.

EVM의 버전화 시스템에 의존할 수 없기 때문에 기능 폐기는 더 어렵습니다. 따라서 옵코드를 제거하거나 작동 방식을 변경하면 이를 사용하던 오래된 컨트랙트가 깨질 수 있으며, 수동 개입(새 컨트랙트 생성) 외에는 이를 수정할 수 있는 것이 없습니다.

[EIP-2929](https://oreil.ly/_9kTv)가 상태 접근 옵코드의 가스 계량을 변경하기 위해 도입되었을 때, 일부 컨트랙트는 사용하거나 예상하는 가스 양을 하드코딩했기 때문에 깨졌습니다. 다시 작동하게 하는 해결책은 트랜잭션에 의해 터치될 것으로 알고 있는 일부 계정과 스토리지 슬롯을 미리 로드하고 가스 비용을 낮출 수 있는 *접근 목록*을 도입하는 것이었습니다.

레거시 EVM의 다른 중요한 측면으로 업그레이드를 더 어렵게 만드는 것은 *코드 내성*과 *가스 관찰 가능성*입니다. 가스 관찰 가능성은 `GAS`와 같은 옵코드 또는 가스를 입력으로 받는 모든 `*CALL` 옵코드 덕분에 가능하며, 코드 내성은 `CODESIZE`, `CODECOPY`, `EXTCODESIZE`, `EXTCODECOPY`, `EXTCODEHASH`와 같은 옵코드 때문에 달성 가능합니다.

문제는 EVM이 실행의 특정 지점에서 남은 가스에 접근할 수 있다면 스마트 컨트랙트의 로직이 이에 의존하게 만들 수 있다는 것입니다. 미래에 일부 옵코드의 가스 계량에 변경이 있다면(이것은 그리 드물지 않게 관찰되는 것입니다), 오래된 가스 계량에 의존하던 모든 스마트 컨트랙트에 문제가 발생할 수 있습니다. 코드 내성에도 동일하게 적용됩니다.

> **참고**
>
> 코드 내성 없이, 미래 버전의 EOF는 기존의 모든 컨트랙트 코드를 동일한 기능을 가진 새 VM의 코드로 자동 변환하여 Cairo VM이나 Wasm 또는 다른 것으로 기본 가상 머신을 완전히 변경할 수 있습니다.

### 코드와 데이터 분리

레거시 EVM은 온체인에 게시되는 바이트코드에 구조를 부과하지 않습니다. 실제 코드와 해당 코드 내에서 사용되는 데이터 사이에 구분이 없습니다. 모든 것은 단지 바이트이며 실행 중 EVM에 의해 단계별로 해석됩니다.

전체 컨트랙트를 보지 않고는 바이트코드의 특정 부분이 코드인지 데이터인지 말할 수 없습니다. 다음 예를 보세요:

```
…730102030405060708090a0b0c0d0e0f101112131431…
[00]            PUSH20    0102030405060708090a0b0c0d0e0f1011121314
[15]            BALANCE
```

코드를 들여다보지 않고는 `0102030405060708090a0b0c0d0e0f1011121314`가 일련의 옵코드—`0x01`: `ADD`, `0x02`: `MUL` 등—로 해석되는 것이 아니라 잔액을 쿼리하려는 고정 주소를 나타내는 푸시 데이터라는 것을 즉시 알 수 없습니다. 이것은 정적 분석 도구와 형식 검증에 좋지 않으며, 스마트 컨트랙트가 온체인에서 직접 실행 가능한 코드를 올바르게 처리하기 더 어렵게 만듭니다.

### 스택 너무 깊음

이제 EVM의 가장 싫어하는 제한 중 하나인 "stack too deep" 오류를 살펴보겠습니다. 다음 스마트 컨트랙트를 컴파일하려고 하면 즉시 발생합니다:

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.27;

contract StackTooDeep {
    function add(
        uint256 a,uint256 b,uint256 c,uint256 d,uint256 e,uint256 f,uint256 g,uint256 h,uint256 i
    ) external pure returns(uint256) {
        return a+b+c+d+e+f+g+h+i;
    }
}
```

컨트랙트를 컴파일하려고 할 때의 출력:

```
solc StackTooDeep.sol --bin
Error: Stack too deep. Try compiling with `--via-ir` (cli) or the equivalent `viaIR: true` (standard JSON) while enabling the optimizer. Otherwise, try removing local variables.
 --> StackTooDeep.sol:8:16:
  |
8 |         return a+b+c+d+e+f+g+h+i;
  |                                ^
```

이 오류는 EVM이 작동하는 방식의 직접적인 결과이기 때문에 매우 미묘합니다. 실제로 스택에 푸시할 수 있는 최대 항목 수는 1,024개이지만, EVM은 `DUP1..16` 및 `SWAP1..16`과 같은 옵코드를 통해 상위 16개 요소에만 쉽게 접근할 수 있습니다.

`StackTooDeep` 예에서 `add` 함수는 9개의 다른 매개변수를 받으며, 각각 스택에 넣어야 합니다. 그런 다음 최종 결과를 얻기 위해 8개의 덧셈을 수행합니다. 문제는 이러한 세부 사항에 있습니다. 최종 연산이 큰 단일 덧셈처럼 보일 수 있지만, 실제로 컴파일러는 각각을 분리하고 스택에 저장해야 하는 중간 결과를 보유하는 임시 변수를 생성해야 합니다. 따라서 9개의 매개변수 + 8개의 중간 결과로 총 17개의 스택 항목이 필요합니다. 컴파일러가 스택에서 17번째 위치 이상에 있는 변수를 참조하려고 하면 쉽게 접근할 수 있는 옵코드가 없기 때문에 실패합니다.

문제를 더 잘 시각화하려면 모든 단계에서 스택 구성을 자세히 보여주는 그림 14-27을 볼 수 있습니다. 실행 끝에서 변수 `i`가 깊이 17에 있음을 쉽게 볼 수 있습니다. 컴파일러는 함수 범위에서 지역 변수나 매개변수에 쉽게 접근할 수 없게 두지 않으므로 "stack too deep" 오류를 발생시킵니다.

![스택 너무 깊음 시각화](../images/ch14/maet_1427.png)

**그림 14-27.** 모든 단계에서의 스택 구성

이것은 스마트 컨트랙트 개발자가 일상 업무 중에 극복해야 하는 문제 중 하나를 보여주는 매우 간단한 예일 뿐입니다. 컴파일러가 이러한 종류의 상황을 자동으로 분석하고 관리하는 데 점점 더 나아지고 있지만, EVM은 현재 작동 방식에 따라 몇 가지 하드 제한을 부과합니다.

### EOF

EOF는 배포 시 검증과 함께 EVM 바이트코드를 위한 컨테이너 형식, 버전화 시스템, 코드와 데이터의 완전한 분리를 도입하여 이러한 모든 문제를 해결합니다. 다음은 EOF 유효 바이트코드의 예입니다:

```
EF00010100040200010008030001003004002000008000045F5FD1005FEC0000EF00010100040200010004030001001404000000008000025F5FEE00EF00010100040200010001040000000080000000000102030405060708090a0b0c0d0e0f10111213141516171819101a1b1c1d1e
```

사람이 읽을 수 있는 형식으로 번역:

```
매직 바이트                      EF00
EOF 버전                         01
스택 검증 데이터                 01 0004
코드 섹션                        02 0001 0008
서브컨테이너 섹션 크기           03 0001 0030
데이터 섹션 크기                 04 0020
헤더 종료자                      00
스택: #ins, #outs, max stack     00 80 0004
코드                             5F5FD1005FEC0000
서브컨테이너                     EF00010100040200010004030001001404000000008000025F5FEE00
                                 EF00010100040200010001040000000080000000
데이터                           000102030405060708090a0b0c0d0e0f10111213141516171819101
                                 a1b1c1d1e
```

잠시만요—다음 섹션에서 모든 것을 설명할 것입니다.

#### 개선 사항

Jumpdest 분석과 모든 가스 및 코드 내성 옵코드는 완전히 제거되고 이제 정의되지 않은 것으로 간주됩니다. 코드 섹션의 모든 옵코드는 유효해야 하고, 즉시 값(푸시 데이터 등)은 코드에 있어야 하며, 도달할 수 없는 명령어가 없어야 합니다. 스택 검증도 생성 시 수행됩니다. 이것은 실행 중 스택 언더플로우와 오버플로우를 불가능하게 만들어, 컨트랙트가 배포 시 검증되었기 때문에 이미 모든 규칙을 준수한다고 EVM이 가정할 수 있어 런타임에 모든 검사를 수행할 필요가 없습니다.

> **팁**
>
> 이러한 검증 보장은 EVM 바이트코드를 머신 네이티브 코드로 AOT 또는 JIT 컴파일하는 실현 가능성을 향상시킵니다.

동적 점프도 제거되고 `PUSH` 옵코드와 유사하게 즉시 값을 받는 세 가지 새로운 옵코드인 `RJUMP`, `RJUMPI`, `RJUMPV`와 함께 정적 상대 점프가 도입됩니다. 더 이상 jumpdest 분석이 없고 모든 것이 런타임 대신 생성 시 확인되기 때문에 EOF에서 즉시 값을 받는 새 명령어를 추가할 수 있다는 점에 주목하세요.

이전 섹션의 EOF 컨테이너에서 볼 수 있듯이, EOF는 *함수*(즉, 코드 섹션)의 개념을 도입하여 각각에 대해 스택을 격리합니다. 레거시 EVM은 동적 점프에 의존하여 이 동작을 모방할 수 있습니다: Solidity 또는 Vyper 함수는 내부 표현일 뿐입니다.

그 이유로 세 개의 옵코드—`CALLF`, `RETF`, `JUMPF`—와 *리턴 스택*(EVM의 일반적인 피연산자 스택과 완전히 분리됨)이 추가됩니다. 특히 리턴 스택은 데이터 손실 없이 호출자에게 돌아갈 수 있도록 함수로 점프하기 전에 실행 정보를 저장하는 데 필요합니다. 그림 14-28은 이것이 어떻게 작동하는지 더 잘 시각화하는 데 도움이 될 수 있습니다.

![리턴 스택이 있는 EOF 함수 호출](../images/ch14/maet_1428.png)

**그림 14-28.** EOF는 함수 또는 코드 섹션의 개념을 도입합니다

"stack too deep" 문제는 세 가지 새로운 옵코드인 `DUPN`, `SWAPN`, `EXCHANGE`의 추가를 통해 해결됩니다. 처음 두 명령어는 이전의 `DUP1..16` 및 `SWAP1..16`과 유사하며, 복제하거나 스왑할 항목의 인덱스를 나타내는 하나의 즉시 값을 받는다는 점만 다릅니다. 해당 인덱스는 이전의 하드 제한인 16보다 훨씬 큰 256까지 갈 수 있습니다.

`EXCHANGE` 옵코드는 스택에서 두 개의 다른 항목을 스왑할 수 있는 새로운 옵코드입니다(`SWAPN`은 항상 n 항목을 첫 번째 항목과 스왑하는 반면, `EXCHANGE`는 임의의 항목을 서로 스왑할 수 있음). 이것은 변수 집합과 사용 분석이 주어지면 스택 트래픽을 최소화하려는 *스택 스케줄링 알고리즘*을 구현하는 컴파일러에 특히 유용합니다.

`CREATE`와 `CREATE2`는 EOF 컨트랙트에서 더 이상 사용되지 않습니다. 대신 새로운 EOF 컨트랙트를 생성하는 방법을 제공하기 위해 `EOFCREATE`와 `RETURNCONTRACT`가 도입됩니다.

마지막으로 새로운 `CALL` 명령어가 이전의 제거된 것들을 대체하기 위해 추가됩니다: `EXTCALL`, `EXTDELEGATECALL`, `EXTSTATICCALL`, `RETURNDATALOAD`. 이들은 가스 한도를 지정하는 것을 허용하지 않으며(가스 관찰 가능성 없음) EVM이 서브콜의 반환 데이터를 저장할 출력 버퍼를 요구하지 않습니다. `RETURNDATALOAD`는 마지막으로 실행된 서브콜의 반환 데이터를 호출자의 스택에 가져오기 위한 특정 이유로 도입되었습니다.

#### EOF 실제 사용

이 섹션의 시작 부분에 표시된 EOF 컨트랙트를 분석해 봅시다:

```
EF00010100040200010008030001003004002000008000045F5FD1005FEC0000EF00010100040200010004030001001404000000008000025F5FEE00EF00010100040200010001040000000080000000000102030405060708090a0b0c0d0e0f10111213141516171819101a1b1c1d1e
```

먼저 EOF 헤더가 있으며, 다음으로 구성됩니다:

```
매직 바이트                    EF00
```

매직 바이트는 EOF 컨트랙트를 레거시 컨트랙트와 구별하는 데 필요합니다(EIP-3541 덕분에 이더리움 메인넷에서 `EF00`으로 시작하는 다른 컨트랙트는 없습니다).

그런 다음 EOF 버전이 있으며, 이는 미래에 EOF 형식에 대한 업그레이드를 우아하게 이끌 수 있습니다:

```
EOF 버전                       01
```

스택 검증 데이터는 항상 식별자 `01`로 시작하고 "Stack" 부분의 크기가 뒤따릅니다. 이 예에서는 4바이트 길이의 "Stack" 섹션이 있습니다:

```
스택 검증 데이터                 01 0004
```

코드 섹션은 식별자 `02`로 시작하고 코드 섹션(일명 함수) 수와 관련 크기가 뒤따릅니다. 여기서는 8바이트 길이의 하나의 코드 섹션이 있습니다:

```
코드 섹션                      02 0001 0008
```

서브컨테이너 섹션 크기는 식별자 `03`으로 시작하고 서브컨테이너 수와 관련 크기가 뒤따릅니다. 여기서는 48바이트 길이(기억하세요, 항상 16진수 형식)의 하나의 서브컨테이너가 있습니다:

```
서브컨테이너 섹션 크기           03 0001 0030
```

데이터 섹션 크기는 식별자 `04`로 시작하고 데이터 섹션의 크기가 뒤따릅니다. 여기서는 데이터 섹션에 32바이트가 있습니다:

```
데이터 섹션 크기                 04 0020
```

마지막으로 항상 EOF 헤더의 끝을 표시하는 헤더 종료자 `00`이 있습니다:

```
헤더 종료자                      00
```

Stack 섹션은 각 코드 섹션(이 예에서는 하나만 있음)에 대한 입력과 출력 수 및 최대 스택 높이를 보여줍니다. 우리는 0개의 입력과 반환하지 않는 함수(`80`은 반환하지 않는 함수를 나타내는 특별한 바이트)가 있으며, 스택의 최대 높이는 4입니다:

```
스택: #ins, #outs, max stack        00 80 0004
```

다음은 EVM에 의해 실행되는 EVM 바이트코드를 포함하는 모든 코드 섹션입니다:

```
코드                            5F5FD1005FEC0000
```

다음 옵코드를 포함하는 하나의 함수(코드 섹션)만 있습니다:

```
PUSH0 PUSH0 DATALOADN 0 PUSH0 EOFCREATE 0 STOP
```

이 코드는 먼저 처음 두 `PUSH0` 옵코드 덕분에 스택에 `0-0`을 푸시합니다. 그런 다음 오프셋 0(코드의 다음 즉시 값)에서 시작하는 데이터 섹션의 32바이트를 읽고 스택에 푸시합니다. 그런 다음 마지막 `PUSH0`을 통해 또 다른 `0`이 푸시됩니다. 마지막으로 즉시 인수로 `0`을 사용하여 `EOFCREATE`가 호출되며, 이는 첫 번째 서브컨테이너의 첫 번째 코드 섹션을 호출합니다:

```
서브컨테이너                     EF00010100040200010004030001001404000000008000025F5FEE00EF0001
                                0100040200010001040000000080000000
```

서브컨테이너 섹션에는 EOF 바이트코드에 포함된 모든 EOF 서브컨테이너가 포함됩니다. 이 예에서는 하나의 서브컨테이너가 있습니다. 서브컨테이너는 EOF 형식의 바이트코드입니다: 아이디어는 다른 EOF 컨테이너 내에 EOF 컨테이너를 중첩할 수 있다는 것입니다. 이것은 팩토리 컨트랙트에 유용합니다.

마지막으로 컨트랙트가 실행에 필요로 하는 모든 데이터를 포함하는 데이터 섹션이 있습니다. 여기서는 32바이트의 데이터가 있습니다:

```
데이터                          000102030405060708090a0b0c0d0e0f10111213141516171819101a1b1c1d1e
```

이 분석은 EOF 바이트코드의 서브컨테이너에 재귀적으로 적용하여 그것이 무엇을 하는지 완전히 이해할 수 있지만, EVM의 래빗홀에 더 깊이 들어가는 것에 관심이 있다면 독자에게 맡깁니다.

## EVM의 미래

EOF 외에 EVM의 미래는 불확실하며 개발자와 다양한 프로젝트에 의해 EVM이 어떻게 사용될지에 따라 달라집니다. 그러나 각 블록에 첨부되어 올바른 실행을 증명하는 영지식 증명을 제공할 *zk-EVM*과 같이 EVM이 확장할 수 있는 몇 가지 흥미로운 영역이 있습니다. 또한 [*EVMMAX*](https://oreil.ly/ioqSx)와 [*SIMD*](https://oreil.ly/7q0Dq)는 EVM에 더 많은 힘을 가져와 많은 암호학적 처리를 훨씬 더 빠르게 수행할 수 있게 하며, 이는 프라이버시 프로토콜이나 L2와 같은 암호학 의존 애플리케이션에 특히 유익할 것입니다.

## 결론

이 장에서는 EVM을 탐구하고 다양한 스마트 컨트랙트의 실행을 추적하며 EVM이 바이트코드를 어떻게 실행하는지 살펴보았습니다. 또한 EVM의 회계 메커니즘인 가스를 살펴보고 정지 문제를 어떻게 해결하고 DoS 공격으로부터 이더리움을 어떻게 보호하는지 보았습니다. 또한 레거시 EVM의 다양한 흐름을 어떻게 수정하려고 하는지 살펴보며 EOF를 분석했습니다.
