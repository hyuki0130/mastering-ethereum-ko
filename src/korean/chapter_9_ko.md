# 9장. 스마트 컨트랙트 보안

보안은 스마트 컨트랙트를 작성할 때 가장 중요한 고려 사항 중 하나입니다. 스마트 컨트랙트 프로그래밍 분야에서 실수는 비용이 많이 들고 쉽게 악용됩니다. 이 장에서는 보안 모범 사례와 디자인 패턴뿐만 아니라 스마트 컨트랙트에 취약점을 도입할 수 있는 관행과 패턴인 *보안 안티패턴*을 살펴보겠습니다.

다른 프로그램과 마찬가지로, 스마트 컨트랙트는 작성된 대로 정확히 실행되며, 이것이 항상 프로그래머가 의도한 것은 아닙니다. 또한 모든 스마트 컨트랙트는 공개되어 있으며, 모든 사용자가 단순히 트랜잭션을 생성하여 상호 작용할 수 있습니다. 모든 취약점은 악용될 수 있으며, 손실은 거의 항상 복구가 불가능합니다. 따라서 모범 사례를 따르고 잘 테스트된 디자인 패턴을 사용하는 것이 중요합니다.

견고한 개발을 보안의 "스위스 치즈 모델"의 첫 번째 레이어로 생각하세요. 각 보호 레이어는 스위스 치즈 조각처럼 작용합니다: 어떤 것도 그 자체로 완벽하지 않지만, 함께하면 더 강력한 방어를 만듭니다. 가장 첫 번째 레이어는 견고한 개발 관행을 따르는 것입니다: 신뢰할 수 있는 디자인 패턴을 사용하고, 명확하고 의도적인 코드를 작성하며, 알려진 함정을 적극적으로 피하는 것입니다. 이 기본 레이어는 취약점으로부터 컨트랙트를 보호하는 가장 좋은 시작점을 제공합니다. 이 외에도 테스트, 코드 리뷰, 버그 바운티와 같은 다른 레이어가 추가 보호를 제공하지만, 모든 것은 우리의 개발 관행에서 시작됩니다.

## 보안 모범 사례

*방어적 프로그래밍*은 스마트 컨트랙트에 특히 적합한 프로그래밍 스타일입니다. 이는 다음을 강조하며, 모두 모범 사례입니다:

**미니멀리즘/단순성**

코드를 작성하기 전에도, 모든 구성 요소가 정말 필요한지 의문을 제기하기 위해 한 발 물러서는 것이 좋습니다. 디자인을 단순화할 수 있을까요? 특정 데이터 구조가 불필요한 공격 표면을 도입하고 있지는 않을까요? 아키텍처가 정해지면, 코드를 비판적인 시각으로 다시 살펴보면서 줄을 줄이거나, 엣지 케이스를 제거하거나, 비필수 기능을 삭제할 기회를 찾아야 합니다. 더 간단한 컨트랙트는 추론, 테스트 및 감사하기가 더 쉽습니다. 그리고 일부 DeFi 프로토콜이 수천 줄로 합법적으로 성장하더라도, 누군가가 코드베이스 크기를 자랑할 때 여전히 회의적일 필요가 있습니다. 더 많은 코드는 종종 더 많은 가치가 아니라 더 많은 버그를 의미합니다.

**코드 재사용**

바퀴를 다시 발명하지 마세요. 필요한 것의 대부분을 수행하는 라이브러리나 컨트랙트가 이미 존재한다면 재사용하세요. 예를 들어 [OpenZeppelin](https://www.openzeppelin.com)은 널리 채택되고, 철저히 테스트되며, 커뮤니티에 의해 지속적으로 검토되는 컨트랙트 모음을 제공합니다. 자신의 코드 내에서도 DRY 원칙을 따르세요: 반복하지 마세요. 코드 조각이 한 번 이상 반복되는 것을 보면, 함수나 라이브러리로 작성하고 재사용할 수 있는지 자문해 보세요. 많은 배포에 걸쳐 실전 테스트를 거친 코드는 아무리 자신감이 있더라도 방금 작성한 것보다 거의 항상 더 안전합니다. 처음부터 빌드하여 기능이나 구성 요소를 "개선"하고 싶은 유혹이 드는 "여기서 발명되지 않음" 증후군을 조심하세요. 보안 위험은 종종 개선 가치보다 큽니다. 재사용은 게으름이 아닙니다. 그것은 스마트하고 방어적인 엔지니어링입니다.

**코드 품질**

스마트 컨트랙트 코드는 용서가 없습니다. 모든 버그는 금전적 손실로 이어질 수 있습니다. 스마트 컨트랙트 프로그래밍을 일반적인 범용 프로그래밍과 같은 방식으로 다루어서는 안 됩니다. Solidity로 DApp을 작성하는 것은 JavaScript로 웹 위젯을 만드는 것과 같지 않습니다. 오히려, 항공우주 공학이나 마찬가지로 용서 없는 분야에서와 같이 엄격한 엔지니어링 및 소프트웨어 개발 방법론을 적용해야 합니다. 일단 코드를 "출시"하면 문제를 해결하기 위해 할 수 있는 일이 거의 없습니다. 그리고 코드가 업그레이드 가능하더라도, 무언가 잘못되면 대응할 시간이 거의 없습니다. 누군가가 여러분보다 먼저 프로젝트에서 버그를 발견하면, 익스플로잇은 단일 트랜잭션 또는 몇 개의 트랜잭션에서 펼쳐질 것이며, 이는 여러분이 개입하기 훨씬 전에 몇 초 내에 피해가 발생한다는 것을 의미합니다.

**가독성/감사 가능성**

코드는 명확하고 이해하기 쉬워야 합니다. 읽기 쉬울수록 감사하기도 쉽습니다. 스마트 컨트랙트는 공개되어 있습니다: 누구나 바이트코드를 읽을 수 있고, 충분한 기술이 있는 사람이라면 리버스 엔지니어링할 수 있습니다. 따라서 개발자 커뮤니티의 집단 지혜를 활용하고 오픈 소스 개발의 가장 높은 공통 분모의 혜택을 받기 위해 협업적이고 오픈 소스 방법론을 사용하여 공개적으로 작업을 개발하는 것이 유익합니다. 이더리움 커뮤니티의 일부인 스타일과 명명 규칙을 따르면서 잘 문서화되고 읽기 쉬운 코드를 작성해야 합니다.

**테스트 커버리지**

가능한 모든 것을 테스트하세요. 스마트 컨트랙트는 누구나 원하는 입력으로 실행할 수 있는 공개 실행 환경에서 실행됩니다. 함수 인자와 같은 입력이 잘 형성되어 있거나 적절하게 제한되어 있거나 양성 목적을 가지고 있다고 가정해서는 안 됩니다. 모든 인자가 예상 범위 내에 있고 코드 실행을 계속하기 전에 적절하게 형식화되어 있는지 확인하기 위해 모든 인자를 테스트하세요.

## 보안 위험 및 안티패턴

스마트 컨트랙트 프로그래머로서, 가장 일반적인 보안 위험에 익숙해야 하며, 컨트랙트가 이러한 위험에 노출되는 프로그래밍 패턴을 감지하고 피할 수 있어야 합니다. 다음 여러 섹션에서는 다양한 보안 위험, 취약점이 어떻게 발생할 수 있는지에 대한 예시, 그리고 이를 해결하기 위해 사용할 수 있는 대응책 또는 예방 솔루션을 살펴보겠습니다.

다음 안티패턴들은 Web2 보안에서와 마찬가지로 익스플로잇을 실행하기 위해 종종 결합됩니다. 실제 익스플로잇은 일반적으로 이 장의 예시보다 더 복잡합니다.

### 재진입(Reentrancy)

이더리움 스마트 컨트랙트의 기능 중 하나는 다른 외부 컨트랙트의 코드를 호출하고 활용할 수 있는 능력입니다. 컨트랙트는 또한 일반적으로 이더를 처리하므로 종종 다양한 외부 사용자 주소로 이더를 보냅니다. 이러한 작업은 컨트랙트가 외부 호출을 제출해야 합니다. 이러한 외부 호출은 공격자에 의해 하이재킹될 수 있으며, 공격자는 컨트랙트가 콜백(폴백 함수 또는 일부 훅, 일반적으로 `transfer`)을 통해 자신에게 다시 호출하는 것을 포함하여 추가 코드를 실행하도록 강제할 수 있습니다. 이러한 종류의 공격은 2016년의 악명 높고 여전히 기억되는 DAO 해킹에서 사용되었습니다. 이 모든 년이 지난 후에도, 이 취약점을 악용하는 [많은 공격을 여전히 보고 있으며](https://oreil.ly/87VUR), 발견하기가 꽤 간단하고 수정하는 데 비용이 적게 듭니다.

#### 취약점

이러한 유형의 공격은 공격자가 다른 컨트랙트의 실행 중에 해당 컨트랙트가 상태를 업데이트하기 전에 제어권을 가져갈 때 발생합니다. 컨트랙트가 여전히 프로세스 중간에 있기 때문에 아직 상태(예: 중요한 변수)를 업데이트하지 않았습니다. 그런 다음 공격자는 이 취약한 순간에 컨트랙트에 "재진입"하여 의도되거나 예상되지 않은 동작을 트리거하기 위해 일관성 없는 상태를 이용할 수 있습니다. 이 재진입을 통해 공격자는 보호 장치를 우회하고, 데이터를 조작하거나, 자금을 빼낼 수 있으며, 이 모든 것은 컨트랙트가 아직 안전하고 일관된 상태로 완전히 정착되지 않았기 때문입니다.

재진입은 실제 예시 없이는 이해하기 어려울 수 있습니다. 예제 9-1의 간단한 취약한 컨트랙트를 살펴보세요. 이 컨트랙트는 예금자가 일주일에 1 이더만 인출할 수 있도록 하는 이더리움 금고 역할을 합니다.

**예제 9-1. EtherStore: 재진입에 취약한 컨트랙트**

```solidity
1 contract EtherStore {
2      uint256 public withdrawalLimit = 1 ether;
3      mapping(address => uint256) public lastWithdrawTime;
4    mapping(address => uint256) balances;
5
6    function depositFunds() public payable{
7      balances[msg.sender] += msg.value;
8    }
9
10    function withdrawFunds() public {
11        require(block.timestamp >= lastWithdrawTime[msg.sender] + 1 weeks);
12        uint256 _amt = balances[msg.sender];
13        if(_amt > withdrawalLimit){
14            _amt = withdrawalLimit;
15        }
16      (bool res, ) = address(msg.sender).call{value: _amt}("");
17        require(res, "Transfer failed");
18      balances[msg.sender] = 0;
19        lastWithdrawTime[msg.sender] = block.timestamp;
20    }
21 }
```

이 컨트랙트에는 `depositFunds`와 `withdrawFunds`라는 두 개의 퍼블릭 함수가 있습니다. `depositFunds` 함수는 단순히 발신자의 잔액을 증가시킵니다. `withdrawFunds` 함수는 발신자가 잔액을 인출할 수 있게 합니다. 이 함수는 지난 주에 인출이 발생하지 않은 경우에만 성공하도록 의도되었습니다.

취약점은 17줄에 있으며, 여기서 컨트랙트가 사용자에게 요청한 이더 금액을 보냅니다. 예제 9-2에서 컨트랙트를 생성한 공격자를 고려해 보세요.

**예제 9-2. Attack.sol: EtherStore 컨트랙트의 재진입 취약점을 악용하는 데 사용되는 컨트랙트**

```solidity
1 contract Attack {
2  EtherStore public etherStore;
3
4  // etherStore 변수를 컨트랙트 주소로 초기화
5  constructor(address _etherStoreAddress) {
6      etherStore = EtherStore(_etherStoreAddress);
7  }
8
9  function attackEtherStore() public payable {
10      // 가장 가까운 이더로 공격
11      require(msg.value >= 1 ether, "no bal");
12      // depositFunds() 함수에 eth 전송
13      etherStore.depositFunds{value: 1 ether}();
14      // 마법 시작
15      etherStore.withdrawFunds();
16  }
17
18  function collectEther() public {
19      payable(msg.sender).transfer(address(this).balance);
20  }
21
22  // receive 함수 - fallback() 함수도 작동했을 것입니다
23  receive() external payable {
24      if (address(etherStore).balance >= 1 ether) {
25          // 피해자 컨트랙트에 대한 재진입 호출
26          etherStore.withdrawFunds();
27      }
28  }
29 }
```

익스플로잇이 어떻게 발생할 수 있을까요? 먼저, 공격자는 `EtherStore`의 컨트랙트 주소를 유일한 생성자 매개변수로 사용하여 악성 컨트랙트(예를 들어 주소 `0x0...123`)를 생성합니다. 이렇게 하면 퍼블릭 변수 `etherStore`를 공격할 컨트랙트로 초기화하고 가리킵니다.

그런 다음 공격자는 1보다 크거나 같은 이더 금액으로 `attackEtherStore` 함수를 호출합니다—당분간 1 이더라고 가정하겠습니다. 이 예시에서, 다른 여러 사용자가 이 컨트랙트에 이더를 입금했으므로 현재 잔액이 10 이더라고 가정하겠습니다. 그러면 다음이 발생합니다:

- *Attack.sol*, 13줄: `EtherStore` 컨트랙트의 `depositFunds` 함수가 `1 ether`의 `msg.value`(와 많은 가스)로 호출됩니다. 발신자(`msg.sender`)는 악성 컨트랙트(`0x0..123`)가 됩니다. 따라서, `balances[0x0..123] = 1 ether`.
- *Attack.sol*, 15줄: 악성 컨트랙트는 그 다음 `EtherStore` 컨트랙트의 `withdrawFunds` 함수를 호출합니다. 이전에 인출이 없었으므로 요구 사항(EtherStore 컨트랙트의 11줄)을 통과합니다.
- *EtherStore.sol*, 16줄: 컨트랙트는 악성 컨트랙트에 `1 ether`를 다시 보냅니다.
- *Attack.sol*, 23줄: 악성 컨트랙트에 대한 지불이 `receive` 함수를 실행합니다.
- *Attack.sol*, 24줄: `EtherStore` 컨트랙트의 총 잔액이 10 이더였고 이제 9 이더이므로 이 `if` 문이 통과합니다.
- *Attack.sol*, 26줄: 폴백 함수는 `EtherStore` `withdrawFunds` 함수를 다시 호출하고 `EtherStore` 컨트랙트에 *재진입*합니다.
- *EtherStore.sol*, 10줄: `withdrawFunds`에 대한 이 두 번째 호출에서, 18줄이 아직 실행되지 않았으므로 공격 컨트랙트의 잔액은 여전히 1 이더입니다. 따라서, 여전히 `balances[0x0..123] = 1 ether`입니다. `lastWithdrawTime` 변수도 마찬가지입니다. 다시, 요구 사항을 통과합니다.
- *EtherStore.sol*, 16줄: 공격 컨트랙트가 또 다른 `1 ether`를 인출합니다.
- *Attack.sol*의 24줄에 명시된 대로 `EtherStore.balance >= 1`이 더 이상 아닐 때까지 EtherStore 컨트랙트에 재진입합니다.
- *Attack.sol*, 24줄: `EtherStore` 컨트랙트에 1 이더 미만이 남으면 이 `if` 문이 실패합니다. 그러면 `EtherStore` 컨트랙트의 17-19줄이 실행됩니다(`withdrawFunds` 함수에 대한 각 호출에 대해).
- *EtherStore.sol*, 18줄과 19줄: `balances`와 `lastWithdrawTime` 매핑이 설정되고 실행이 종료됩니다.

최종 결과는 공격자가 단일 트랜잭션에서 `EtherStore` 컨트랙트의 모든 이더를 인출했다는 것입니다.

폴백 함수에 의해 가로채어지는 네이티브 이더 전송은 재진입 공격의 일반적인 벡터이지만, 이 위험을 도입할 수 있는 유일한 메커니즘은 아닙니다. ERC-721 및 ERC-777과 같은 여러 토큰 표준에는 재진입 공격을 가능하게 할 수 있는 콜백 메커니즘이 포함되어 있습니다. 예를 들어, ERC-721의 `safeTransfer` 함수는 컨트랙트에 대한 토큰 전송이 수신자의 `onERC721Received` 함수를 호출하도록 보장합니다. 마찬가지로, ERC-777 토큰은 전송 중에 `tokensReceived` 함수를 통해 훅이 호출되도록 허용합니다.

#### 클래식 재진입 패턴을 넘어서

재진입 공격은 단일 함수나 컨트랙트에 국한되지 않습니다. 클래식 재진입은 함수가 완료되기 전에 동일한 함수에 재진입하는 것을 포함하지만, 교차 함수 재진입, 교차 컨트랙트 재진입, 그리고 가장 까다로운 읽기 전용 재진입과 같이 발견하기 어려운 변형이 있습니다.

읽기 전용 재진입은 다른 컨트랙트의 뷰 함수에 의존하는 컨트랙트를 이용합니다. 이러한 함수는 상태를 수정하지 않지만 다른 컨트랙트가 의존하는 데이터를 반환하며, 종종 재진입 보호가 없습니다. 문제는 재진입 호출이 공격자가 대상 컨트랙트를 일시적으로 일관성 없는 상태에 두고, 다른 컨트랙트(피해자)를 사용하여 뷰 함수를 통해 이 불안정한 상태를 쿼리할 수 있게 할 때 발생합니다.

어떻게 진행되는지 살펴보겠습니다:
1. 공격자의 컨트랙트는 재진입할 수 있는 취약한 컨트랙트—컨트랙트 A라고 부르겠습니다—와 상호 작용합니다. 이 컨트랙트는 다른 프로토콜이 의존하는 데이터를 보유합니다.
2. 컨트랙트 A는 공격자의 컨트랙트에 콜백을 트리거하여 공격자의 컨트랙트 로직이 실행되도록 합니다.
3. 폴백에 있는 동안, 공격자의 컨트랙트는 컨트랙트 A에 연결되어 있고 제공하는 데이터에 의존하는 다른 프로토콜인 컨트랙트 B를 호출합니다.
4. 컨트랙트 B는 어떤 문제도 인식하지 못하고 컨트랙트 A에서 데이터를 읽습니다. 그러나 컨트랙트 A의 상태는 아직 업데이트를 완료하지 않았기 때문에 오래되었습니다.

이 사이클이 끝날 때까지, 공격자는 이미 컨트랙트 A의 오래된 데이터를 활용하여 컨트랙트 B를 악용했고, 그런 다음 컨트랙트 A의 콜백과 원래 호출이 정상적으로 완료되도록 합니다. 이 프로세스는 그림 9-1에 설명되어 있습니다.

![읽기 전용 재진입](../images/ch9/maet_0901.png)

**그림 9-1.** 읽기 전용 재진입

여기서 핵심은 컨트랙트 B가 컨트랙트 A의 데이터를 신뢰하지만, 컨트랙트 A의 상태가 따라잡지 못해 공격자가 지연을 악용할 수 있다는 것입니다. 이러한 유형의 공격은 개발자가 상태를 수정하지 않기 때문에 안전하다고 생각하여 뷰 함수를 재진입 잠금으로 보호하지 않는 경우가 많아 방어하기가 더 어렵습니다.

읽기 전용 재진입은 읽기 전용 함수도 외부 컨트랙트에 의해 의존될 때 위험할 수 있다는 것을 가르쳐줍니다.

#### 예방 기법

재진입 문제를 방지하기 위해 따라야 할 첫 번째 모범 사례는 스마트 컨트랙트를 작성할 때 검사-효과-상호작용 패턴을 고수하는 것입니다. 이 패턴은 외부 컨트랙트와 상호 작용하기 전에 상태 변수에 대한 모든 변경이 발생하도록 보장하는 것입니다. 예를 들어, *EtherStore.sol* 컨트랙트에서 상태 변수를 수정하는 줄은 모든 외부 호출 전에 나타나야 합니다. 목표는 외부 주소와 상호 작용하는 모든 코드 조각이 함수에서 실행되는 마지막 것이 되도록 보장하는 것입니다. 이것은 필요한 업데이트가 이미 이루어졌기 때문에 재진입 시 외부 컨트랙트가 내부 상태를 방해하는 것을 방지합니다.

또 다른 유용한 기법은 재진입 잠금을 적용하는 것입니다. *재진입 잠금*은 함수를 실행하는 동안 컨트랙트를 "잠그는" 간단한 상태 변수로, 다른 외부 호출이 중단되는 것을 방지합니다. 이것은 다음과 같은 모디파이어로 구현할 수 있습니다:

```solidity
contract EtherStore {
    bool lock;
      uint256 public withdrawalLimit = 1 ether;
      mapping(address => uint256) public lastWithdrawTime;
    mapping(address => uint256) balances;

      modifier nonReentrant {
      require(!lock, "Can't reenter");
      lock = true;
      _;
      lock = false;
    }

    function withdrawFunds() public nonReentrant{
        [...]
    }
}
```

이 예시에서 `nonReentrant` 모디파이어는 lock 변수를 사용하여 `withdrawFunds` 함수가 아직 실행 중인 동안 재진입되는 것을 방지합니다. `nonReentrant` 모디파이어는 시작할 때 컨트랙트를 잠그고 함수가 완료되면 잠금을 해제합니다. 그러나 바퀴를 다시 발명해서는 안 됩니다. 우리만의 재진입 잠금을 만드는 대신, OpenZeppelin의 ReentrancyGuard와 같이 잘 테스트된 라이브러리에 의존하는 것이 좋습니다. 이러한 라이브러리는 안전하고 가스 최적화된 솔루션을 제공합니다.

> **참고**
>
> 이더리움에서 Solidity 0.8.24의 임시 저장소(transient storage)의 출현으로, OpenZeppelin은 크게 낮은 가스 비용을 위해 임시 저장소를 활용하는 ReentrancyGuard의 새로운 변형인 ReentrancyGuardTransient를 도입했습니다. [EIP-1153](https://oreil.ly/fRvKl)에 의해 활성화된 임시 저장소는 단일 트랜잭션 기간 동안만 필요한 데이터를 저장하는 더 저렴한 방법을 제공하여 재진입 가드 및 유사한 임시 로직에 이상적입니다. 그러나 ReentrancyGuardTransient는 EIP-1153이 사용 가능한 체인에서만 사용할 수 있으므로 구현하기 전에 대상 체인이 이 기능을 지원하는지 확인하세요.

한 가지 더 접근 방식은 이더를 보내기 위해 Solidity의 내장 `transfer` 및 `send` 함수를 사용하는 것입니다. 이러한 함수는 제한된 양의 가스(2,300 유닛)만 전달하며, 이는 일반적으로 수신 컨트랙트가 재진입 호출을 실행하기에 충분하지 않으므로 재진입에 대한 간단한 보호 방법입니다. 그러나 주목할 만한 단점이 있습니다. 수신자가 폴백 또는 receive 함수에 비악성 로직이 있는 스마트 컨트랙트인 경우, 전송이 실패하여 잠재적으로 자금이 잠길 수 있습니다. 이 위험은 EOA가 폴백 로직을 포함한 첨부된 코드를 가질 수 있게 하는 EIP-7702의 도입으로 더욱 관련성이 높아지고 있습니다. 더 많은 EOA가 이 기능을 채택함에 따라, `transfer` 또는 `send`를 사용하는 트랜잭션은 가스 부족으로 인해 트랜잭션의 정상적인 실행 중에 되돌려질 가능성이 더 높습니다. 그리고 보안 관점에서, 이 접근 방식은 미래에 대비한 것이 아닙니다: 향후 하드 포크가 특정 작업의 가스 비용을 줄이면, 2,300 유닛이 재진입하기에 충분해질 수 있어 이전에 안전했던 가정을 깨뜨릴 수 있습니다. 따라서 `transfer`와 `send`는 좁은 경우에 여전히 도움이 될 수 있지만, 주의해서 사용해야 하며 주요 방어 수단으로 의존해서는 안 됩니다.

읽기 전용 및 교차 컨트랙트 재진입은 특별한 주의가 필요합니다: 이러한 익스플로잇은 두 개의 별도 프로토콜을 포함할 수 있어 조정된 예방이 도전이 될 수 있기 때문에 까다로울 수 있습니다. 프로젝트가 데이터를 위해 외부 프로토콜에 의존할 때, 결합된 로직이 어떻게 작동하는지 깊이 파고들어야 합니다. 각 프로젝트가 자체적으로 안전하더라도, 통합 중에 취약점이 나타날 수 있습니다.

#### 실제 사례: The DAO 공격

재진입은 2016년에 발생한 DAO 공격에서 주요 역할을 했으며, 이더리움의 초기 개발 동안 주요 해킹 중 하나였습니다. 당시 컨트랙트는 이더 순환 공급량의 15%인 1억 5천만 달러 이상을 보유하고 있었습니다. 해킹의 영향을 되돌리기 위해, 이더리움 커뮤니티는 궁극적으로 이더리움 블록체인을 분리하는 하드 포크를 선택했습니다. 그 결과, 이더리움 클래식(ETC)은 원래 체인으로 계속되었고, 해킹을 되돌리기 위한 업데이트된 규칙이 있는 포크된 버전이 오늘날 우리가 알고 있는 이더리움이 되었습니다.

#### 실제 사례: Libertify

재진입이 유일한 공격 벡터인 최근 익스플로잇은 2023년 7월 Libertify 사례로, 40만 달러가 침해된 DeFi 프로토콜입니다. 악용된 함수의 코드를 확인하고 어떻게 발생했는지 살펴보겠습니다:

```solidity
function _deposit(
    uint256 assets,
    address receiver,
    bytes calldata data,
    uint256 nav
) private returns (uint256 shares) {
        /*
        유효성 검사
    */
    uint256 returnAmount = 0;
    uint256 swapAmount = 0;
    if (BASIS_POINT_MAX > invariant) {
        swapAmount = assetsToToken1(assets);
        returnAmount = userSwap( // 외부 호출
            data,
            address(this),
            swapAmount,
            address(asset),
            address(other)
        );
    }
    uint256 supply = totalSupply(); // 상태 업데이트
    if (0 < supply) {
        uint256 valueToken0 = getValueInNumeraire(
            asset,
            assets - swapAmount,
            MathUpgradeable.Rounding.Down
        );
        uint256 valueToken1 = getValueInNumeraire(
            other,
            returnAmount,
            MathUpgradeable.Rounding.Down
        );
        shares = supply.mulDiv(
            valueToken0 + valueToken1,
            nav,
            MathUpgradeable.Rounding.Down
        );
    } else {
        shares = INITIAL_SHARE;
    }
    uint256 feeAmount = shares.mulDiv(
        entryFee, BASIS_POINT_MAX, MathUpgradeable.Rounding.Down
    );
    _mint(receiver, shares - feeAmount);
    _mint(owner(), feeAmount);
}
```

이것은 재진입 문제의 전형적인 예입니다—요즘에는 이렇게 직접적인 것을 자주 볼 수 없습니다! 여기서 핵심 문제는 재진입 보호의 부재였습니다. `userSwap()` 함수는 공격자가 원래 호출이 `totalSupply`를 업데이트하기 전에 `deposit()` 함수에 재진입할 수 있게 했습니다. 이것은 공격자가 실제로 빚진 것보다 더 많은 주식을 발행하여 이익을 위해 컨트랙트를 악용할 수 있게 했습니다.

### DELEGATECALL

`CALL`과 `DELEGATECALL` 옵코드는 이더리움 개발자가 코드를 모듈화할 수 있게 하는 데 유용합니다. 컨트랙트에 대한 표준 외부 메시지 호출은 *호출된* 컨트랙트의 컨텍스트에서 코드를 실행하는 `CALL` 옵코드에 의해 처리됩니다. 반면, `DELEGATECALL`은 *호출하는* 컨트랙트의 컨텍스트에서 다른 컨트랙트의 코드를 실행합니다. 이것은 저장소, `msg.sender`, `msg.value`가 모두 변경되지 않음을 의미합니다. `DELEGATECALL`을 이해하는 데 도움이 되는 방법은 호출하는 컨트랙트가 호출된 컨트랙트의 바이트코드를 일시적으로 빌려와 마치 자신의 것처럼 실행하는 것입니다. 이것은 프록시 컨트랙트 및 라이브러리와 같은 강력한 패턴을 가능하게 하며, 여기서 재사용 가능한 로직을 한 번 배포하고 많은 컨트랙트에서 재사용합니다. 이 두 옵코드 간의 차이점은 간단하고 직관적이지만, `DELEGATECALL`의 사용은 특히 저장소 레이아웃과 관련하여 미묘하고 예상치 못한 동작으로 이어질 수 있습니다. 더 읽으려면 Loi.Luu의 [이 주제에 대한 Ethereum Stack Exchange 질문](https://oreil.ly/GJOUl)과 [Solidity 문서](https://oreil.ly/gA7vg)를 참조하세요.

#### 취약점

`DELEGATECALL`의 컨텍스트 보존 특성의 결과로, 취약점 없는 커스텀 라이브러리를 구축하는 것은 생각만큼 쉽지 않습니다. 라이브러리 자체의 코드는 안전하고 취약점이 없을 수 있지만, 다른 애플리케이션의 컨텍스트에서 실행될 때 새로운 취약점이 발생할 수 있습니다. 피보나치 수를 사용하여 이것의 상당히 복잡한 예를 살펴보겠습니다. 예제 9-3의 라이브러리를 고려해 보세요. 이 라이브러리는 피보나치 수열과 유사한 형태의 수열을 생성할 수 있습니다. (참고: 이 코드는 [*https://oreil.ly/EHjOb*](https://oreil.ly/EHjOb)에서 수정되었습니다.)

**예제 9-3. FibonacciLib: 커스텀 라이브러리의 결함 있는 구현**

```solidity
1 // library contract - 피보나치 같은 수를 계산
2 contract FibonacciLib {
3     // 표준 피보나치 수열 초기화
4     uint256 public start;
5     uint256 public calculatedFibNumber;
6
7     // 수열의 0번째 숫자 수정
8     function setStart(uint256 _start) public {
9         start = _start;
10     }
11
12     function setFibonacci(uint256 n) public {
13         calculatedFibNumber = fibonacci(n);
14     }
15
16     function fibonacci(uint256 n) internal view returns (uint) {
17         if (n == 0) return start;
18         else if (n == 1) return start + 1;
19         else return fibonacci(n - 1) + fibonacci(n - 2);
20     }
21 }
```

이 라이브러리는 수열에서 *n*번째 피보나치 수를 생성할 수 있는 함수를 제공합니다. 사용자가 수열의 시작 숫자(`start`)를 변경하고 이 새로운 수열에서 *n*번째 피보나치 같은 수를 계산할 수 있게 합니다.

이제 이 라이브러리를 활용하는 컨트랙트를 고려해 보겠습니다:

```solidity
contract FibonacciBalance {
    address public fibonacciLibrary;
    // 인출할 현재 피보나치 수
    uint256 public calculatedFibNumber;
    // 시작 피보나치 수열 숫자
    uint256 public start = 3;
    uint256 public withdrawalCounter;
    // 피보나치 함수 셀렉터
    bytes4 constant fibSig = bytes4(keccak256("setFibonacci(uint256)"));
    // 생성자 - 이더로 컨트랙트 로드
    constructor(address _fibonacciLibrary) payable {
        fibonacciLibrary = _fibonacciLibrary;
    }
    function withdraw() public {
        withdrawalCounter += 1;
        // 현재 인출 사용자에 대한 피보나치 수 계산-
        // 이것은 calculatedFibNumber를 설정
        (bool success, ) = fibonacciLibrary.delegatecall(
            abi.encodeWithSelector(fibSig, withdrawalCounter)
        );
        require(success, "Delegatecall failed");
        payable(msg.sender).transfer(calculatedFibNumber * 1 ether);
    }
    // 사용자가 피보나치 라이브러리 함수를 호출할 수 있도록 허용
    fallback() external {
        (bool success, ) = fibonacciLibrary.delegatecall(msg.data);
        require(success, "Delegatecall failed");
    }
}
```

이 컨트랙트는 참가자가 컨트랙트에서 이더를 인출할 수 있게 하며, 이더의 양은 참가자의 인출 순서에 해당하는 피보나치 수와 같습니다—즉, 첫 번째 참가자는 1 이더를 받고, 두 번째도 1, 세 번째는 2, 네 번째는 3, 다섯 번째는 5 등등(컨트랙트의 잔액이 인출되는 피보나치 수보다 적을 때까지).

이 컨트랙트에서 몇 가지 설명이 필요할 수 있는 요소가 있습니다. 첫째, 흥미롭게 생긴 변수가 있습니다: `fibSig`. 이것은 문자열 `"setFibonacci(uint256)"`의 Keccak-256 해시의 처음 4바이트를 보유합니다. 이것은 [*함수 셀렉터*](https://oreil.ly/u9uaH)로 알려져 있으며 스마트 컨트랙트의 어떤 함수가 호출될지 지정하기 위해 calldata에 넣습니다. 21줄의 `delegatecall` 함수에서 `fibonacci(uint256)` 함수를 실행하려는 것을 지정하는 데 사용됩니다. `delegatecall`의 두 번째 인자는 함수에 전달하는 매개변수입니다. 둘째, FibonacciLib 라이브러리의 주소가 생성자에서 올바르게 참조된다고 가정합니다.

이 컨트랙트에서 오류를 발견할 수 있나요? 이 컨트랙트를 배포하고 이더로 채운 다음 `withdraw`를 호출하면, 아마 되돌려질 것입니다.

라이브러리와 메인 호출 컨트랙트 모두에서 상태 변수 `start`가 사용된다는 것을 알아차렸을 수 있습니다. 라이브러리 컨트랙트에서 `start`는 피보나치 수열의 시작을 지정하는 데 사용되며 `0`으로 설정되어 있고, 호출 컨트랙트에서는 `3`으로 설정되어 있습니다. `FibonacciBalance` 컨트랙트의 폴백 함수가 라이브러리 컨트랙트의 `setStart` 함수를 포함한 모든 호출을 라이브러리 컨트랙트로 전달할 수 있게 한다는 것도 알아차렸을 수 있습니다. 컨트랙트의 상태를 보존한다는 것을 상기하면, 이 함수가 로컬 `FibonacciBalance` 컨트랙트에서 `start` 변수의 상태를 변경할 수 있게 할 것처럼 보일 수 있습니다. 그렇다면, 결과 `calculatedFibNumber`가 `start` 변수에 의존하므로(라이브러리 컨트랙트에서 볼 수 있듯이) 더 많은 이더를 인출할 수 있을 것입니다. 실제로, `setStart` 함수는 `FibonacciBalance` 컨트랙트에서 `start` 변수를 수정하지 않습니다(그리고 할 수 없습니다). 이 컨트랙트의 근본적인 취약점은 단순히 `start` 변수를 수정하는 것보다 훨씬 더 나쁩니다.

실제 문제를 논의하기 전에, 상태 변수가 실제로 컨트랙트에 어떻게 저장되는지 빠르게 살펴보겠습니다. *상태* 또는 *저장소 변수*(개별 트랜잭션에 걸쳐 지속되는 변수)는 컨트랙트에 도입될 때 순차적으로 *슬롯*에 배치됩니다. (여기에 몇 가지 복잡성이 있으니 더 철저한 이해를 위해 [Solidity 문서](https://oreil.ly/LzV7L)를 참조하세요.)

예를 들어, 라이브러리 컨트랙트를 살펴보겠습니다. 두 개의 상태 변수가 있습니다: `start`와 `calculatedFibNumber`. 첫 번째 변수 `start`는 컨트랙트의 저장소 `slot[0]`(즉, 첫 번째 슬롯)에 저장됩니다. 두 번째 변수 `calculatedFibNumber`는 다음 사용 가능한 저장소 슬롯인 `slot[1]`에 배치됩니다. `setStart` 함수는 입력을 받아 `start`를 입력이 무엇이든 설정합니다. 따라서 이 함수는 `setStart` 함수에서 제공하는 입력이 무엇이든 `slot[0]`을 설정합니다. 마찬가지로, `setFibonacci` 함수는 `calculatedFibNumber`를 `fibonacci(n)`의 결과로 설정합니다. 다시 말해, 이것은 단순히 저장소 `slot[1]`을 `fibonacci(n)`의 값으로 설정하는 것입니다.

이제 `FibonacciBalance` 컨트랙트를 살펴보겠습니다. 저장소 `slot[0]`은 이제 `fibonacciLibrary` 주소에 해당하고, `slot[1]`은 `calculatedFibNumber`에 해당합니다. 취약점이 발생하는 것은 이 잘못된 매핑 때문입니다: `delegatecall`은 *컨트랙트 컨텍스트를 보존합니다*. 이것은 `delegatecall`을 통해 실행되는 코드가 호출하는 컨트랙트의 상태(즉, 저장소)에 작용한다는 것을 의미합니다.

이제 21줄의 `withdraw`에서 `fibonacciLibrary.delegatecall(fibSig,withdrawalCounter)`를 실행한다는 것에 주목하세요. 이것은 논의한 대로 저장소 `slot[1]`을 수정하는 `setFibonacci` 함수를 호출하며, 우리의 현재 컨텍스트에서 이것은 `calculatedFibNumber`입니다. 이것은 예상대로입니다(즉, 실행 후 `calculatedFibNumber`가 수정됩니다). 그러나 `FibonacciLib` 컨트랙트의 `start` 변수가 저장소 `slot[0]`에 위치해 있다는 것을 상기하세요. 현재 컨트랙트에서 이것은 `fibonacciLibrary` 주소입니다. 이것은 `fibonacci` 함수가 예상치 못한 결과를 줄 것임을 의미합니다. 이것은 `start`(`slot[0]`)를 참조하기 때문이며, 현재 호출 컨텍스트에서 이것은 `fibonacciLibrary` 주소입니다(`uint`로 해석될 때 상당히 클 것입니다). 따라서 `calculatedFibNumber`가 반환할 `uint(fibonacciLibrary)` 양의 이더를 포함하지 않을 것이므로 `withdraw` 함수가 되돌려질 가능성이 높습니다.

더 나쁜 것은, `FibonacciBalance` 컨트랙트가 27줄의 폴백 함수를 통해 사용자가 모든 `fibonacciLibrary` 함수를 호출할 수 있게 한다는 것입니다. 앞서 논의한 대로, 여기에는 `setStart` 함수가 포함됩니다. 이 함수가 누구나 저장소 `slot[0]`을 수정하거나 설정할 수 있게 한다고 논의했습니다. 이 경우, 저장소 `slot[0]`은 `fibonacciLibrary` 주소입니다. 따라서 공격자는 악성 컨트랙트를 생성하고, 주소를 `uint256`으로 변환하고(Python에서 `int('<address>',16)`을 사용하여 쉽게 할 수 있음), 그런 다음 `setStart(<attack_contract_address_as_uint>)`를 호출할 수 있습니다. 이것은 `fibonacciLibrary`를 공격 컨트랙트의 주소로 변경합니다. 그런 다음, 사용자가 `withdraw` 또는 폴백 함수를 호출할 때마다, 악성 컨트랙트가 실행됩니다(컨트랙트의 전체 잔액을 훔칠 수 있음). 왜냐하면 `fibonacciLibrary`의 실제 주소를 수정했기 때문입니다. 이러한 공격 컨트랙트의 예는 다음과 같습니다:

```solidity
contract Attack {
    uint256 private storageSlot0; // fibonacciLibrary에 해당
    uint256 private storageSlot1; // calculatedFibNumber에 해당
    // 폴백 - 지정된 함수를 찾을 수 없으면 실행
    fallback() external {
        storageSlot1 = 0; // calculatedFibNumber를 0으로 설정하여 withdraw가
        // 호출되어도 이더를 보내지 않음
        payable(<attacker_address>).transfer(this.balance); // 모든 이더를 가져감
    }
}
```

이 공격 컨트랙트가 저장소 `slot[1]`을 변경하여 `calculatedFibNumber`를 수정한다는 것에 주목하세요. 원칙적으로, 공격자는 이 컨트랙트에 대한 모든 종류의 공격을 수행하기 위해 선택한 다른 저장소 슬롯을 수정할 수 있습니다. 이러한 컨트랙트를 [Remix](https://remix.ethereum.org)에 넣고 이러한 `delegatecall` 함수를 통해 다양한 공격 컨트랙트와 상태 변경을 실험해 보시기 바랍니다.

또한 `delegatecall`이 상태 보존적이라고 말할 때, 컨트랙트의 변수 이름이 아니라 해당 이름이 가리키는 실제 저장소 슬롯에 대해 이야기하고 있다는 것을 인식하는 것이 중요합니다. 이 예에서 볼 수 있듯이, 간단한 실수가 공격자가 전체 컨트랙트와 이더를 하이재킹하는 것으로 이어질 수 있습니다.

#### 예방 기법

Solidity는 라이브러리 컨트랙트를 구현하기 위한 `library` 키워드를 제공합니다(자세한 내용은 [문서](https://oreil.ly/K7kF1) 참조). 이것은 라이브러리 컨트랙트가 무상태이고 자체 파괴 불가능하도록 보장합니다. 라이브러리를 무상태로 강제하면 이 섹션에서 시연한 저장소 컨텍스트의 복잡성이 완화됩니다. 무상태 라이브러리는 또한 공격자가 라이브러리의 코드에 의존하는 컨트랙트에 영향을 미치기 위해 라이브러리의 상태를 직접 수정하는 공격을 방지합니다. 일반적인 경험 법칙으로, `DELEGATECALL`을 사용할 때, 라이브러리 컨트랙트와 호출 컨트랙트 모두의 가능한 호출 컨텍스트에 주의를 기울이고, 가능하면 무상태 라이브러리를 구축하세요.

#### 실제 사례: Parity 멀티시그 지갑 (두 번째 해킹)

두 번째 Parity 멀티시그 지갑 해킹은 잘 작성된 라이브러리 코드가 의도된 컨텍스트 외부에서 실행될 때 어떻게 악용될 수 있는지의 예입니다. ["Parity Multisig Hacked. Again"](https://oreil.ly/OLt5Q)과 같은 이 해킹에 대한 많은 좋은 설명이 있습니다. 이러한 참조에 추가하여, 악용된 컨트랙트를 탐색해 보겠습니다.

익스플로잇이 7년 전이므로, 다음 코드 스니펫은 최근 Solidity 버전의 문법을 반영하도록 업데이트되어 읽고 이해하기 쉬워졌습니다.

라이브러리 컨트랙트는 다음과 같습니다:

```solidity
1 contract WalletLibrary is WalletEvents {
2
3   ...
4
5   // 컨트랙트가 아직 초기화되지 않으면 throw.
6   modifier only_uninitialized { if (m_numOwners > 0) revert(); _; }
7
8   // 생성자 - 소유자 배열을 multiowned에 전달하고
9   // 제한을 daylimit에 전달
10   function initWallet(address[] memory _owners, uint256 _required, uint256
11        _daylimit) public only_uninitialized {
12     initDaylimit(_daylimit);
13     initMultiowned(_owners, _required);
14   }
15
16   // 모든 것을 `_to`로 보내면서 컨트랙트 종료.
17   function kill(address _to) onlymanyowners(keccak256(msg.data)) external {
18     selfdestruct(_to);
19   }
20
21   ...
22
23 }
```

그리고 지갑 컨트랙트입니다:

```solidity
1 contract Wallet is WalletEvents {
2
3   ...
4
5   // 메서드
6
7   // 다른 함수가 일치하지 않으면 호출됨
8   fallback() external payable {
9     // 현금이 전송되었나?
10     if (msg.value > 0)
11       Deposit(msg.sender, msg.value);
12     else if (msg.data.length > 0)
13       _walletLibrary.delegatecall(msg.data);
14   }
15
16   ...
17
18   // 필드
19   address constant _walletLibrary =
20     0xcafecafecafecafecafecafecafecafecafecafe;
21 }
```

`Wallet` 컨트랙트가 본질적으로 델리게이트 호출을 통해 모든 호출을 `WalletLibrary` 컨트랙트로 전달한다는 것에 주목하세요. 이 코드 스니펫의 상수 `_walletLibrary` 주소는 실제로 배포된 `WalletLibrary` 컨트랙트(`0x863DF6BFa4469f3ead0bE8f9F2AAE51c91A907b4`에 있었음)의 플레이스홀더 역할을 합니다.

이러한 컨트랙트의 의도된 작동은 코드베이스와 주요 기능이 `WalletLibrary` 컨트랙트에 있는 간단하고 저비용의 배포 가능한 `Wallet` 컨트랙트를 갖는 것이었습니다. 불행히도, `WalletLibrary` 컨트랙트 자체가 컨트랙트이며 자체 상태를 유지합니다. 이것이 왜 문제가 될 수 있는지 알 수 있나요?

`WalletLibrary` 컨트랙트 자체에 호출을 보낼 수 있습니다. 특히, `WalletLibrary` 컨트랙트는 초기화되어 소유될 수 있습니다. 실제로, 한 사용자가 `WalletLibrary` 컨트랙트에서 `initWallet` 함수를 호출하여 라이브러리 컨트랙트의 소유자가 되었습니다. 같은 사용자가 이후 `kill` 함수를 호출했습니다. 사용자가 라이브러리 컨트랙트의 소유자였기 때문에 모디파이어가 통과했고, 라이브러리 컨트랙트가 자체 파괴되었습니다. 존재하는 모든 `Wallet` 컨트랙트가 이 라이브러리 컨트랙트를 참조하고 이 참조를 변경할 방법이 없기 때문에, 이더를 인출하는 능력을 포함한 모든 기능이 `WalletLibrary` 컨트랙트와 함께 손실되었습니다. 결과적으로, 이 유형의 모든 Parity 멀티시그 지갑의 모든 이더가 즉시 손실되거나 영구적으로 복구 불가능해졌습니다.

### 엔트로피 환상

이더리움 블록체인의 모든 트랜잭션은 *결정론적 상태 전환* 작업입니다. 이것은 모든 트랜잭션이 불확실성 없이 계산 가능한 방식으로 이더리움 생태계의 전역 상태를 수정한다는 것을 의미합니다. 이것은 이더리움에 엔트로피나 무작위성의 소스가 없다는 근본적인 함의를 가집니다. 초기에는 분산된 방식으로 무작위성을 만드는 것이 큰 도전이었습니다. 그러나 수년에 걸쳐 이 문제를 해결하기 위한 몇 가지 견고한 솔루션을 개발했습니다.

#### 취약점

개발자가 이더리움에서 스마트 컨트랙트를 구축할 때, 게임, 복권 또는 예측 불가능성이 필요한 기타 기능을 위해 무작위성 소스가 종종 필요합니다. 도전은 블록체인인 이더리움이 본질적으로 결정론적이라는 것입니다: 모든 노드는 합의를 유지하기 위해 동일한 결과에 도달해야 합니다. 따라서 진정한 무작위성을 도입하려면 약간의 창의성이 필요합니다.

많은 개발자가 의존한 한 가지 접근 방식은 블록 변수(블록 해시, 타임스탬프 또는 블록 번호 등)를 무작위 수를 생성하기 위한 시드로 사용하는 것입니다. 이러한 값은 무작위로 보일 수 있지만, 실제로는 현재 블록을 제안하는 검증자에 의해 제어됩니다. 예를 들어, 게임의 결과가 다음 블록 해시가 짝수로 끝나는지에 기반하는 DApp을 상상해 보세요. 검증자는 프로세스를 조작할 수 있습니다: 블록을 제안하려고 하는데 해시가 원하는 결과에 맞지 않으면, 예를 들어 블록 해시를 유리한 방식으로 변경하기 위해 트랜잭션 순서를 변경할 수 있습니다.

검증자 조작이 블록 변수에서 무작위성을 도출할 때의 유일한 위험은 아닙니다. 다른 스마트 컨트랙트는 이러한 블록 변수의 값을 알고 있어, 결과가 유리할 때만 취약한 컨트랙트와 상호 작용할 수 있습니다.

#### 예방 기법

과거와 비교하여, 이더리움 개발자는 이제 무작위성을 생성하기 위한 신뢰할 수 있는 방법을 가지고 있습니다: `PREVRANDAO`와 *검증 가능한 무작위 함수*(VRF).

VRF는 생성된 무작위성이 공정하고 편향되지 않았음을 보장하는 암호화 증명입니다. VRF는 Chainlink와 같은 여러 제공업체에서 지원됩니다. VRF는 공정성을 검증하는 증명과 함께 무작위 수를 생성합니다. 이 증명은 누구나 검증할 수 있어 무작위성이 안전함을 보장합니다. VRF는 스마트 컨트랙트에서 무작위성을 안전하게 얻기 위한 표준 분산 솔루션이 되었습니다.

또 다른 견고한 옵션은 PoS로의 전환과 함께 이더리움에 도입된 `PREVRANDAO` 옵코드입니다. 이 옵코드는 PoS 블록 생성의 필수 구성 요소인 Randao 프로세스에서 유래한 `PREVRANDAO` 값을 얻는 데 사용됩니다. 본질적으로, Randao는 검증자들이 각각 데이터 조각을 기여하여 무작위성을 생성하는 집단적 노력입니다. `PREVRANDAO`는 이전 블록에서 이 프로세스의 결과이며, 신뢰할 수 있는 무작위성 소스 역할을 합니다. `PREVRANDAO` 값을 조작하려면 상당한 수의 검증자를 손상시켜야 하므로 이러한 악용이 비실용적이고 경제적으로 불가능하기 때문에 신뢰할 수 있습니다. 개발자는 컨트랙트에서 이 값을 사용할 수 있지만, `PREVRANDAO`가 이미 알려진 이전 블록의 값을 나타낸다는 점을 명심해야 합니다. 커밋 시점에 이 값이 예측 가능하지 않도록 하려면 스마트 컨트랙트가 대신 미래 블록의 `PREVRANDAO` 값에 커밋해야 합니다. 이렇게 하면 커밋이 이루어질 때 값을 알 수 없습니다.

> **경고**
>
> Randao는 공격자가 에포크의 마지막 슬롯에 할당된 제안자들의 제어권을 얻으면 조작될 수 있습니다. `PREVRANDAO`가 스마트 컨트랙트에서 무작위성을 생성하는 데 신뢰할 수 있는 선택인지 결정하려면 조작의 비용과 이점을 신중하게 따져봐야 합니다. Randao를 조작하는 것은 비용이 많이 들 수 있지만, 컨트랙트에 귀중한 자산이 포함된 경우 대신 분산 오라클 솔루션을 사용하는 것이 더 안전합니다.

`PREVRANDAO`와 VRF와 같은 솔루션이 널리 문서화되고 접근 가능해지면서, 요즘에는 개발자가 무작위성 소스로 안전하지 않은 블록 변수를 사용하는 것을 보기 드뭅니다. 그러나 지름길을 택하거나 개발자가 이러한 도구를 인식하지 못할 때 실수가 여전히 발생합니다.

#### 실제 사례: Fomo3D

Fomo3D는 플레이어가 타이머를 연장하기 위해 "키"를 구매하고, 타이머가 0이 될 때 마지막 구매자가 되어 상금 풀을 얻기 위해 경쟁하는 이더리움 복권 게임이었습니다. 다음 코드에서 볼 수 있듯이 열악한 무작위성이 있는 에어드롭 기능이 포함되어 있었습니다:

```solidity
function airdrop()
        private
        view
        returns(bool)
    {
        uint256 seed = uint256(keccak256(abi.encodePacked(

            (block.timestamp).add
            (block.difficulty).add
            ((uint256(keccak256(abi.encodePacked
            (block.coinbase)))) / (block.timestamp)).add
            (block.gaslimit).add
            ((uint256(keccak256(abi.encodePacked
            (msg.sender)))) / (block.timestamp)).add
            (block.number)
        )));
        if((seed - ((seed / 1000) * 1000)) < airDropTracker_) {
            return(true);
        } else {
            return(false);
        }
    }
```

악성 컨트랙트는 시드를 계산하는 데 사용되는 값을 미리 알 수 있어, 승리로 이어질 때만 `airdrop` 함수를 트리거할 수 있습니다. 컨트랙트가 악용된 것은 놀라운 일이 아닙니다.

### 확인되지 않은 CALL 반환 값

Solidity에서 외부 호출을 수행하는 방법은 여러 가지가 있습니다. 외부 계정으로 이더를 보내는 것은 일반적으로 `transfer` 메서드를 통해 수행됩니다. 그러나 `send` 함수도 사용할 수 있으며, 더 다양한 외부 호출을 위해 `CALL` 옵코드를 Solidity에서 직접 사용할 수 있습니다. `call`과 `send` 함수는 호출이 성공했는지 실패했는지를 나타내는 Boolean을 반환합니다. 따라서 이러한 함수에는 간단한 주의 사항이 있습니다: `call` 또는 `send`에 의해 초기화된 외부 호출이 실패하더라도 이러한 함수를 실행하는 트랜잭션은 되돌려지지 않습니다; 함수는 단순히 `false`를 반환합니다. 일반적인 오류는 개발자가 외부 호출이 실패하면 되돌리기가 발생할 것으로 예상하고 반환 값을 확인하지 않는 것입니다.

#### 취약점

예제 9-4의 컨트랙트를 고려해 보세요.

**예제 9-4. 취약한 Lotto 컨트랙트**

```solidity
1 contract Lotto {
2
3     bool public payedOut;
4     address public winner;
5     uint256 public winAmount;
6
7     // ... 추가 기능 여기에
8
9     function sendToWinner() public {
10         require(!payedOut);
11         payable(winner).send(winAmount);
12         payedOut = true;
13     }
14
15     function withdrawLeftOver() public {
16         require(payedOut);
17         payable(msg.sender).send(address(this).balance);
18     }
19 }
```

이것은 `winner`가 `winAmount`의 이더를 받는 Lotto와 같은 컨트랙트를 나타내며, 일반적으로 누구나 인출할 수 있도록 약간의 잔액이 남습니다. 취약점은 11줄에 있으며, 여기서 `send`가 응답을 확인하지 않고 사용됩니다. 이 사소한 예에서, 트랜잭션이 실패한 `winner`(가스가 부족하거나 폴백 함수에서 의도적으로 throw하는 컨트랙트에 의해)는 이더가 전송되었는지 여부와 관계없이 `payedOut`이 `true`로 설정되도록 허용합니다. 이 경우, 누구나 `withdrawLeftOver` 함수를 통해 `winner`의 상금을 인출할 수 있습니다.

#### 예방 기법

첫 번째 방어선은 항상 예외 없이 `send` 함수와 저수준 호출의 반환 값을 확인하는 것입니다. 오늘날 모든 정적 분석 도구가 이 문제를 표시하므로 간과하기 어렵습니다.

이더를 보낼 때, 어떤 방법을 사용할지 신중하게 고려해야 합니다. 실패 시 트랜잭션이 자동으로 되돌려지길 원한다면, `transfer`가 기본적으로 실패를 처리하므로 매력적으로 보일 수 있습니다. 그러나 `send`와 `transfer` 모두 2,300 가스 유닛만 전달하므로, 수신자(컨트랙트든, 이제 EIP-7702로 인해 EOA든)에 폴백 로직이 있으면 쉽게 실패할 수 있습니다. 이러한 진화하는 상황을 고려할 때, 더 안전하고 유연한 접근 방식은 대신 `call`을 사용하고, 반환 값을 명시적으로 확인하며, 그에 따라 오류를 관리하는 것입니다. 이것은 가스 전달에 대한 완전한 제어를 제공하고 컨트랙트가 더 넓은 범위의 수신자와 호환되도록 유지합니다.

#### 실제 사례: Etherpot과 King of the Ether

[Etherpot](https://oreil.ly/_-iC-)은 예제 9-4의 컨트랙트와 크게 다르지 않은 스마트 컨트랙트 복권이었습니다. 이 컨트랙트의 몰락은 주로 블록 해시의 잘못된 사용 때문이었습니다(마지막 256개의 블록 해시만 사용 가능합니다; "사전 정의된 전역 변수 및 함수" 참조). 그러나 이 컨트랙트도 확인되지 않은 `call` 값 문제를 겪었습니다.

예제 9-5의 `cash` 함수를 고려해 보세요: 다시 말해, 다음 코드 스니펫은 최근 Solidity 버전의 문법을 반영하도록 업데이트되었습니다.

**예제 9-5. Lotto.sol: 코드 스니펫**

```solidity
1 function cash(uint256 roundIndex, uint256 subpotIndex) public {
2    uint256 subpotsCount = getSubpotsCount(roundIndex);
3    if(subpotIndex>=subpotsCount)
4        return;
5    uint256 decisionBlockNumber = getDecisionBlockNumber(roundIndex,subpotIndex);
6    if(decisionBlockNumber>block.number)
7        return;
8    if(rounds[roundIndex].isCashed[subpotIndex])
9        return;
10    //서브팟은 한 번만 현금화할 수 있습니다. 이중 지불을 방지하기 위함입니다
11    address winner = calculateWinner(roundIndex,subpotIndex);
12    uint256 subpot = getSubpot(roundIndex);
13    payable(winner).send(subpot);
14    rounds[roundIndex].isCashed[subpotIndex] = true;
15    //라운드를 현금화된 것으로 표시
16 }
```

13줄에서 `send` 함수의 반환 값이 확인되지 않고, 다음 줄에서 승자에게 자금이 전송되었음을 나타내는 Boolean이 설정됩니다. 이 버그는 승자가 이더를 받지 못했지만 컨트랙트의 상태는 승자가 이미 지불받았다고 나타내는 상태를 허용할 수 있습니다.

이 버그의 더 심각한 버전이 [King of the Ether](https://oreil.ly/4zLMH) 컨트랙트에서 발생했습니다. 확인되지 않은 실패한 `send`가 컨트랙트를 공격하는 데 어떻게 사용될 수 있는지를 자세히 설명하는 훌륭한 [사후 분석](https://oreil.ly/U8ckx)이 작성되었습니다.

#### ERC-20 케이스

Solidity에서 ERC-20 토큰을 다룰 때, 토큰 전송의 반환 값을 단순히 확인하는 것만으로는 안전한 상호 작용을 보장하기에 충분하지 않습니다. 이것은 모든 ERC-20 토큰이 ERC-20 표준을 엄격하게 따르지 않기 때문이며, 특히 오래된 토큰이 그렇습니다. 일부 토큰은 작업이 실패할 때 직접 되돌리거나 예외를 던지는 대신 전송이 완료되면 Boolean 값을 반환합니다. 다른 토큰은 전혀 값을 반환하지 않아 표준 메서드를 사용하여 상호 작용할 때 모호한 동작으로 이어질 수 있습니다. Tether(USDT)는 ERC-20 표준을 완전히 준수하지 않는 널리 사용되는 토큰의 대표적인 예입니다.

이를 완화하기 위해, OpenZeppelin의 SafeERC20과 같은 라이브러리를 사용합니다. 이 라이브러리는 표준 ERC-20 작업(`transfer`, `transferFrom`, `approve` 등)을 이러한 변형을 우아하게 처리하는 방식으로 래핑합니다. 토큰이 `false`를 반환하면 라이브러리는 트랜잭션이 되돌려지도록 보장하고, 토큰이 값을 반환하지 않으면 라이브러리는 되돌리기가 발생하지 않았다면 작업이 성공했다고 가정합니다.

### 경쟁 조건과 프론트 러닝

이 취약점을 정말로 이해하려면, 이더리움에서 트랜잭션이 어떻게 작동하는지 간략히 다시 살펴보겠습니다. 트랜잭션을 보내면, 노드 네트워크에 브로드캐스트되고 대기 중인 트랜잭션을 위한 대기실인 멤풀에 배치됩니다. 그런 다음 검증자가 멤풀에서 이러한 트랜잭션을 가져와 블록을 구축합니다. 블록 내의 트랜잭션은 특정 순서로 순차적으로 실행되며, 각 트랜잭션이 블록체인의 전역 상태를 변경하기 때문에 트랜잭션의 결과는 블록 내 위치에 따라 달라질 수 있습니다. 이 트랜잭션 순서는 트랜잭션 실행 결과에 상당한 영향을 미칠 수 있으므로 중요합니다.

> **참고**
>
> 실제로 블록 내 트랜잭션의 위치를 제어하는 것은 대부분 지불에 달려 있습니다. 원래는 더 높은 가스 가격을 제공함으로써 순서에 영향을 줄 수 있었습니다. 오늘날, Flashbots 인프라가 빌더-제안자 분리(아직 이더리움에 기본적으로 포함되지 않음)를 구현함으로써, 사용자는 특정 순서로 트랜잭션 번들을 제출하고 오프체인 릴레이 시스템을 통해 포함을 입찰할 수 있습니다. 이러한 프로세스—레거시 멤풀 기반 시스템과 새로운 빌더 기반 시스템 모두—는 6장에서 더 자세히 다룹니다.

#### 취약점

*프론트 러닝*은 블록에 다른 트랜잭션을 삽입하여 프론트 러너에게 이익이 되는 방식으로 이 순차적 실행을 악용하는 관행입니다. 본질적으로, 누군가가 시장이나 특정 컨트랙트에 영향을 줄 수 있는 대기 중인 트랜잭션을 감시한 다음 원본보다 먼저 처리되도록 자신의 트랜잭션을 제출합니다. 그렇게 함으로써 대기 중인 트랜잭션의 정보를 활용하여 이익을 얻을 수 있으며, 종종 원래 발신자에게 피해를 줍니다. 우리 코드가 이러한 역학을 고려하고 블록 내 트랜잭션 순서 변경에 대해 탄력적으로 설계되는 것이 중요합니다.

간단한 예로 이것이 어떻게 작동하는지 살펴보겠습니다. 예제 9-6에 표시된 컨트랙트를 고려해 보세요.

**예제 9-6. FindThisHash: 프론트 러닝에 취약한 컨트랙트**

```solidity
contract FindThisHash {
    bytes32 constant public hash =
      0xb5b5b97fafd9855eec9b41f74dfb6c38f5951141f9a3ecd7f44d5479b630ee0a;
    constructor() payable {} // 이더로 로드
    function solve(string memory solution) public {
        // 해시의 사전 이미지를 찾을 수 있다면 1000 이더를 받습니다
        require(hash == keccak256(abi.encodePacked(solution)));
        payable(msg.sender).transfer(1000 ether);
    }
}
```

이 컨트랙트가 1,000 이더를 가지고 있다고 가정해 보세요. SHA-3 해시 `0xb5b5b97fafd9855eec9b41f74dfb6c38f5951141f9a3ecd7f44d5479b630ee0a`의 사전 이미지를 찾을 수 있는 사용자는 솔루션을 제출하고 1,000 이더를 검색할 수 있습니다. 한 사용자가 솔루션이 `Ethereum!`이라는 것을 알아냈다고 가정해 보겠습니다. 그들은 `Ethereum!`을 매개변수로 사용하여 `solve`를 호출합니다. 불행히도, 공격자가 멤풀에서 트랜잭션을 발견하고 유효성을 확인한 후 블록에서 더 높은 우선순위로 동등한 트랜잭션을 제출했습니다. 공격자의 트랜잭션이 먼저 처리되므로 원래 트랜잭션은 되돌려집니다.

#### 예방 기법

프론트 러닝 취약점은 종종 스마트 컨트랙트나 프로토콜의 특정 로직에 따라 다양한 형태로 나타날 수 있습니다. 트랜잭션 순서를 통해 작업이 악용될 수 있을 때마다 프론트 러닝 취약점이 있습니다. 따라서 솔루션은 일반적으로 특정 문제에 맞춤화됩니다. 예를 들어, 자동화된 시장 메이커(AMM) 프로토콜은 사용자가 스왑 중에 받아야 하는 최소 토큰 수를 설정할 수 있게 하여 이 문제를 해결합니다. 이것은 프론트 러닝을 완전히 방지하지는 않지만 공격자가 추출할 수 있는 잠재적 이익을 심각하게 제한하여 피해를 줄이고 극단적인 슬리피지로부터 사용자를 보호합니다.

또 다른 일반적인 기술은 커밋-공개 스킴의 사용입니다. 이 접근 방식에서 사용자는 먼저 숨겨진 정보를 포함하는 트랜잭션을 제출합니다. 일반적으로 해시로 표현됩니다(커밋 단계). 이 트랜잭션이 블록에 포함되면 사용자는 실제 데이터를 공개하는 두 번째 트랜잭션을 보냅니다(공개 단계). 이 방법은 공격자가 너무 늦어서 행동할 때까지 초기 트랜잭션의 세부 정보를 볼 수 없으므로 프론트 러닝을 효과적으로 방지합니다. 그러나 트레이드오프는 두 개의 별도 트랜잭션이 필요하다는 것이며, 이는 더 높은 비용과 추가된 지연을 의미합니다. 더 나쁜 사용자 경험 외에도, 트랜잭션 사이의 필요한 지연은 시간에 민감한 애플리케이션에서 실질적인 제한이 될 수 있습니다.

#### 실제 사례: AMM과 minAmountOut

일반적인 실제 프론트 러닝 취약점을 살펴보겠습니다. 이것은 AMM 프로토콜을 통합하는 스마트 컨트랙트가 받을 최소 토큰 수를 설정하지 않고 스왑을 수행할 때 발생하며, 해당 스왑이 프론트 러닝 공격에 취약해집니다. 받을 최소 토큰 수가 제대로 설정되지 않거나(또는 너무 낮게 남겨지면), 스왑 트랜잭션은 샌드위치 공격이라는 특정 유형의 프론트 러닝에 취약해집니다.

샌드위치 공격이 어떻게 전개되는지 살펴보겠습니다: 프론트 러너가 멤풀에서 대기 중인 트랜잭션을 모니터링하고 최소 출력 금액을 강제하지 않는 우리의 스왑 트랜잭션을 발견합니다. 공격자는 토큰 가격을 인위적으로 부풀리기 위해 우리의 스왑 직전에 구매 트랜잭션을 제출합니다. 그런 다음 우리의 트랜잭션이 이 부풀려진 가격으로 진행되어 예상했던 것보다 적은 토큰을 받게 됩니다. 게다가 우리의 트랜잭션이 가격을 더 부풀립니다. 그 직후, 공격자는 이 더 높은 가격에 토큰을 팔아 가격을 다시 낮추고 우리의 트랜잭션으로 인해 생긴 가격 차이로 이익을 얻습니다. 이 전략은 그들의 두 거래 사이에 우리의 트랜잭션을 "샌드위치"하므로 *샌드위치 공격*이라는 이름이 붙었습니다. 이 문제를 해결하려면, AMM을 통합하는 스마트 컨트랙트가 오라클(시간 가중 평균 가격 기반도 가능)과 같은 신뢰할 수 있는 소스에서 실제 자산 가격을 가져온 다음 스왑을 수행할 때 정확한 최소 출력 금액을 계산하고 강제해야 합니다.

### 서비스 거부(Denial of Service)

이 범주는 매우 광범위하지만 근본적으로 사용자가 일정 기간 동안 또는 경우에 따라 영구적으로 컨트랙트나 그 일부를 작동 불능하게 만들 수 있는 공격으로 구성됩니다. 이것은 "실제 사례: Parity 멀티시그 지갑 (두 번째 해킹)"에서 설명된 것처럼 이러한 컨트랙트에 자금을 영원히 가둘 수 있습니다.

#### 취약점

컨트랙트가 작동 불능해질 수 있는 다양한 방법이 있습니다. 여기서는 DoS 취약점으로 이어질 수 있는 덜 명백한 Solidity 코딩 패턴 몇 가지를 강조합니다.

#### 외부에서 조작 가능한 매핑이나 배열을 통한 루핑

이 패턴은 일반적으로 소유자가 예제 9-7의 컨트랙트처럼 `distribute`와 같은 함수로 투자자에게 토큰을 배포하려고 할 때 나타납니다.

**예제 9-7. DistributeTokens 컨트랙트**

```solidity
1 contract DistributeTokens {
2     address public owner; // 어딘가에서 설정됨
3     address[] investors; // 투자자 배열
4     uint[] investorTokens; // 각 투자자가 받는 토큰 양
5
6     // ... 추가 기능, transfertoken() 포함
7
8     function invest() public payable {
9         investors.push(msg.sender);
10         investorTokens.push(msg.value * 5); // 보낸 wei의 5배
11         }
12
13     function distribute() public {
14         require(msg.sender == owner); // 소유자만
15         for(uint256 i = 0; i < investors.length; i++) {
16             // 여기서 transferToken(to,amount)는 "amount"의
17             // 토큰을 주소 "to"로 전송합니다
18             transferToken(investors[i],investorTokens[i]);
19         }
20     }
21 }
```

이 컨트랙트의 루프는 인위적으로 부풀릴 수 있는 배열을 순회한다는 것에 주목하세요. 공격자는 많은 사용자 계정을 생성하여 `investors` 배열을 매우 크게 만들 수 있습니다. 위험은 루프 자체만이 아니라 `transferToken`이나 다른 로직과 같은 내부 작업의 누적 가스 비용입니다. 각 추가 반복은 사용되는 총 가스에 추가되며, 배열이 충분히 커지면 루프를 완료하는 데 필요한 가스가 블록 가스 제한을 초과할 수 있습니다. 그 시점에서 `distribute` 함수는 사실상 사용할 수 없게 됩니다.

> **참고**
>
> 이러한 종류의 DoS는 상태 변경 함수에만 국한되지 않습니다. 읽기 전용 view 함수도 큰 배열을 순회하면 접근할 수 없게 될 수 있습니다. 호출 시 온체인에서 가스를 소비하지 않지만, RPC 엔드포인트는 `eth_call` 실행에 자체적인 임의의 가스 상한을 적용합니다. 따라서 view 함수가 그 제한을 초과할 만큼 충분한 로직을 실행하면 RPC 호출이 실패합니다.

#### 외부 호출에 기반한 상태 진행

컨트랙트는 때때로 새로운 상태로 진행하려면 이더를 주소로 보내거나 외부 소스의 입력을 기다려야 하도록 작성됩니다. 이러한 패턴은 외부 호출이 실패하거나 외부적인 이유로 방해받을 때 DoS로 이어질 수 있습니다. 이더를 보내는 예에서, 사용자는 이더를 받지 않는 컨트랙트를 생성할 수 있습니다. 컨트랙트가 새로운 상태로 진행하기 위해 이더를 보내야 한다면, 이더를 받지 않는 사용자의 컨트랙트로 이더를 보낼 수 없으므로 컨트랙트는 절대로 새로운 상태를 달성하지 못할 것입니다.

#### 예상치 못한 문제들

DoS 문제는 예상치 못한 방식으로 나타날 수 있으며, 항상 악의적인 공격을 수반하지는 않습니다. 때로는 예상치 못한 사건으로 인해 컨트랙트의 기능이 중단될 수 있습니다. 예를 들어, 스마트 컨트랙트가 특정 권한 있는 함수를 호출하기 위해 소유자의 개인 키에 의존하고 그 키가 분실되거나 손상되면 문제가 생깁니다. 그 키 없이는 그러한 중요한 함수에 영구적으로 접근할 수 없게 되어 전체 컨트랙트의 운영이 중단될 수 있습니다. 소유자가 판매를 완료하기 위해 함수를 호출해야 하는 초기 코인 공개(ICO) 컨트랙트를 상상해 보세요. 키가 분실되면 아무도 호출할 수 없고 토큰은 영원히 잠긴 상태로 남습니다.

예상치 못한 중단의 또 다른 예는 컨트랙트의 지식이나 의도 없이 이더가 전송되는 것입니다. 이더는 `selfdestruct`(현재 더 이상 사용되지 않음)라는 방법을 사용하거나 컨트랙트가 미리 결정된 주소에 배포되기 전에 이더를 보내는 것으로도 컨트랙트에 "강제"될 수 있습니다. 컨트랙트가 자체 함수를 통해 받는 모든 이더의 회계를 제어한다고 가정하면, 이러한 초대받지 않은 자금을 어떻게 처리해야 할지 모를 수 있어 의도하지 않은 동작으로 이어질 수 있습니다. 예상치 못한 돈이 은행 계좌에 들어오는 것과 같습니다—때로는 좋지만, 계좌 잔액이 틀릴 수 있고 정확한 숫자에 의존하는 모든 시스템이 작동하기 시작할 수 있습니다.

#### 예방 기법

DoS 문제가 다른 형태로 나타나기 때문에, 솔루션도 일반적으로 상황에 따라 다릅니다.

블록 가스 제한에 도달할 위험이 있는 긴 목록은 상당히 일반적인 상황이므로, 이를 처리하기 위한 몇 가지 제안을 드릴 수 있습니다. 첫 번째 예에서, 컨트랙트는 외부 사용자에 의해 인위적으로 조작될 수 있는 데이터 구조를 순회해서는 안 됩니다. 각 투자자가 독립적으로 토큰을 청구하기 위해 `withdraw` 함수를 호출하는 인출 패턴(풀-오버-푸시 패턴)이 권장됩니다. 긴 목록을 반복하는 함수의 경우, 페이지네이션 기능을 구현하는 것이 좋은 솔루션입니다.

DoS에 대한 일반적인 솔루션은 무엇이 잘못될 수 있는지 가능한 한 많이 조사하고 안전 장치를 구현하는 것입니다.

#### 실제 사례: ZKsync Era Gemholic 자금 잠금

방금 말했듯이, 가장 예상치 못한 오류가 스마트 컨트랙트에서 DoS 문제로 이어질 수 있습니다. 최근 예는 이더리움 L2 솔루션인 ZKsync Era에 스마트 컨트랙트를 배포한 프로젝트 Gemholic과 관련이 있습니다. Gemholic은 토큰 세일에서 모금한 921 ETH(약 170만 달러)에 접근할 수 없는 큰 문제에 직면했습니다. 근본 원인은? 스마트 컨트랙트가 ZKsync Era에서 지원되지 않는 `transfer()` 함수에 의존했습니다. ZKsync Era는 대부분의 EVM 기능과 호환되지만 완전히 EVM과 동등하지 않아 `transfer()`와 같은 일부 기능이 이더리움 메인넷에서처럼 작동하지 않습니다. 이 비호환성으로 인해 스마트 컨트랙트가 의도한 대로 이더를 인출할 수 없어 Gemholic의 자금이 잠겼습니다. 다행히 ZKsync 팀이 개입하여 자금을 해제하는 "우아한 솔루션"을 개발하여 Gemholic이 다시 접근할 수 있게 했습니다. 불행히도 이 "우아한 솔루션"의 구체적인 내용은 공개되지 않았습니다.

### 부동 소수점과 정밀도

이 글을 쓰는 시점에서 Solidity v0.8.29는 고정 소수점 및 부동 소수점 숫자를 완전히 지원하지 않습니다. 이 설계 선택은 결정론에 대한 블록체인의 근본적인 필요에서 비롯됩니다: 합의를 유지하기 위해 네트워크의 모든 노드는 동일한 입력에서 동일한 결과에 도달해야 합니다. 불행히도, 부동 소수점 산술은 본질적으로 다른 하드웨어 아키텍처에서 비결정론적이며, 동일한 계산에서 미묘하게 다른 결과를 생성할 수 있습니다.

블록체인 애플리케이션은 네트워크 포크를 방지하고 보안을 유지하기 위해 절대적인 결정론을 요구하므로, Solidity는 개발자가 표준 정수 유형을 사용하여 부동 소수점 표현을 구현하도록 강제합니다. 이 접근 방식은 더 번거롭고 올바르게 구현되지 않으면 오류가 발생하기 쉽지만, 금융 계산과 스마트 컨트랙트 로직이 네트워크의 모든 노드에서 동일한 결과를 생성하도록 보장합니다.

#### 취약점

고정 소수점 숫자는 아직 Solidity에서 완전히 지원되지 않습니다. 선언할 수는 있지만 할당하거나 할당받을 수 없어, 개발자는 표준 정수 데이터 유형을 사용하여 자체적으로 구현해야 합니다. 이 과정에서 개발자가 빠질 수 있는 몇 가지 함정이 있습니다. 이 섹션에서 그 중 일부를 강조하겠습니다. 코드 예제(예제 9-8)로 시작하겠습니다.

**예제 9-8. FunWithNumbers**

```solidity
1 contract FunWithNumbers {
2    uint256 constant public tokensPerEth = 10;
3    uint256 constant public weiPerEth = 1e18;
4    mapping(address => uint) public balances;
5
6    function buyTokens() public payable {
7        // wei를 eth로 변환한 다음 토큰 비율을 곱함
8        uint256 tokens = msg.value/weiPerEth*tokensPerEth;
9        balances[msg.sender] += tokens;
10    }
11
12    function sellTokens(uint256 tokens) public {
13        require(balances[msg.sender] >= tokens);
14        uint256 eth = tokens/tokensPerEth;
15        balances[msg.sender] -= tokens;
16        payable(msg.sender).transfer(eth*weiPerEth);
17    }
18 }
```

이 간단한 토큰 구매 및 판매 컨트랙트에는 몇 가지 명백한 문제가 있습니다. 토큰 구매 및 판매에 대한 수학적 계산은 정확하지만, 부동 소수점 숫자의 부재는 잘못된 결과를 줄 것입니다. 예를 들어, 8줄에서 토큰을 구매할 때 값이 1 이더 미만이면 초기 나눗셈은 0이 되어 최종 곱셈의 결과가 `0`이 됩니다(예: 200 wei를 `1e18` `weiPerEth`로 나누면 0). 마찬가지로, 토큰을 판매할 때 10개 미만의 토큰도 0 이더가 됩니다. 실제로 여기서 반올림은 항상 내림이므로, 29개의 토큰을 판매하면 2 이더가 됩니다(29 토큰 / 10 `tokensPerEth` = 2.9, 내림하면 2가 됨).

이 컨트랙트의 문제는 정밀도가 가장 가까운 이더(즉, 1e18 wei)에 불과하다는 것입니다. 더 높은 정밀도가 필요할 때 [ERC-20](https://oreil.ly/YzzyU) 토큰에서 소수점을 다룰 때 까다로울 수 있습니다. 실제 사례에서 정밀도 손실은 작아 보일 수 있지만, 쉽게 증폭되고 악용될 수 있습니다. 플래시 론은 예를 들어 공격자가 선불 비용 없이 대량의 자본을 빌릴 수 있게 하여 사소한 불일치도 악용할 수 있게 합니다.

#### 예방 기법

스마트 컨트랙트에서 올바른 정밀도를 유지하는 것은 특히 경제적 결정을 반영하는 비율과 요율을 다룰 때 매우 중요합니다. 사용하는 모든 비율이나 요율이 분수에서 큰 분자를 허용하는지 확인해야 합니다. 예를 들어, 우리 예제에서 `tokensPerEth` 요율을 사용했습니다. 큰 숫자인 `weiPerTokens`를 사용하는 것이 더 나았을 것입니다. 해당 토큰 수를 계산하기 위해 `msg.sender/weiPerTokens`를 수행할 수 있습니다. 이것은 더 정확한 결과를 줄 것입니다.

또 다른 전술은 연산 순서에 주의하는 것입니다. 우리 예제에서 토큰을 구매하는 계산은 `msg.value/weiPerEth*tokenPerEth`였습니다. 나눗셈이 곱셈보다 먼저 발생한다는 것에 주목하세요. 일부 언어와 달리 Solidity는 작성된 순서대로 연산을 수행하는 것을 보장합니다. 이 예제는 곱셈을 먼저 수행한 다음 나눗셈을 수행했다면 더 높은 정밀도를 달성했을 것입니다: `msg.value*tokenPerEth/weiPerEth`.

마지막으로, 숫자에 대한 임의의 정밀도를 정의할 때, 값을 더 높은 정밀도로 변환하고, 모든 수학 연산을 수행한 다음, 출력에 필요한 정밀도로 다시 변환하는 것이 좋은 아이디어일 수 있습니다. 일반적으로 `uint256`이 가스 사용에 최적이므로 사용됩니다; 이것은 범위에서 약 60자릿수의 크기를 제공하며, 그 중 일부는 수학 연산의 정밀도에 전용될 수 있습니다. Solidity에서 모든 변수를 높은 정밀도로 유지하고 외부 앱에서 낮은 정밀도로 다시 변환하는 것이 좋습니다. 이것이 본질적으로 ERC-20 토큰 컨트랙트에서 `decimals` 변수가 작동하는 방식입니다: MetaMask에서 1,000 USDT를 보낼 때, 실제로는 1,000에 USDT의 소수점(1e6)을 곱한 1,000,000,000 단위의 USDT를 보내는 것입니다.

정밀도가 증가된 수학 연산을 처리하는 방법의 예를 보려면, Wad와 Ray 수학을 살펴보겠습니다. *Wad*는 18자리 정밀도의 소수를 나타내며, 이더와 같은 ERC-20 토큰에 공통적인 18 소수점과 완벽하게 일치합니다. 이것은 토큰 잔액을 나타내는 데 이상적이며, 계산 중 충분한 정확도를 보장합니다. *Ray*는 27자리 정밀도로 더 나아가며, 0에 매우 가까운 비율의 계산에 유용합니다. DS-Math로 알려진 첫 번째 Solidity 고정 소수점 수학 라이브러리는 이러한 고정밀 숫자로 작업하기 위한 구조를 제공했습니다.

MakerDAO의 개발자들은 원래 프로젝트의 필요에 맞게 Wad와 Ray를 특별히 만들었습니다. 이더의 18 소수점 표준—그리고 대부분의 ERC-20 토큰도 이 규칙을 따르지만 많은 예외가 있음—을 감안하면, Wad는 주요 금융 단위에 완벽했고, Ray는 정밀한 분수 조정이 필요한 경우를 위해 예약되었습니다. DS-Math가 이 접근 방식을 개척했지만, 이제 정밀한 Solidity 수학 연산을 위해 더 많은 라이브러리를 사용할 수 있습니다. Aave의 WadRayMath, Solmate의 FixedPointMathLib, OpenZeppelin의 Math 라이브러리는 오늘날 사용 가능한 몇 가지 옵션입니다.

#### 실제 사례: ERC-4626 인플레이션 공격

이제 실제로 흔히 악용되는 정밀도 손실 취약점을 OpenZeppelin의 ERC-4626 구현의 단순화된 버전을 사용하여 살펴보겠습니다. ERC-4626은 사용자가 금고에 자산(USDT 등)을 입금하고 금고 자산의 일부를 나타내는 주식을 받을 수 있게 하는 토큰화된 금고 표준입니다. 예제 9-9는 우리가 작업하는 컨트랙트의 단순화된 버전입니다.

**예제 9-9. 원래 ERC4626 OpenZeppelin 구현의 단순화된 버전**

```solidity
1 abstract contract ERC4626 is ERC20, IERC4626 {
2    using Math for uint256;
3    IERC20 private immutable _asset;
4
5    constructor(IERC20 asset_) {
6        _asset = asset_;
7    }
8
9    function totalAssets() public view returns (uint256) {
10        return _asset.balanceOf(address(this));
11    }
12    function deposit(address receiver, uint256 assets) public {
13        SafeERC20.safeTransferFrom(_asset, msg.sender, address(this), assets);
14        uint256 shares = _convertToShares(assets, Math.Rounding.Down);
15        _mint(receiver, shares);
16        emit Deposit(msg.sender, receiver, assets, shares);
17    }
18    function _withdraw(address receiver, uint256 assets) public {
19        uint256 shares = _convertToShares(assets, Math.Rounding.Up);
20        _burn(msg.sender, shares);
21        SafeERC20.safeTransfer(_asset, receiver, assets);
22        emit Withdraw(msg.sender, receiver, msg.sender, assets, shares);
23    }
24    function _convertToShares(uint256 assets, Math.Rounding rounding) internal view
      returns (uint256) {
25        uint256 supply = totalSupply();
26        return
27            (assets == 0 || supply == 0)
28                ? assets
29                : assets.mulDiv(supply, totalAssets(), rounding); // (assets * supply) /
                  totalAssets()
30    }
31    function _convertToAssets(uint256 shares, Math.Rounding rounding) public view returns
      (uint256) {
32        uint256 supply = totalSupply();
33        return
34            (supply == 0)
35                ? shares
36                : shares.mulDiv(totalAssets(), supply, rounding); // (shares * totalAssets())
                  / supply
37    }
38 }
```

이제 공격이 어떻게 진행되는지 살펴보겠습니다.

새로 생성된 ERC-4626 금고를 주시하던 공격자가 하나가 나타나는 것을 봅니다. 그들은 시간을 낭비하지 않고 자신을 위한 주식을 발행하기 위해 금고 자산의 아주 작은 금액, 단 한 단위만 입금합니다. 이 시점에서 금고의 총 자산은 단 하나입니다(공격자가 입금한 것이 전부이기 때문), 주식의 총 공급량도 하나입니다(공격자가 한 주식을 발행했기 때문).

여기서 상황이 교활해집니다. 공격자는 이제 다른 사용자가 상당한 금액—예를 들어 1,000 USDT—을 입금하기를 기다립니다. 그러나 합법적인 트랜잭션이 진행되기 전에, 공격자가 끼어들어 금고 컨트랙트에 직접 1,000 USDT를 전송하여 입금을 프론트 런합니다. 중요한 것은, 공격자가 금고의 `deposit` 함수를 사용하지 않습니다; 그들은 단지 `USDT.transfer()`를 호출합니다. 이 1,000 USDT의 "기부"는 금고의 `totalAssets()`를 1000e6 + 1로 부풀리고, 주식의 `totalSupply()`는 1로 유지됩니다. 1,000 USDT가 실제로 1,000e6으로 계산된다는 것을 명심하세요. 이것은 1,000에 USDT의 소수점(1e6)을 곱한 것입니다.

피해자의 입금이 마침내 처리되면, 스마트 컨트랙트는 사용자에게 발행할 주식 수를 계산하려고 합니다. 기억하세요, 주식 계산 공식은:

(assets × supply) / `totalAssets()`

우리의 경우, 피해자는 1,000e6 USDT를 입금하고 있으며, 공식은 다음과 같이 됩니다:

1,000e6 × 1 / (1,000e6 + 1) = 0.999

내림 메커니즘 때문에, 이것은 0 주식이 됩니다. 피해자는 1,000 USDT 입금에 대해 아무것도 받지 못합니다.

한편 공격자는 여전히 한 주식을 보유하고 있으며, 이제 그 주식을 소각하고 총 금고 잔액인 2,000 USDT를 인출할 수 있습니다. 공격자는 모든 자금을 가지고 떠나고 피해자는 빈손으로 남습니다.

> **참고**
>
> OpenZeppelin은 이후 가상 오프셋과 소수점 오프셋을 모두 도입하여 이 공격을 방지하기 위해 ERC-4626 구현을 업데이트했습니다. 소수점 오프셋은 금고 주식에 사용되는 소수점 자릿수를 늘려 반올림 오류를 최소화하고 정밀도 손실 공격의 수익성을 낮춥니다. 가상 오프셋은 환율 계산에 가상 자산과 주식을 추가하여 공격자가 초기 전환율을 조작하는 능력을 제한하고 금고를 죽은 주식 생성으로부터 보호합니다.

### 가격 조작

정확한 자산 가격 책정은 DeFi 프로토콜이 원활하게 운영되는 데 필수적입니다. 이러한 시스템은 현재 자산 가치를 제공하기 위해 가격 오라클에 의존합니다. *오라클*을 스마트 컨트랙트에 실세계 정보를 공급하는 데이터 피드로 생각하세요. 가격 조작 공격은 이러한 오라클에 초점을 맞춥니다—따라서 스마트 컨트랙트의 코드 자체가 아니라 컨트랙트가 의존하는 데이터입니다. 이 조작은 DeFi 프로토콜의 동작을 크게 변경하여 일반적으로 존재하지 않을 차익 거래 기회를 만들어낼 수 있습니다. 결과는? 공격자가 시스템을 악용하여 상당한 이익을 얻을 수 있습니다.

#### 취약점

이 간단한 시나리오를 상상해 보세요: 공격자가 가격 책정을 위해 안전하지 않은 오라클에 의존하는 대출 프로토콜을 발견합니다. 자산의 가격을 실제보다 낮게 보이도록 조작함으로써, 공격자는 허용되어야 하는 것보다 더 많은 해당 자산을 빌릴 수 있습니다. 그런 다음 빌린 자산을 실제 시장 가격에 팔아 이익을 얻습니다. 이 취약점의 근본은 자산 가격을 결정하기 위해 조작될 수 있는 온체인 가격 지표에 의존하는 것입니다. 조작은 종종 *플래시 론*을 사용하여 증폭됩니다: 동일한 트랜잭션 블록 내에서 상환해야 하는 즉각적이고 담보 없는 대출입니다.

#### 예방 기법

가격을 결정해야 할 때, 가장 좋은 방법은 Chainlink, RedStone, Pyth 등과 같은 분산 오라클을 사용하는 것입니다. 이러한 오라클이 분산되어 있기 때문에, 공격자가 네트워크 노드의 50% 이상을 제어해야 하므로 훼손하기가 훨씬 더 어렵습니다. 그러나 제한 사항이 있습니다. 예를 들어, 모든 자산에 대해 사용할 수 없을 수 있습니다. 그러한 경우, 시간 가중 평균 가격(TWAP) 오라클로 전환할 수 있습니다.

TWAP 오라클은 추가된 보안과 함께 온체인 데이터에서 자산 가격을 도출합니다. 지난 5분과 같은 정의된 시간 프레임에 걸쳐 자산의 평균 가격을 계산하여 작동합니다. 계산에서 현재 블록을 제외함으로써, TWAP 오라클은 플래시 론 공격으로부터 효과적으로 보호합니다. 그러나 TWAP 오라클은 자금이 풍부한 공격자에 의한 조작에 완전히 면역되지 않습니다. 핵심은 기간 길이를 조정하는 것입니다: 기간이 길수록 공격자가 가격을 조작하는 데 더 많은 자본이 필요합니다. 그러나 기간이 길수록 TWAP 가격이 실제 시장 가격에서 더 많이 벗어날 수 있음을 의미합니다. 따라서 프로젝트의 특정 필요와 위험 프로필에 따라 TWAP를 미세 조정하는 것이 중요합니다.

사용하는 오라클에 관계없이, 제공하는 데이터를 맹목적으로 신뢰해서는 안 됩니다. 오라클 데이터를 다른 소스와 정기적으로 검증하는 것이 좋은 관행입니다. 예를 들어, 오라클 가격을 다른 소스의 가격과 비교하고 상당한 불일치를 표시하는 스크립트를 작성할 수 있습니다. 그러한 차이가 발견되면, 추가 문제를 방지하기 위해 프로토콜을 일시 중지할 수 있습니다.

#### 프로토타입 예제: AMM 온체인 데이터에 대한 의존

종종 취약한 오라클 모듈은 이 예에서 볼 수 있듯이 프로토콜 자체의 일부입니다. 일반적인 악용 시나리오는 스마트 컨트랙트가 Uniswap과 같은 온체인 AMM 프로토콜에서 직접 자산 가격을 도출할 때 발생합니다. 4,000 USDC와 1 ETH의 준비금이 있는 Uniswap V2 풀을 상상해 보세요. 스마트 컨트랙트는 1 ETH가 4,000 USDC의 가치가 있다고 가정할 수 있습니다. 그러나 이 가정은 추론된 가격이 추가 상태 변경 작업에 사용될 경우 매우 위험할 수 있습니다. 그러한 경우, 공격자는 플래시 론을 받아 대규모 스왑을 수행하여 풀의 잔액을 변경하고 따라서 ETH의 추론된 가격을 변경할 수 있습니다. 이 조작된 가격에 의존하는 취약한 프로토콜은 공격자에 의해 악용됩니다.

다행히도 이 특정 공격 벡터는 잘 알려져 있습니다. 예전만큼 자주 악용되지는 않지만, 여전히 주목할 만한 사건에서 나타납니다. 예를 들어 2025년 5월, Mobius Token이 210만 달러에 악용되었습니다. 즉각적인 트리거는 `mint` 함수에서 1018을 곱하는 결함 있는 곱셈이었지만, 컨트랙트에는 BNB/USDT 가격을 계산하기 위해 온체인 지표에 의존하는 별개이지만 똑같이 중요한 취약점도 포함되어 있어 조작에 노출되었습니다. 수학 버그가 없었더라도, 컨트랙트는 짧은 시간 내에 여전히 악용되었을 것입니다. 이렇게 많은 총 잠금 가치(TVL)를 확보하는 코드가 어떻게 프로덕션에 올라갔는지 궁금할 수 있습니다. 팀은 컨트랙트의 소스 코드를 공개하지 않기로 선택했으며, 숨기는 것이 안전을 제공할 것이라고 가정했습니다—특히 그 위험이 높을 때 불명확성을 통한 보안이 작동하지 않는다는 또 다른 알림입니다.

> **참고**
>
> 온체인 데이터에서 추론된 가격을 사용하는 것은 이러한 가격이 상태 변경 작업에 적용될 때만 위험합니다. 가격이 프론트엔드가 데이터를 가져오는 데 사용하는 view 함수와 같이 정보 목적으로만 사용된다면, 공격은 실행 가능하지 않습니다. 그러나 외부 컨트랙트가 그러한 view 함수에서 가격을 검색한 다음 상태 변경 작업에 사용한다면, 조작에 취약해집니다.

#### 실제 사례: Mango Markets

Mango Markets 익스플로잇에서, 트레이더는 플랫폼의 가격 조작 취약점을 이용하여 1억 1,600만 달러 이상을 추출했습니다. 두 개의 지갑에 1,000만 달러를 사용하여, 공격자는 각각 3.8센트에 4억 8,300만 개의 Mango 영구 선물(MNGO-PERPs)을 열었습니다. 그런 다음 세 개의 개별 거래소에서 400만 달러 상당의 MNGO를 구매하여 오라클 보고 가격을 2,300% 끌어올렸습니다. 이 부풀려진 영구 포지션을 담보로 사용하여, 공격자는 Mango Markets에서 1억 1,600만 달러를 빌렸고, 상당한 불량 부채를 남기고 자금을 가지고 도주했습니다. 가격 조작 익스플로잇에서 흔히 발생하듯이, 이것은 해킹이 아니라 시스템 역학의 조작으로, 기본 코드를 깨지 않고 Mango의 유동성을 악용했습니다.

#### 익스플로이터와의 협상
익스플로이터와 프로토콜은 종종 온체인에서 직접 협상하여 익스플로이터가 고소를 취하하는 대가로 도난당한 자금의 얼마를 반환해야 하는지를 결정합니다. 이러한 거래는 흔하지만, 법정에서 법적 효력이 거의 없을 것입니다. 일반적으로 프로토콜은 익스플로이터에게 약 10%의 바운티를 제공합니다. 즉, 익스플로이터가 도난당한 자금의 90%를 반환하면 프로토콜은 추적을 중단하는 데 동의합니다. 이러한 유형의 협상이 흔하지만, 이 사례에서 발생한 일은 특히 주목할 만했습니다.
익스플로잇 후, 공격자는 Mango Markets의 DAO에 거래를 제안했습니다: 커뮤니티가 이전에 다른 Solana 프로젝트인 Solend를 구하기 위해 인수한 일부 불량 부채를 충당하는 데 동의하면 도난당한 자금의 대부분을 반환하겠다는 것이었습니다. 이에 대응하여, Mango 팀은 공격자가 최대 6,700만 달러를 반환하고 4,700만 달러를 일종의 버그 바운티로 유지하는 두 번째 제안을 내놓았습니다. 계약에는 불량 부채와 관련된 모든 청구의 포기와 토큰이 반환되면 형사 고발을 추구하거나 공격자의 자금을 동결하지 않겠다는 약속이 포함되었습니다. 첫 번째 제안은 거부되었고, 두 번째 제안은 통과되었습니다. 이로 인해 Mango Markets는 10월 15일에 6,700만 달러의 자산이 실제로 반환되었다고 트윗했습니다.
공격자 중 한 명이 트위터에서 자신을 밝히고 익스플로잇을 "매우 수익성 있는 거래 전략"이라고 부르며 모든 것이 프로토콜의 의도된 설계 내에서 이루어졌다고 주장하면서 상황이 법적 전환점을 맞았습니다. 그러나 미국 당국은 다르게 보고 시장 조작 혐의로 그를 체포했습니다. Mango Markets는 그 후 계약이 강박 하에 이루어졌기 때문에 무효가 되어야 한다고 주장하며 민사 소송을 제기하고 4,700만 달러의 손해 배상을 요구했습니다. DAO는 법적으로 비교적 새로운 개념이므로, 이 사건은 많은 주목을 받았으며 분산 조직이 법적 분쟁을 처리하는 방식에 선례를 세울 수 있습니다.
암호화폐의 혼란스러운 법적 지형을 완벽하게 포착하는 반전에서, 공격자는 실제로 2025년 5월에 사기 사건에서 승리했습니다: 판사는 서비스 약관이 없는 허가 없는 프로토콜을 사기할 수 없다고 판결했습니다. 그러나 여기에 반전이 있습니다: 당국이 원래 Mango Markets 조사 중에 그의 장치를 검색했을 때, 1,200개 이상의 아동 성적 학대 이미지와 비디오를 발견했고, 그는 현재 그것으로 4년 이상의 형을 살고 있습니다. 이는 훌륭한 DeFi 익스플로잇조차도 기본적인 인간 품위 위반으로부터 여러분을 구할 수 없다는 것을 증명합니다.

### 부적절한 입력 유효성 검사

종종 간과되는 주요 취약점 중 하나는 부적절한 입력 유효성 검사입니다. 사용자나 외부 소스의 입력이 적절하게 유효성 검사되지 않으면, 스마트 컨트랙트에 대한 결과는 사소한 문제부터 상당한 자금 손실까지 광범위하게 달라질 수 있습니다. 적절한 입력 유효성 검사는 컨트랙트의 동작을 조작할 수 있는 악의적인 행위자와 자금 손실로 이어질 수 있는 사용자나 관리자의 진정한 실수 모두로부터 보호하는 데 도움이 됩니다. 적절한 예방 조치를 취하지 않으면, 겉보기에 무해한 실수가 컨트랙트 실행에 상당한 문제를 일으킬 수 있습니다.

#### 취약점

핵심적으로, 부적절한 입력 유효성 검사는 스마트 컨트랙트가 받는 데이터나 매개변수를 처리하기 전에 철저히 확인하지 않을 때 발생합니다. 특정 값이 특정 조건을 충족하는지 확인하지 않으면, 진정한 사용자 실수와 잠재적 공격 모두에 문을 열어둡니다. 사용자는 실수로 잘못된 데이터를 입력할 수 있고, 공격자는 의도적으로 예상치 못한 데이터를 컨트랙트에 공급할 수 있습니다. 이것은 의도된 로직을 우회하고 예상치 못한 상태 변경으로 이어져 컨트랙트가 예측 불가능하게 동작하게 만들 수 있습니다.

이 취약점의 간단한 예는 세터 함수가 자금의 수신자로 설정하기 전에 주소가 제로 주소가 아닌지 확인하지 않을 때 발생합니다. 실수로 제로 주소를 수신자로 설정하면, 제로 주소로 전송된 자금은 영원히 잠겨 회수할 수 없게 됩니다.

스마트 컨트랙트 개발에서 흔하고 위험한 오해는 소스 코드를 비공개로 유지하면 어떻게든 악용으로부터 보호될 것이라는 믿음입니다. 이 장에서 불명확성을 통한 보안이 작동하지 않는 이유를 이전에 논의했으며, 이 원칙은 입력 유효성 검사에도 적용됩니다. 개발자는 때때로 코드가 공개되지 않으면 발견되지 않을 것이라고 가정하여 함수를 보호하지 않은 채로 둡니다. 그러나 공격자는 컨트랙트 바이트코드를 리버스 엔지니어링하여 민감하고 보호되지 않은 함수를 식별할 수 있고 실제로 그렇게 합니다. 예를 들어, 여러 비공개 소스 MEV 봇이 보호되지 않은 플래시 론 콜백을 통해 악용되어 수백만 달러의 손실을 초래했습니다. 코드를 숨기는 것은 위험을 숨기지 않습니다.

#### 예방 기법

그렇다면 부적절한 입력 유효성 검사로부터 어떻게 보호할까요? 첫 번째 단계는 간단합니다: 받는 입력이 유효하다고 가정하지 마세요. 입력이 EOA, 다른 컨트랙트 또는 때로는 동일한 컨트랙트에서 오든, 엄격하게 확인해야 합니다. 입력 길이뿐만 아니라 최소값과 최대값과 같은 엣지 케이스와 경계 조건도 유효성 검사해야 합니다. 간과해서는 안 되는 전형적인 엣지 케이스는 0 값입니다.

재사용 가능한 유효성 검사 로직은 안전하고 유지 관리 가능한 스마트 컨트랙트를 작성하는 핵심 부분입니다. 가장 적합한 것에 따라 모디파이어나 내부 함수를 사용하여 이러한 유효성 검사 블록을 구현할 수 있습니다. 모디파이어는 일관되고 선언적인 방식으로 여러 함수에 사전 조건이나 사후 조건을 첨부하는 데 특히 유용합니다. 예를 들어, 함수의 입력이 제로 주소가 아닌지 확인하거나 민감한 작업을 실행하기 전에 호출자가 올바른 권한을 가지고 있는지 확인하기 위해 모디파이어를 사용할 수 있습니다. 내부 함수는 동일한 목표를 달성할 수 있으며 때로는 더 많은 유연성을 제공합니다. 특히 유효성 검사가 복잡한 로직에 의존하거나 값을 반환해야 할 때 그렇습니다.

#### 접근 제어
권한에 대해 말하자면, 강력한 접근 제어를 구현하는 것이 중요합니다: `msg.sender`는 매개변수이며 그렇게 취급되어야 합니다. 커스텀 로직은 옵션이지만, OpenZeppelin과 같은 신뢰할 수 있는 라이브러리를 사용하면 복잡성을 최소화하면서 안전하게 접근을 관리하는 데 도움이 됩니다.
한 엔터티가 완전한 제어가 필요한 간단한 프로젝트의 경우, 개발자는 핵심 함수에 대한 권한을 가진 단일 "소유자"를 지정하는 OpenZeppelin의 Ownable 컨트랙트를 사용할 수 있습니다. 추가 보안을 위해, Ownable2Step을 사용하는 것이 좋습니다. 이 버전에는 우발적인 소유권 손실을 방지하는 2단계 소유권 이전 프로세스가 포함됩니다.
더 복잡한 필요의 경우, OpenZeppelin의 AccessControl을 사용하면 각각 다른 권한을 가진 여러 역할을 만들 수 있습니다. 역할 기반 접근 제어를 통해 다른 사용자에게 특정 작업을 할당할 수 있어 더 큰 프로젝트에 이상적입니다.
적절한 접근 제어를 구현하기 전에, 누가 외부 및 공개 함수를 호출할 수 있는지에 대한 모든 가정을 검증해야 합니다. 스마트 컨트랙트는 공개적이고 신뢰 없는 환경에서 작동하므로, 의도한 엔터티만 컨트랙트와 상호 작용할 것이라고 가정할 수 없습니다. 사실, 공격자가 이러한 함수를 호출하여 의도하지 않은 동작을 트리거하려고 시도할 것이라고 항상 가정해야 합니다.

#### 프로토타입 예제: 임의 호출

가장 일반적인 익스플로잇은 임의 호출을 수반합니다. 여기서, 취약한 스마트 컨트랙트는 공격자가 호출할 주소를 제공할 수 있게 합니다. 이러한 상황에서, 컨트랙트는 공격자가 원하는 모든 호출을 효과적으로 수행합니다. 이를 악용하는 한 가지 가능한 방법은 컨트랙트가 전송해서는 안 되는 토큰을 전송하도록 속이는 조작된 값을 반환하는 것입니다.

취약한 수익 집계 프로토콜의 이 샘플 코드를 확인하세요:

```solidity
contract Aggregator {
    function stake( ... ) external {
        ...
    }
    function claimMultipleStakingRewards(address[] calldata _claimContracts) external {
        uint256 totalRewards;
        for (uint256 i = 0; i < _claimContracts.length; i++) {
            totalRewards += IClaimContract(_claimContracts[i]).claimStakingRewards(
            msg.sender
            );
        }
        IERC20(stakingToken).transfer(msg.sender, totalRewards);
    }
}
```

목표는 간단합니다: `claimMultipleStakingRewards` 함수는 사용자가 제공한 스테이킹 컨트랙트 주소 배열을 순회하고, 각각에서 `claimStakingRewards` 함수를 호출하며, 총 보상을 합산합니다. 마지막으로, 누적된 보상을 사용자의 주소로 보냅니다. 문제는 컨트랙트가 `_claimContracts`의 주소가 실제로 신뢰할 수 있는 스테이킹 컨트랙트를 가리키는지 확인하지 않는다는 것입니다. 이것은 임의의 외부 호출에 문을 열어둡니다.

예를 들어, 공격자는 다음과 같은 컨트랙트를 배포할 수 있습니다:

```solidity
contract Attack {
    function claimStakingRewards(address ) external pure returns (uint256) {
        return 1_000_000 ether; // 조작된 보상
    }
}
```

이 악성 컨트랙트는 스테이킹 컨트랙트인 척하고 단순히 부풀려진 보상 값을 반환합니다. `Aggregator`가 그것에서 `claimStakingRewards`를 호출하면, 호출자에게 엄청난 양의 토큰이 빚져 있다고 생각하도록 속습니다. 추가 확인 없이, `Aggregator`는 맹목적으로 그것을 총계에 추가하고 공격자에게 실제 토큰을 전송합니다. 이것은 `claimMultipleStakingRewards`에서 신뢰할 수 있는 컨트랙트만 허용되도록 하는 기본 허용 목록으로 피할 수 있었습니다.

### 서명 재생 공격

이더리움의 서명은 오프체인에서 작업을 승인할 수 있게 하여 비용이 많이 드는 온체인 트랜잭션의 필요를 줄이기 때문에 매우 유용합니다. 예를 들어, 토큰 전송이나 스마트 컨트랙트의 특정 기능에 접근하는 것과 같이 누군가에게 대신 특정 작업을 수행할 권한을 부여하는 경우, 권한을 주는 오프체인 메시지에 서명할 수 있습니다. 그런 다음 컨트랙트는 서명을 검증하고 온체인에서 직접 상호 작용할 필요 없이 작업을 실행합니다. 이것은 또한 가스 없는 트랜잭션을 가능하게 합니다. 여기서 오프체인에서 서명하고 릴레이어가 가스 비용을 지불하면서 온체인에 제출합니다. 스마트 컨트랙트는 이러한 서명을 검증하여 지속적인 온체인 상호 작용 없이 작업이 안전하게 승인되도록 보장할 수 있습니다.

그러나 데이터 조각이 한 번 서명되면, 논리적으로 한 번만 사용되어야 합니다. 서명된 트랜잭션이 재사용될 수 있다면, 공격자가 서명을 재생하여 자금 전송이나 권한 없이 컨트랙트 상태 변경과 같은 동일한 작업을 여러 번 실행하는 재생 공격에 문을 열어둡니다. 스마트 컨트랙트는 각 서명된 메시지가 고유하고 재생될 수 없도록 하여 이를 방지하도록 설계되어야 합니다.

#### 취약점

재생 공격에 취약한 예제 컨트랙트(예제 9-10)를 살펴보겠습니다.

**예제 9-10. Token: 서명 재생 공격에 취약한 컨트랙트**

```solidity
1 contract Token {
2    mapping(address => uint256) public balances;
3    struct Signature {
4        bytes32 r;
5        bytes32 s;
6        uint8 v;
7    }
8    event Transfer(address indexed from, address indexed to, uint256 amount);
9    function transfer(uint256[] memory _amount, address[] memory _from, address[]
     memory _to,  Signature memory _signature) public {
10        bytes32 messageHash = keccak256(abi.encodePacked(_from, _to, _amount));
11        address signer = ecrecover(messageHash, _signature.v, _signature.r, _signature.s);
12        for(uint256 i = 0; i < _from.length; i++){
13            address __from = _from[i];
14            address __to = _to[i];
15            uint256 __amount = _amount[i];
16            require(balances[__from] >= _amount[i], "Insufficient balance");
17            require(signer == _from[i], "Invalid signature");
18            balances[__from] -= __amount;
19            balances[__to] += __amount;
20            emit Transfer(__from, __to, __amount);
21        }
22    }
23 }
```

언뜻 보기에, 이것은 편리한 컨트랙트 함수처럼 보입니다. 유효한 서명이 있는 누구나 서명자가 가스를 지불할 필요 없이 여러 전송을 수행할 수 있습니다. 관리자는 오프체인에서 데이터에 서명할 수 있고, 다른 누군가—아마도 서비스—가 대신 온체인에 트랜잭션을 제출할 수 있습니다. 어쨌든, 서명 처리는 사소하지 않으며, 이 매우 짧은 코드에는 상당한 수의 문제가 포함되어 있습니다.

가장 명백한 문제는 누군가가 동일한 서명을 반복해서 재사용하는 것을 방지하는 메커니즘이 없다는 것입니다. 서명이 사용되었는지 추적할 방법이 없으면, 공격자는 피해자의 잔액이 소진될 때까지 트랜잭션을 반복할 수 있습니다. 수정은 꽤 간단합니다: 서명되는 데이터에 *논스*(한 번만 사용되는 값, 일반적으로 각 트랜잭션마다 증가하는 카운터)를 추가해야 합니다. 서명을 검증하는 컨트랙트는 제공된 논스가 이전에 사용되지 않았는지 확인할 책임이 있습니다. 이것은 각 서명도 고유하도록 보장하여 재생을 방지합니다. 이더리움 트랜잭션은 이러한 이유로 이미 논스를 사용합니다.

여기서 또 다른 중요한 문제는 서명 가변성입니다. 이것은 암호화 서명이 동일한 기본 메시지에 대해 다르지만 여전히 유효한 서명을 생성하도록 변경될 수 있을 때 발생합니다. 컨트랙트에서 사용되는 내장 `ecrecover` 함수는 이 문제에 취약합니다. 공격자는 유효한 서명을 조정하여 기본 서명된 메시지가 동일하게 유지되더라도 작동하는 또 다른 서명을 만들 수 있습니다. 이를 피하기 위해, 개발자는 OpenZeppelin ECDSA 라이브러리에서 제공하는 것과 같은 더 안전한 서명 검증 방법을 사용해야 합니다. 가변 서명은 재생 공격을 피하기 위해 서명을 고유 식별자로 사용하고 싶지 않은 이유입니다—논스를 고수하세요.

재생 공격에 취약한 것에 대해 주소했지만, 서명되는 데이터도 조작될 수 있다면 어떻게 될까요? 이 컨트랙트에서는 그럴 수 있습니다. 문제는 컴팩트한 인코딩으로 더 적은 메모리가 필요하기 때문에 종종 선택되는 `abi.encodePacked`의 사용에 있습니다. 그러나 그 효율성에는 트레이드오프가 있으며, 이제 그것을 탐구할 것입니다. 구체적으로, `abi.encodePacked`는 길이 정보나 경계를 추가하지 않고 원시 바이트를 연결합니다. 이것은 다른 입력 세트가 결국 동일한 출력을 생성할 수 있음을 의미합니다. 어떻게 진행되는지 살펴보겠습니다.

단순화를 위해, 금액이 8비트(두 자리 16진수)를 차지하고 주소가 12비트(세 자리 16진수)를 차지한다고 가정하겠습니다. 매개변수가 다음과 같다고 가정해 보겠습니다:

```solidity
_amount = [0x64, 0x64]
_from = [0x001, 0x002]
_to = [0x003, 0x003]
```

`abi.encodePacked`를 사용하면, 이러한 값을 `0x6464001002003003`으로 결합합니다. 그러나 여기서 상황이 까다로워집니다. `0x002`를 `_from`에서 `_to`로 이동해도, 이전과 정확히 동일한 출력을 `abi.encodePacked`에서 얻습니다:

```solidity
_amount = [0x64, 0x64]
_from = [0x001]
_to = [0x002, 0x003, 0x003]
```

이 새로운 값 세트에 대해, `abi.encodePacked`는 동일한 출력을 반환합니다: `0x6464001002003003`. 이것은 사용자 `0x002`가 유효한 서명을 사용하지만 입력 매개변수 `_from`과 `_to`를 변경하여, 수행해야 할 유일한 전송이 `0x001`에서 `0x002`로라고 컨트랙트가 생각하도록 속일 수 있음을 의미합니다. 예제에서 사용된 코드는 입력 유효성 검사를 매우 잘못 수행하여 이러한 문제 상황을 허용합니다. 어쨌든, 배열과 같은 동적 데이터 유형에 대한 서명을 생성할 때 `encodePacked`를 피해야 함을 보여줍니다. 이러한 경우, 동적 데이터를 연결할 때도 모호하지 않은 출력을 생성하여 이러한 유형의 공격을 효과적으로 방지하는 `abi.encode`를 사용해야 합니다.

그러나 잠깐, 또 하나의 문제가 있습니다. 이 컨트랙트가 여러 체인에 배포된다면 어떻게 될까요? 동일한 서명이 모든 체인에서 유효할 것이며, 크로스체인 재생 공격의 기회를 만듭니다. 공격자는 한 체인에서 사용자의 활동을 모니터링한 다음 다른 체인에서 서명을 재사용할 수 있습니다. 이를 방지하려면, 서명된 메시지에 컨텍스트 데이터를 포함해야 합니다—최소한 `chainId`. 사용 사례에 따라, 컨트랙트 주소나 버전도 포함할 수 있습니다. 다행히도 처음부터 새로운 솔루션을 만들 필요가 없습니다: EIP-712는 컨텍스트 인식 서명을 허용하여 이를 해결하는 표준입니다. 또한 혼란스러운 바이트 문자열 대신 서명하는 내용에 대한 읽을 수 있는 정보를 사용자에게 보여줌으로써 사용자 경험을 개선합니다.

#### 예방 기법

재생 공격 및 기타 취약점을 방지하려면, 각 서명이 고유하고 안전하며 한 번만 사용 가능하도록 보장해야 합니다. 논스, 안전한 서명 처리, 컨텍스트 인식 서명을 통해 쉽게 달성할 수 있습니다.

논스는 고유성을 보장하는 데 사용됩니다. 각 서명된 메시지에 논스를 추가함으로써, 공격자가 서명을 재사용하는 것을 방지합니다. 서명을 검증하는 컨트랙트는 사용된 논스가 고유한지 확인합니다. 서명이 한 번 사용되면, 그 논스는 무효가 되어 재생 시도를 중지합니다.

서명을 검증할 때, 일반 내장 `ecrecover` 함수를 사용하지 말고 서명 가변성에 면역인 OpenZeppelin의 ECDSA 라이브러리에 의존해야 합니다. 또한 서명을 고유 식별자로 사용해서는 안 됩니다. 조작될 수 있기 때문입니다.

동적 데이터에 서명할 때, `abi.encodePacked` 대신 `abi.encode`를 사용하면 데이터를 적절하게 분리하여 조작을 방지하고 변조되거나 오해될 수 없도록 합니다.

마지막으로, 서명으로 작업할 때마다 EIP-712를 구현해야 합니다. 크로스체인 재생을 방지하기 위한 `chainId`와 같은 컨텍스트 인식 추가 외에도, EIP-712는 사용자가 불투명한 바이트 문자열 대신 서명하는 데이터의 명확하고 의미 있는 시각화를 볼 수 있게 하여 사용자 경험을 개선합니다. 이것은 트랜잭션을 이해하기 쉽게 만들 뿐만 아니라 사용자가 의심스러운 요청을 더 잘 인식할 수 있어 피싱 공격을 더 어렵게 만들어 사용자 안전도 향상시킵니다.

#### 실제 사례: TCH 토큰

2024년 5월, TCH 토큰은 일반적인 서명 가변성 취약점으로 인해 악용되었습니다. 문제는 토큰 소각을 승인하기 위해 서명을 검증하는 컨트랙트의 `burnToken` 함수에 있었습니다. 서명 재생 공격을 방지하기 위해, 컨트랙트는 사용된 서명을 매핑에 저장했습니다. 그러나 서명이 변조되면 이 방어를 우회할 수 있었습니다.

공격자는 이전에 제출된 서명을 수집하고 서명의 일부인 `v`와 `s` 값을 수정하여 이를 악용했습니다. 서명이 변경되었지만, 여전히 `ecrecover`를 사용한 검증을 통과했습니다. 수정된 서명이 원본과 달랐기 때문에, 이미 사용된 것으로 인식되지 않았고, 새 버전이 매핑에 저장되었습니다. 이 트릭으로, 공격자는 PancakeSwap 유동성 쌍이 소유한 대량의 TCH 토큰을 반복적으로 소각할 수 있었습니다. 이를 통해 공격자는 풀에서 토큰의 가격을 조작하고 자신이 야기한 가격 변동으로 이익을 얻을 수 있었습니다.

### 스마트 컨트랙트 구성 오류

구성 오류는 기술적으로 취약점은 아니지만 여전히 스마트 컨트랙트에 심각한 결과를 초래할 수 있는 교활한 문제 중 하나입니다. 스마트 컨트랙트를 작성하고 감사를 받은 후에도 작업이 끝나지 않습니다; 여전히 배포, 유지 관리, 때로는 업그레이드해야 합니다. 그리고 구성 오류가 종종 발생하는 것은 이러한 단계 동안입니다. 예를 들어 DeFi 프로토콜은 수많은 매개변수와 함께 제공되며, 이 중 하나라도 잘못 구성되면 상당한 손실로 이어질 수 있습니다. 불행히도, 감사자가 종종 배포 및 업그레이드 스크립트를 간과하기 때문에 이러한 종류의 문제는 감사에서도 잡기 어렵습니다. 따라서 구성 오류 자체는 취약점이 아니지만, 취약점에 대한 기회를 만들 수 있어 배포 및 관리 단계에서 각별히 주의하는 것이 중요합니다.

구성 오류 문제는 광범위하게 다양할 수 있어 분류하기 어려우므로, 모든 것을 나열하려고 하는 대신 무엇이 잘못될 수 있는지 감을 잡기 위해 실제 사례로 바로 들어가겠습니다.

#### 실제 사례: yUSDT

가장 간단한 구성 오류 사례를 살펴보겠습니다: 2023년 4월 익스플로잇으로 이어진 Yearn Finance의 yUSDT 토큰의 잘못 구성된 저장소 변수입니다. yUSDT 토큰은 USDT 기반 파생 상품에 투자하여 수익을 창출해야 하지만, 구성 오류로 인해 실제로는 기본 자산으로 다른 토큰(IUSDC)을 사용하고 있었습니다. 미친 점은 이것이 천 일 이상 발견되지 않았다는 것입니다. 구성 오류로 인해 공격자는 시스템을 조작하고, 풀에서 가치를 빼내고, 본질적으로 무료로 yUSDT를 발행할 수 있었습니다. 결과적으로, yUSDT의 가치가 0으로 떨어졌고, 공격자는 1,160만 달러의 이익을 가지고 떠났습니다.

#### 실제 사례: Ronin Bridge

2024년 8월, Ronin Bridge는 컨트랙트 업그레이드 후 한 시간 만에 해킹당했습니다. 근본 원인은 업그레이드 과정에서의 실수였습니다: 중요한 변수인 `_totalOperatorWeight`가 초기화되지 않았습니다. 이 변수는 `initializeV3` 함수에서 설정되어야 했지만, 업그레이드 중에 `initializeV4`만 호출되어 이전 버전의 필요한 설정을 건너뛰었습니다. 이 실수로 컨트랙트가 노출되었습니다. 이 경우, 화이트햇 MEV 봇이 공격을 선점하고 도난당한 4,000 ETH를 반환할 수 있었지만, 이것은 업그레이드 절차의 철저한 검토와 테스트의 중요성을 강조합니다.

> **참고**
>
> 컨트랙트 업그레이드 직후 해킹이 발생하는 것이 우연이라고 생각한다면, 착각입니다. 블랙햇과 화이트햇 모두 컨트랙트 업그레이드를 면밀히 모니터링합니다: 블랙햇은 악용할 약점을 찾고 화이트햇은 공격을 방지하려고 합니다. 팀은 종종 작은 코드 변경의 보안 위험을 과소평가하고 감사 과정을 건너뜁니다. 불행히도, 컨트랙트를 깨는 데는 많은 것이 필요하지 않으며, 이 사례가 보여주듯이 취약점이 항상 스마트 컨트랙트 자체에 있는 것은 아닙니다—때로는 업그레이드가 실행되는 방식에 있습니다.

#### 실제 사례: Sonne Finance

Sonne Finance 2024년 5월 해킹의 근본 원인은 단순히 전형적인 프로토콜 버그가 아니라 시장 활성화 프로세스의 결함이었습니다. 많은 프로토콜과 마찬가지로, Sonne는 Compound v2에서 발견된 "빈 시장" 버그를 알고 있었습니다. 열려 있지만 자금이 없는 시장이 전체 프로토콜을 빼내는 데 악용될 수 있습니다. 이 버그에 대한 표준 수정은 시장이 활성화될 때 원자적으로 자금이 입금되어 시장이 어느 시점에서도 비어 있지 않도록 보장하는 것입니다.

Sonne는 이것을 처리할 계획을 세웠습니다. 시장을 추가하고, 자금을 입금하고, 사용을 위해 시장을 열려고 했습니다—세 가지 작업 모두 타임록을 통해. 올바른 순서로 수행되었다면 프로세스가 작동했을 것입니다. 문제는 Sonne가 이러한 각 단계를 거버넌스 타임록 컨트롤러에서 별도의 트랜잭션으로 예약했기 때문에 실행 순서가 강제되지 않았다는 것입니다. Sonne 팀은 거버넌스 `EXECUTOR_ROLE`을 모든 사람에게 접근 가능하게 만들어 타임록이 만료되면 모든 사용자가 거버넌스 트랜잭션을 실행할 수 있게 했습니다. 이 설정은 비정상적이지만 본질적으로 문제가 되지는 않았습니다; 그러나 이 특정 상황에서는 치명적임이 입증되었습니다. 타임록이 만료되면 누구나 순서에 상관없이 작업을 실행할 수 있는 문을 열어두었습니다.

공격자는 단순히 자금 입금을 기다리지 않고 대기 중인 모든 타임록 작업을 실행하여 빈, 취약한 시장을 열어두었습니다. 이 자금 없는 시장을 악용하여, 그들은 프로토콜에서 2,000만 달러를 빼냈습니다.

여기서 핵심 교훈은 거버넌스 작업이 보안을 보장하기 위해 특정 순서로 발생해야 할 때, 원자적으로 만들어야 한다는 것입니다. 예를 들어, OpenZeppelin Timelock을 사용하는 경우, `schedule()` 대신 `scheduleBatch()`로 예약해야 합니다. Sonne의 실수는 이러한 작업을 별도로 대기열에 넣을 수 있게 하여 노출되었다는 것입니다.

#### 예방 기법

구성 오류 문제와 우리가 논의한 종류의 비용이 많이 드는 실수를 피하려면, 스마트 컨트랙트의 전체 수명 주기 동안 특히 배포, 업그레이드, 중요한 거버넌스 작업에 관해서는 사전 예방적 접근 방식을 취해야 합니다. 배포 및 업그레이드 스크립트가 철저히 테스트되고 감사되었는지 항상 확인해야 합니다. 코드 자체를 감사하는 것 이상으로 메인넷에 접촉하는 스크립트에 주의를 기울여 프로세스의 모든 측면이 실제와 같은 환경에서 테스트되었는지 확인해야 합니다.

## 컨트랙트 라이브러리

온체인에 배포된 호출 가능한 라이브러리와 오프체인 코드 템플릿 라이브러리로 재사용할 수 있는 기존 코드가 많이 있습니다. 이더리움에서 가장 널리 사용되는 리소스는 [OpenZeppelin 스위트](https://oreil.ly/OSSoV)로, 다양한 토큰 구현부터 다양한 프록시 아키텍처, `Ownable`, `Pausable` 또는 `ReentrancyGuard`와 같이 컨트랙트에서 흔히 발견되는 간단한 동작에 이르기까지 풍부한 컨트랙트 라이브러리입니다. 이 저장소의 컨트랙트는 광범위하게 테스트되었으며, 어떤 경우에는 사실상의 표준 구현으로 기능하기도 합니다. 무료로 사용할 수 있으며 [OpenZeppelin](https://www.openzeppelin.com)과 점점 늘어나는 외부 기여자 목록이 함께 구축하고 유지 관리합니다.

다른 주목할 만한 컨트랙트 라이브러리로는 Paradigm의 [Solmate](https://oreil.ly/yTuU9)와 Vectorized의 [Solady](https://oreil.ly/zqpib)가 있습니다. Solmate는 설계에서 더 의견이 강하고, Solady는 주로 가스 최적화에 중점을 둡니다.

## 결론

업데이트 덕분에, Solidity 컴파일러는 이제 정수 오버플로우 및 기본 가시성 문제와 같은 위험을 완화합니다. 이를 통해 책의 첫 번째 판에서 언급된 일부 오래된 함정을 제거하고 대신 더 현재적이고 관련성 있는 취약점에 집중할 공간을 사용할 수 있었습니다. 어쨌든, 스마트 컨트랙트 분야에서 일하는 모든 개발자가 알고 이해해야 할 것이 여전히 많습니다. 스마트 컨트랙트 설계 및 코드 작성에서 모범 사례를 따르면, 많은 심각한 함정과 트랩을 피할 수 있습니다.

아마도 가장 근본적인 소프트웨어 보안 원칙은 신뢰할 수 있는 코드의 재사용을 극대화하는 것입니다. 암호학에서 이것은 너무 중요해서 "자신만의 암호화를 만들지 마세요"라는 격언으로 압축되었습니다. 스마트 컨트랙트의 경우, 이것은 커뮤니티에 의해 철저히 검증된 무료로 이용 가능한 라이브러리에서 최대한 많이 얻는 것을 의미합니다.
