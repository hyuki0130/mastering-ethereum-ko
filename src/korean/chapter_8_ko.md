# 8장. 스마트 컨트랙트와 Vyper

Vyper는 EVM을 위한 잘 확립된 컨트랙트 지향 프로그래밍 언어로, 개발자가 이해하기 쉬운 코드를 작성할 수 있게 함으로써 뛰어난 감사 가능성을 제공하고자 합니다. 실제로 Vyper의 원칙 중 하나는 개발자가 오해의 소지가 있는 코드를 작성하는 것을 사실상 불가능하게 만드는 것입니다.

이 장에서는 스마트 컨트랙트의 일반적인 문제점들을 살펴보고, Vyper 컨트랙트 프로그래밍 언어를 소개하며, Solidity와 비교하여 차이점을 설명하겠습니다.

## 취약점과 Vyper

2023년에만 이더리움 생태계에서 스마트 컨트랙트 취약점으로 인해 거의 20억 달러가 도난당했습니다. 취약점은 코드를 통해 스마트 컨트랙트에 도입됩니다. 이러한 취약점들이 의도적으로 도입되지 않았다고 강력히 주장할 수 있지만, 어쨌든 바람직하지 않은 스마트 컨트랙트 코드는 이더리움 사용자에게 예상치 못한 자금 손실을 초래하며, 이는 이상적이지 않습니다. Vyper는 안전한 코드를 더 쉽게 작성하거나, 마찬가지로 실수로 오해의 소지가 있거나 취약한 코드를 작성하기 어렵게 설계되었습니다.

## Solidity와의 비교

Vyper가 안전하지 않은 코드를 작성하기 어렵게 만드는 방법 중 하나는 Solidity의 일부 기능을 의도적으로 생략하는 것입니다. 이 설계 선택은 보안 우선 원칙에 뿌리를 두고 있으며 Python의 명확성과 단순성에서 영감을 받았습니다. Vyper로 스마트 컨트랙트 개발을 고려하는 사람들에게 Vyper가 어떤 기능을 가지고 있지 않은지, 그리고 그 이유를 이해하는 것이 중요합니다. 이 섹션에서는 그러한 기능들을 살펴보고 왜 생략되었는지에 대한 정당성을 제공하겠습니다.

모호성을 줄이기 위해 기능 세트를 축소했음에도 불구하고, Vyper는 개발자와 감사자의 실질적인 요구를 충족하기 위해 발전해 왔습니다. 예를 들어, 컨트랙트를 단일 파일에 유지하는 원래 철학은 감사 가능성을 극대화하는 데 도움이 되었지만, 프로토콜이 더 커지고 복잡해지면서 결국 병목 현상이 되었습니다. 이를 해결하기 위해 현대 Vyper는 개발자가 상태 접근과 코드 재사용에 대한 엄격한 제어를 유지하면서 컨트랙트를 여러 파일로 분할할 수 있는 정교한 모듈 시스템을 도입했습니다. 이 모듈 시스템은 전통적인 상속보다는 합성 원칙을 따르며, 구조와 가독성 사이에서 더 나은 균형을 이룹니다. Vyper는 명확성과 감사 용이성을 강조하는 분산 금융(DeFi) 프로토콜과 스테이킹 시스템과 같은 고신뢰성 사용 사례에서 점점 더 큰 역할을 찾아가고 있습니다.

### 모디파이어(Modifier)

7장에서 보았듯이, Solidity에서는 모디파이어를 사용하여 함수를 작성할 수 있습니다. 예를 들어, 다음 함수 `changeOwner`는 실행의 일부로 `onlyBy`라는 모디파이어의 코드를 실행합니다:

```solidity
function changeOwner(address _newOwner)
 public
 onlyBy(owner)
{
 owner = _newOwner;
}
```

이 모디파이어는 소유권과 관련된 규칙을 시행합니다. 보시다시피, 이 특정 모디파이어는 `changeOwner` 함수를 대신하여 사전 검사를 수행하는 메커니즘으로 작동합니다:

```solidity
modifier onlyBy(address _account)
{
 require(msg.sender == _account);
 _;
}
```

하지만 모디파이어는 여기에 표시된 것처럼 단순히 검사를 수행하기 위한 것만이 아닙니다. 실제로 모디파이어로서, 호출 함수의 맥락에서 스마트 컨트랙트의 환경을 크게 변경할 수 있습니다. 간단히 말해서, 모디파이어는 *광범위한 영향력*을 가집니다.

또 다른 Solidity 스타일의 예시를 살펴보겠습니다:

```solidity
enum Stages {
 SafeStage,
 DangerStage,
 FinalStage
}
uint public creationTime = block.timestamp;
Stages public stage = Stages.SafeStage;
function nextStage() internal {
 stage = Stages(uint256(stage) + 1);
}
modifier stageTimeConfirmation() {
 if (stage == Stages.SafeStage &&
 block.timestamp >= creationTime + 10 days)
 nextStage();
 _;
}
function a()
 public
 stageTimeConfirmation
 // 더 많은 코드가 여기에 옵니다
{
}
```

한편으로, 개발자는 자신의 코드가 호출하는 다른 코드를 항상 확인해야 합니다. 그러나 특정 상황(시간 제약이 있거나 피로로 인해 집중력이 떨어지는 경우 등)에서는 개발자가 한 줄의 코드를 간과할 수 있습니다. 이는 개발자가 함수 호출 계층을 정신적으로 추적하면서 스마트 컨트랙트 변수의 상태를 기억에 커밋하면서 큰 파일 내에서 여기저기 이동해야 할 때 더욱 그럴 가능성이 높습니다.

앞의 예시를 조금 더 깊이 살펴보겠습니다. 개발자가 `a`라는 퍼블릭 함수를 작성한다고 상상해 보세요. 개발자는 이 컨트랙트에 처음이고 다른 사람이 작성한 모디파이어를 활용하고 있습니다. 언뜻 보기에, `stageTimeConfirmation` 모디파이어는 단순히 호출 함수와 관련하여 컨트랙트의 나이에 대한 몇 가지 검사를 수행하는 것처럼 보입니다. 개발자가 *인식하지 못할 수 있는* 것은 모디파이어가 `nextStage`라는 또 다른 함수도 호출하고 있다는 것입니다. 이 단순화된 시연 시나리오에서, 단순히 퍼블릭 함수 `a`를 호출하면 스마트 컨트랙트의 `stage` 변수가 `SafeStage`에서 `DangerStage`로 이동하게 됩니다.

Vyper는 모디파이어를 완전히 없앴습니다. Vyper의 권장 사항은 다음과 같습니다: 모디파이어로 단순히 어설션만 수행하는 경우, 함수의 일부로 인라인 검사와 assert를 간단히 사용하세요; 스마트 컨트랙트 상태를 수정하는 경우 등에도 마찬가지로 이러한 변경 사항을 함수의 명시적인 부분으로 만드세요. 이렇게 하면 독자가 함수가 무엇을 하는지 보기 위해 모디파이어 코드를 함수 주위에 정신적으로(또는 수동으로) "래핑"할 필요가 없으므로 감사 가능성과 가독성이 향상됩니다.

### 클래스 상속

상속을 통해 프로그래머는 기존 소프트웨어 라이브러리에서 기존 기능, 속성 및 동작을 획득하여 미리 작성된 코드의 힘을 활용할 수 있습니다. 상속은 강력하며 코드 재사용을 촉진합니다. Solidity는 다중 상속과 다형성을 지원하지만, 이것들이 객체 지향 프로그래밍의 핵심 기능이지만 Vyper는 이를 지원하지 않습니다. Vyper는 상속의 구현이 프로그램이 무엇을 하는지 이해하기 위해 코더와 감사자가 여러 파일 사이를 이동해야 한다고 주장합니다. Vyper는 또한 다중 상속이 코드를 이해하기 너무 복잡하게 만들 수 있다는 견해를 가지고 있습니다—이 견해는 다중 상속이 어떻게 문제가 될 수 있는지에 대한 예시를 제공하는 [Solidity 문서](https://oreil.ly/bkGwS)에서 암묵적으로 인정되었습니다.

### 인라인 어셈블리

인라인 어셈블리는 개발자에게 EVM에 대한 저수준 접근을 제공하여 Solidity 프로그램이 EVM 명령어에 직접 접근하여 작업을 수행할 수 있게 합니다. 예를 들어, 다음 어셈블리 코드는 메모리 위치 `0x80`에 3을 더합니다:

```
3 0x80 mload add 0x80 mstore
```

이것은 변수 이름을 검색하여 변수가 읽히거나 수정되는 모든 발생을 찾는 기능을 방해할 것입니다. Vyper는 가독성의 손실이 추가적인 기능에 비해 너무 높은 대가라고 생각하여 인라인 어셈블리를 지원하지 않습니다.

### 함수 오버로딩

함수 오버로딩을 통해 개발자는 같은 이름의 여러 함수를 작성할 수 있습니다. 특정 경우에 어떤 함수가 사용되는지는 제공된 인자의 타입에 따라 달라집니다. 예를 들어, 다음 두 함수를 살펴보세요:

```solidity
function f(uint256 _in) public pure returns (uint256 out) {
 out = 1;
}
function f(uint256 _in, bytes32 _key) public pure returns (uint256 out) {
 out = 2;
}
```

첫 번째 함수(이름이 `f`)는 `uint256` 타입의 입력 인자를 받습니다; 두 번째 함수(역시 이름이 `f`)는 `uint256` 타입 하나와 `bytes32` 타입 하나, 총 두 개의 인자를 받습니다. 같은 이름으로 다른 인자를 받는 여러 함수 정의가 있으면 혼란스러울 수 있으므로, Vyper는 함수 오버로딩을 지원하지 않습니다.

### 변수 타입캐스팅

Vyper는 Solidity에 비해 타입 변환에 대해 매우 다른 접근 방식을 취하며, 편의성보다 명시적이고 안전한 타입 처리를 우선시합니다. 이 언어는 모든 타입 변환이 내장된 `convert()` 함수를 사용하여 명시적으로 이루어지도록 요구하며, 이는 개발자가 데이터 타입이 언제 어떻게 수정되는지 항상 인식하도록 보장합니다.

타입 변환을 두 가지 범주로 생각할 수 있습니다: 정보를 잃을 수 있는 것과 그렇지 않은 것. Vyper의 `convert()` 함수는 두 경우 모두 처리하지만, 항상 예상치 못한 동작을 방지하기 위해 명시적인 범위 검사를 수행합니다. 예를 들어, 더 큰 정수 타입에서 더 작은 타입으로 변환할 때, 값이 대상 타입의 범위 내에 맞지 않으면 Vyper는 트랜잭션을 되돌립니다.

Vyper에서 타입 변환 문법은 간단합니다:

```
# 정수 타입 간 변환
small_value: uint8 = 42
large_value: uint256 = convert(small_value, uint256)  # 안전한 업캐스트
back_to_small: uint8 = convert(large_value, uint8)   # 범위 검사된 다운캐스트
```

이 명시적인 접근 방식은 타입 변환을 다룰 때 Vyper 코드가 Solidity보다 더 장황할 수 있지만, 훨씬 더 안전하다는 것을 의미합니다. 모든 변환이 의도적이고 명시적이어야 하기 때문에 실수로 값을 자르거나 예상치 못한 오버플로우 동작을 가질 가능성이 없습니다. `convert()` 함수는 변환이 데이터 손실을 초래하거나 입력 값이 대상 타입의 유효한 범위를 벗어나면 트랜잭션을 되돌립니다.

## 데코레이터

다음 데코레이터들은 각 함수의 시작 부분에 사용할 수 있습니다:

**@internal**

`@internal` 데코레이터는 함수를 컨트랙트 외부에서 접근할 수 없게 만듭니다. 이것은 기본 함수 가시성이며, 따라서 선택 사항입니다.

**@external**

`@external` 데코레이터는 함수를 공개적으로 보이고 실행 가능하게 만듭니다. 예를 들어, 이더리움 지갑에서도 컨트랙트를 볼 때 이러한 함수들을 표시합니다.

**@view**

`@view` 데코레이터가 있는 함수는 상태 변수를 변경할 수 없습니다. 실제로, 함수가 상태 변수를 변경하려고 하면 컴파일러는 적절한 오류와 함께 전체 프로그램을 거부합니다.

**@pure**

`@pure` 데코레이터가 있는 함수는 어떤 블록체인 상태도 읽을 수 없고, non-pure 메서드나 다른 컨트랙트에 대한 호출도 할 수 없습니다.

**@payable**

`@payable` 데코레이터가 있는 함수만 값을 전송할 수 있습니다.

**@deploy**

`@deploy` 데코레이터는 컨트랙트의 생성자 함수를 표시하는 데 사용됩니다. 이 함수는 컨트랙트가 블록체인에 배포될 때 정확히 한 번 실행되며, 일반적으로 초기 상태 변수와 구성을 설정하는 데 사용됩니다. Vyper에서는 `__init__()` 함수만 `@deploy`로 표시할 수 있으며, 컨트랙트에 생성자 로직을 포함하려면 이 데코레이터가 필요합니다.

**@raw_return**

`@raw_return` 데코레이터가 있는 함수는 ABI 인코딩을 적용하지 않고 원시 바이트를 반환합니다. 이 데코레이터는 다른 컨트랙트 호출의 정확한 출력을 또 다른 인코딩 레이어로 래핑하지 않고 전달해야 하는 프록시 컨트랙트와 헬퍼 컨트랙트에서 특히 유용합니다. 그러나 중요한 제한 사항이 있습니다: 이 데코레이터는 `@external` 함수에서만 사용할 수 있습니다. 인터페이스 정의에서는 사용할 수 없으며, 다른 컨트랙트에서 이러한 함수를 호출할 때는 반환 데이터가 ABI 인코딩되지 않을 수 있으므로 인터페이스 호출 대신 `raw_call`을 사용해야 합니다.

**@nonreentrant**

`@nonreentrant` 데코레이터는 함수에 잠금을 배치하여 데코레이터가 적용된 모든 함수에 대한 재진입 호출을 방지합니다. 재진입 잠금은 이러한 함수가 실행을 완료할 때까지 다시 진입할 수 없도록 보장합니다. 이 데코레이터는 외부 컨트랙트가 보호된 함수를 다시 호출하여 예상치 못한 동작이나 컨트랙트 익스플로잇을 일으킬 수 있는 재진입 공격을 방지하는 데 사용됩니다. Vyper는 또한 기본적으로 재진입 방지를 위한 pragma를 지원하여, 명시적으로 재정의하지 않는 한 모든 외부 함수가 재진입 방지되도록 합니다. 예를 들어, 컨트랙트 A가 재진입 보호를 위해 이 데코레이터를 사용하고 컨트랙트 B에 대한 외부 호출을 하면, 컨트랙트 B가 컨트랙트 A의 보호된 함수를 다시 호출하려는 시도는 트랜잭션을 되돌리게 됩니다.

> **참고**
>
> Vyper 버전 0.2.15, 0.2.16 및 0.3.0의 이 재진입 방지 기능에는 2023년 중반 Curve 프로토콜을 공격하기 위해 발견되고 악용된 치명적인 버그가 포함되어 있었습니다. 9장에서 재진입 취약점에 대해 더 자세히 살펴보겠습니다.

Vyper는 데코레이터의 로직을 명시적으로 구현합니다. 예를 들어, 함수에 `@payable` 데코레이터와 `@view` 데코레이터가 모두 있으면 Vyper 컴파일 과정이 실패합니다. 이는 값을 전송하는 함수는 정의상 상태를 업데이트했으므로 `@view`가 될 수 없기 때문에 타당합니다. 각 Vyper 함수는 `@external` 또는 `@internal` 중 하나로(둘 다가 아니라!) 데코레이트되어야 합니다.

## 함수 및 변수 순서

Vyper의 스코핑과 선언에 대한 접근 방식은 C99 스코핑 규칙을 따르며, 처음 예상할 수 있는 것보다 더 많은 유연성을 제공합니다. Vyper 컨트랙트는 여전히 단일 파일에 포함되어야 하지만(모듈 시스템을 사용하지 않는 한), 이전 버전에 있던 엄격한 순서 요구 사항은 모듈 범위 선언에 대해 완화되었습니다.

모듈 범위(모든 함수 본문 외부)에서 선언된 변수와 함수는 공식적인 선언 전에도 전체 컨트랙트에서 볼 수 있습니다. 이것은 많은 현대 프로그래밍 언어가 전방 선언을 처리하는 방식과 유사하게, 파일에 나타나기 전에 상태 변수를 참조하고 함수를 호출할 수 있음을 의미합니다.

다음은 현대 Vyper에서 스코핑이 작동하는 방식을 보여주는 실제 예시입니다:

```
# 이 함수는 아래의 상태 변수를 참조할 수 있습니다
@external
def get_stored_value() -> uint256:
    return self.stored_data  # 나중에 선언된 변수를 참조
# 이 함수는 위의 함수를 호출할 수 있습니다
@external
def check_if_positive() -> bool:
    return self.get_stored_value() > 0
# 상태 변수 선언 - 위의 함수들에서 접근 가능
stored_data: public(uint256)
```

그러나 함수 범위 내에서 Vyper는 여전히 엄격한 순서 규칙을 유지합니다. 로컬 변수는 사용 전에 선언되어야 하며, 상수, 불변 변수 또는 기타 모듈 수준 선언의 이름을 로컬 변수로 섀도잉할 수 없습니다. 이 스코핑 접근 방식은 Python의 유연성과 상태 변수 및 함수 관계의 명확한 가시성이 보안 감사에 중요한 스마트 컨트랙트 개발의 요구 사이에서 균형을 이룹니다.

## 컴파일

Vyper를 실험하는 가장 쉬운 방법은 [Remix 온라인 컴파일러](https://remix.ethereum.org)를 사용하는 것으로, 웹 브라우저만 사용하여 스마트 컨트랙트를 작성한 다음 컴파일할 수 있습니다(플러그인 관리자에서 vyper-remix 플러그인을 활성화해야 합니다).

> **참고**
>
> Vyper에는 ERC-20 및 ERC-721과 같은 [내장된 공통 인터페이스](https://oreil.ly/GazPW)가 포함되어 있어, 이러한 컨트랙트와 즉시 상호 작용할 수 있습니다. Vyper의 컨트랙트는 전역 변수로 선언되어야 합니다. ERC-20 변수를 선언하는 예시는 다음과 같습니다:
> `from vyper.interfaces import ERC20` `token: ERC20`

커맨드 라인을 사용하여 컨트랙트를 컴파일할 수도 있습니다. 각 Vyper 컨트랙트는 *.vy* 확장자를 가진 파일에 저장됩니다. Vyper가 설치되면 다음 명령을 실행하여 컨트랙트를 컴파일할 수 있습니다:

```bash
vyper ~/hello_world.vy
```

컴파일러는 광범위한 출력 옵션을 제공합니다. JSON 형식의 사람이 읽을 수 있는 ABI 설명을 얻으려면 다음을 사용하세요:

```bash
vyper -f abi ~/hello_world.vy
```

개발 및 테스트를 위해 바이트코드, 옵코드 또는 인터페이스 파일과 같은 추가 출력이 필요할 것입니다. 컴파일러는 다양한 출력 형식을 지원합니다:

```bash
vyper -f abi,bytecode,interface,source_map ~/hello_world.vy
```

현대 Vyper에는 고급 최적화 모드도 포함되어 있습니다. `--optimize gas`(기본값)로 가스 효율성을 최적화하거나 `--optimize codesize`로 더 작은 컨트랙트 크기를 최적화할 수 있습니다. 더 나은 최적화를 위해 `--experimental-codegen`으로 새로운 실험적 Venom IR 파이프라인을 활성화할 수 있습니다.

Remix와 커맨드 라인 컴파일러는 학습과 실험에 훌륭하지만, 대규모 프로젝트를 작업하는 개발자는 일반적으로 포괄적인 개발 프레임워크가 필요합니다. [ApeWorx](https://oreil.ly/AJRSa)(이전의 Ape)는 자동화된 테스트, 배포 스크립팅 및 다양한 네트워크와의 통합과 같은 기능으로 훌륭한 Vyper 지원을 제공합니다. [Foundry](https://oreil.ly/CWIKj)는 주로 Solidity에 초점을 맞추고 있지만, Vyper 개발도 지원하며 강력한 테스트 및 시뮬레이션 기능을 제공합니다. 이러한 프레임워크는 복잡한 애플리케이션을 구축하기 위해 전문 스마트 컨트랙트 개발자가 필요로 하는 성숙한 개발 환경을 제공합니다.

## 컴파일러 수준에서 오버플로우 오류 방지

소프트웨어의 오버플로우 오류는 실제 가치를 다룰 때 치명적일 수 있습니다. 예를 들어, [2018년 4월 중순의 한 트랜잭션](https://oreil.ly/zOy06)은 57,896,044,618,658,100,000,000,000,000,000,000,000,000,000,000,000,000,000,000개 이상의 BEC 토큰의 악의적인 전송을 보여줍니다. 이 트랜잭션은 Beauty Chain의 ERC-20 토큰 컨트랙트(*BecToken.sol*)의 정수 오버플로우 문제의 결과였습니다.

Vyper의 핵심 기능 중 하나는 항상 내장된 오버플로우 보호였으며, 이는 역사적으로 스마트 컨트랙트 개발을 괴롭혀온 오버플로우 오류의 위험을 완화합니다. Vyper의 오버플로우 보호 접근 방식은 포괄적입니다: 정수 연산에 필요한 예외 케이스를 처리하는 SafeMath 동등 보호가 포함되어 있어, 덧셈, 뺄셈, 곱셈, 나눗셈과 같은 연산이 기본적으로 안전하고 오버플로우나 언더플로우가 발생하면 예외를 발생시킵니다. 또한 Vyper는 리터럴 상수가 로드되거나, 값이 함수에 전달되거나, 변수가 할당될 때마다 값 제한을 적용하기 위해 클램프를 사용합니다.

최근 버전의 Solidity(0.8.0 이상)도 Vyper가 처음부터 제공한 것과 유사하게 컴파일러 수준에서 네이티브 오버플로우 검사를 통합했다는 점에 주목할 가치가 있습니다. 이것은 현대 Solidity의 산술 연산이 이제 자동으로 오버플로우 검사를 포함하여 SafeMath와 같은 추가 라이브러리 없이도 오버플로우 오류의 위험을 크게 줄인다는 것을 의미합니다. 이 변경으로 Solidity가 Vyper의 안전 우선 접근 방식에 더 가까워졌지만, Vyper의 구현은 클램프 연산과 언어 전체에 걸친 더 일관된 범위 검사를 포함하여 더 포괄적입니다. 핵심 차이점은 철학적입니다: Vyper는 처음부터 오버플로우 보호를 핵심 원칙으로 하여 설계되었고, Solidity는 역사적 취약점을 해결하기 위한 개선 사항으로 이를 추가했습니다. 접근 방식의 이러한 차이는 기본적으로 안전하지 않은 코드를 작성하기 어렵게 만들려는 Vyper의 더 광범위한 약속을 반영합니다.

## 데이터 읽기 및 쓰기

저장, 읽기, 수정하는 데 비용이 들지만, 이러한 저장 작업은 대부분의 스마트 컨트랙트에서 필수적인 구성 요소입니다. 스마트 컨트랙트는 두 곳에 데이터를 쓸 수 있습니다:

**전역 상태**

주어진 스마트 컨트랙트의 상태 변수는 이더리움의 전역 상태 트라이에 저장됩니다; 스마트 컨트랙트는 해당 특정 컨트랙트의 주소와 관련된 데이터만 저장, 읽기 및 수정할 수 있습니다(즉, 스마트 컨트랙트는 다른 스마트 컨트랙트에 직접 읽거나 쓸 수 없습니다).

**로그**

스마트 컨트랙트는 로그 이벤트를 통해 이더리움의 체인 데이터에 쓸 수 있습니다. Vyper에서 이벤트를 선언하고 사용하는 문법은 Vyper의 코드 명확성에 초점을 맞춘 것처럼 깔끔하고 직관적입니다.

Vyper의 이벤트 선언은 구조체 선언과 유사하게 보입니다. 예를 들어, `MyLog`라는 이벤트의 선언은 다음과 같이 작성됩니다:

```
event MyLog:
    arg1: indexed(address)
    arg2: uint256
    message: indexed(bytes[100])
```

최대 4개의 인덱스된 인자(검색 가능한 토픽이 됨)와 이벤트 데이터의 일부가 되는 인덱스되지 않은 인자를 원하는 만큼 가질 수 있습니다. 인덱스된 인자는 이벤트를 필터링하고 검색하는 데 유용하며, 인덱스되지 않은 인자는 더 많은 양의 데이터를 포함할 수 있습니다.

로그 이벤트의 실행은 간단한 문법으로 `log` 문을 사용합니다:

```
log MyLog(msg.sender, 42, b"Hello, Vyper!")
```

`pass` 문을 사용하여 인자가 없는 이벤트를 만들 수도 있습니다:

```
event SimpleEvent: pass
# 나중에 코드에서:
log SimpleEvent()
```

스마트 컨트랙트는 로그 이벤트를 통해 이더리움의 체인 데이터에 쓸 수 있지만, 자신이 생성한 온체인 로그 이벤트를 읽을 수는 없습니다. 그러나 로그 이벤트를 통해 이더리움의 체인 데이터에 쓰는 것의 장점 중 하나는 라이트 클라이언트가 공개 체인에서 로그를 발견하고 읽을 수 있다는 것입니다. 예를 들어, 발행된 블록의 `logsBloom` 값은 로그 이벤트가 존재하는지 여부를 나타낼 수 있습니다. 로그 이벤트의 존재가 확인되면, 주어진 트랜잭션 영수증에서 로그 데이터를 얻을 수 있습니다.

## 결론

Vyper는 강력하고 매력적인 컨트랙트 지향 프로그래밍 언어입니다. 그 설계는 "정확성"에 편향되어 있으며, 보안과 단순성을 우선시합니다. 이 접근 방식은 프로그래머가 더 나은 스마트 컨트랙트를 작성하고 심각한 취약점을 일으킬 수 있는 특정 함정을 피하는 데 도움이 될 수 있습니다.

그러나 모든 것에는 트레이드오프가 있다는 것을 인식하는 것이 중요합니다. Vyper의 엄격한 설계 원칙은 보안과 코드 명확성을 향상시키지만, 개발자가 다른 언어에서 찾을 수 있는 일부 유연성을 제한합니다. 또한 Vyper는 Solidity만큼 널리 사용되거나 개발되지 않았기 때문에 개발자가 사용할 수 있는 리소스, 라이브러리 및 도구가 더 적습니다. 이는 커뮤니티 지원, 미리 구축된 솔루션 및 포괄적인 문서를 찾는 사람들에게 도전이 될 수 있습니다.

다음으로, 스마트 컨트랙트 보안을 더 자세히 살펴보겠습니다. 스마트 컨트랙트에서 발생할 수 있는 모든 가능한 보안 문제에 대해 읽으면 Vyper 설계의 일부 뉘앙스가 더 명확해질 수 있습니다.
