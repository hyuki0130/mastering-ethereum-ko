# 12장. 탈중앙화 애플리케이션

이 장에서는 DApp을 설명하고, 그것이 무엇인지, 어떻게 작동하는지, 그리고 핵심 아키텍처가 어떻게 구성되어 있는지 해설합니다. 기본 사항을 다룬 후, 처음부터 첫 번째 DApp을 구축하는 실용적인 실습 예제를 안내합니다. 여기에는 필요한 스마트 컨트랙트 배포, 프론트엔드 통합, 전체 스택을 거의 프로덕션 환경에 맞게 준비하는 것이 포함됩니다. 끝날 무렵에는 작동하는 DApp과 이러한 혁신적인 애플리케이션을 뒷받침하는 핵심 개념에 대한 확고한 이해를 모두 갖게 될 것입니다.

## DApp이란 무엇인가?

*DApp*은 *탈중앙화 애플리케이션(decentralized application)*의 약자입니다; 이는 레거시 애플리케이션과 비교하여 완전히 새로운 패러다임 전환입니다. 레거시 애플리케이션은 일반적으로 그림 12-1과 같은 아키텍처를 가지고 있습니다:

- 앱의 로직 부분을 위한 비공개 소스 코드
- 애플리케이션 데이터를 저장하기 위한 중앙화된 데이터베이스
- 사용자가 앱에 접근할 수 있게 하는 유일한 프론트엔드

![레거시 애플리케이션의 일반 아키텍처](../images/ch12/maet_1201.png)

그림 12-1. 레거시 애플리케이션의 일반 아키텍처

인스타그램, 틱톡, 은행 또는 지금 휴대폰에 있는 어떤 애플리케이션을 생각해 보세요. 아마도 매우 유사한 아키텍처에 의존할 것입니다. 애플리케이션 뒤의 팀이 당신이 접근하기를 원하는 경우에만 애플리케이션에 접근할 수 있습니다; 공식 웹사이트가 서비스 중단되면 인스타그램 계정에 로그인하기 위해 방문할 수 있는 대체 웹사이트가 없습니다.

DApp은 두 가지 명확한 목표를 가지고 있습니다: 단일 장애 지점을 갖지 않고, 전체 팀이 사라지더라도 사람들이 여전히 사용할 수 있는 제품이 되는 것입니다. 그 아키텍처는 그림 12-2와 같이 다음과 같은 방식으로 단순화될 수 있습니다:

- 여러 이더리움 스마트 컨트랙트가 DApp 로직 부분의 기초를 형성합니다. 대부분의 경우, Solidity(또는 Vyper) 코드도 오픈 소스입니다.
- 스마트 컨트랙트는 데이터도 포함할 수 있으며, 적절한 데이터베이스로 작동하고 필요한 모든 사용자 정보를 수집합니다.
- 사람들은 공식 프론트엔드를 통해 앱에 접근할 수 있으며, 이는 어떤 이유로든 메인 프론트엔드가 작동하지 않을 경우 대체 프론트엔드(커뮤니티가 만든 것도 포함)로 쉽게 교체할 수 있습니다.

> **참고**
>
> DApp은 어느 정도의 중앙화를 가진 일부 오프체인 구성 요소를 가질 수도 있지만, 일반적으로 이러한 구성 요소는 애플리케이션의 핵심 로직에 근본적이지 않습니다. 평균적인 경우 애플리케이션 속도를 높이는 데 도움이 될 수 있지만, 최악의 경우 항상 온체인 데이터에 완전히 의존할 수 있어야 합니다. 이것이 항상 사실인 것은 아니며, 중앙화된 구성 요소에 의존하는 핵심 로직 부분을 가진 DApp이 분명히 있습니다. 이들은 진정한 탈중앙화 앱이 아니라 레거시와 완전히 탈중앙화된 애플리케이션 사이의 하이브리드 형태에 가깝습니다.

다음 섹션에서는 DApp 스택의 각 구성 요소를 더 자세히 탐구하여 어떻게 작동하고 서로 및 이더리움 프로토콜과 어떻게 관련되는지 더 잘 이해할 것입니다.

## 백엔드 (스마트 컨트랙트)

DApp에서 핵심 비즈니스 로직과 데이터 저장은 중앙화된 서버에 있는 대신 스마트 컨트랙트로 인코딩되어 이더리움 블록체인에서 실행됩니다. 블록체인은 단일 엔티티가 아닌 네트워크에 의해 트랜잭션 실행, 상태 변경 및 기록 보관이 신뢰 없이 시행되는 탈중앙화된 백엔드 역할을 합니다.

사용자는 DApp에 접근하기 위해 중앙화된 팀을 신뢰할 필요가 없습니다. 왜냐하면 이더리움 네트워크가 날이나 시간에 관계없이 항상 제대로 작동하고, 모든 트랜잭션을 처리하고, 스마트 컨트랙트의 상태를 올바르게 업데이트할 것으로 기대할 수 있기 때문입니다.

또한, 이 아키텍처는 매우 강력한 속성을 도입합니다: *검열 저항성*. 전통적인 애플리케이션의 경우, 정부 법률이나 어떤 이유로 인해 앱에 접근이 금지된 국가 목록이 종종 있습니다. 예를 들어, 2025년 현재 페이스북은 브라질, 중국, 이란, 북한, 미얀마, 러시아, 투르크메니스탄 및 우간다에서 금지되어 있습니다. 해당 국가의 사람들은 프로필을 만들거나 플랫폼에 로그인할 수 없습니다.

이더리움에 구축된 DApp의 경우, 이러한 유형의 검열은 더 이상 달성할 수 없습니다. 특정 DApp의 공식 웹사이트를 금지하는 것은 여전히 가능하지만, 아무도 주소가 체인의 일부 무작위 스마트 컨트랙트와 상호작용하는 것을 막을 수 없습니다. 누구든지 나서서 DApp을 위한 대체 프론트엔드를 만들 수 있고, 모든 사람이 이를 사용하여 다시 DApp과 상호작용할 수 있습니다.

### Tornado Cash 이야기

여기서 Tornado Cash의 이야기를 언급할 가치가 있습니다. Tornado Cash는 추적 가능하거나 "오염된" 암호화폐를 다른 것들과 혼합하여 자금의 실제 발신자와 수신자 사이의 모든 링크를 끊어 원래 출처로의 추적을 흐리게 하는 탈중앙화된 믹싱 서비스입니다.

2022년 8월 8일, 미국 재무부 해외자산통제국이 Tornado Cash를 블랙리스트에 올려 미국 시민과 기업이 이를 사용하는 것을 사실상 금지했습니다. 이 플랫폼은 70억 달러 이상의 암호화폐를 세탁한 혐의를 받았습니다. 이틀 후인 8월 10일, Tornado Cash 개발자 중 한 명인 알렉세이 페르체프가 플랫폼 자체를 만든 것만으로 암스테르담에서 체포되었습니다. 공식 GitHub 저장소가 제거되었고 개발자 계정이 정지되었습니다. 2024년 12월 현재, 공식 웹사이트는 접근이 불가능한 상태입니다.

이 모든 것을 감안하면, Tornado Cash DApp이 운영을 중단했다고 가정할 수 있지만, 이것은 진실과 거리가 멉니다. 이러한 사건 이후 서비스가 덜 주목받고 (그리고 유동성이 줄었지만), 프로토콜은 다양한 IPFS 호스팅 게이트웨이를 통해 완전히 기능하고 접근 가능한 상태로 남아 있습니다. 다시 말해, 세계 어디에서나 누구든지 원래 공식 웹사이트 없이도 이전처럼 Tornado Cash를 여전히 사용할 수 있습니다.

## 데이터 저장

데이터 저장은 사용자 데이터를 저장하는 데 사용되는 솔루션을 말합니다. 스마트 컨트랙트에 데이터를 저장하고 읽는 것은 가능하지만, 비용이 많이 드는 작업이며 확장성이 좋지 않습니다; 또한 모든 것이 온체인에 저장될 필요는 없습니다.

일반적으로 스마트 컨트랙트는 중요한 상태 정보를 저장하고 DApp 로직을 시행합니다. 계정 잔액, 소유권 기록 또는 계산 결과와 같은 핵심 정보는 스마트 컨트랙트에 직접 저장됩니다. 이는 민감하고 가치 있는 데이터가 완전히 투명하고, 변조에 강하며, 이더리움 노드를 가진 누구에게나 접근 가능하도록 보장합니다.

다른 모든 정보는 고전적인 데이터베이스와 같이 덜 탈중앙화된 데이터 저장 솔루션에 저장할 수 있습니다. 예를 들어, DApp 개발자는 빠른 데이터 쿼리를 위해 인덱서를 사용하거나 사용자 데이터를 저장하기 위해 중앙화된 데이터베이스를 사용하여 프론트엔드가 이더리움 체인과 전혀 상호작용할 필요가 없게 합니다.

> **참고**
>
> *블록체인 인덱서*는 개발자가 빠르고 효율적인 방식으로 블록체인에 저장된 데이터를 쿼리하고 분석할 수 있게 해주는 도구입니다. 트랜잭션 데이터를 가져와 기계 및 인간이 읽을 수 있는 데이터로 변환하고 쉬운 쿼리를 위해 데이터베이스에 로드합니다.
>
> 사실, 블록체인에서 데이터를 직접 "검색"할 수 없습니다. 예를 들어, 특정 계정이 블록 15364050에서 보유한 USDC 토큰이 얼마인지 알고 싶다고 가정해 봅시다. USDC 스마트 컨트랙트로 가서 찾을 수 없습니다. 왜냐하면 과거 데이터를 저장하지 않기 때문입니다. 해당 블록부터 지금까지 발생한 모든 트랜잭션을 가져와 필터링하고 해당 계정과 관련된 모든 USDC 전송 정보를 추출한 다음 최종적으로 답을 얻을 수 있습니다. 상상할 수 있듯이, 이것은 바람직한 접근 방식이 아닙니다. 이것이 인덱서가 등장하는 이유입니다. 인덱서는 과거 정보를 포함하여 필요한 모든 정보에 대한 쿼리를 즉시 실행하고 빠르게 답을 얻을 수 있게 해주는 데이터베이스와 같은 구조를 유지합니다.

아이디어는 누구나 DApp이 올바르게 작동하는지 확인할 수 있도록 필수 데이터와 애플리케이션 로직만 온체인에 저장해야 한다는 것입니다; 다른 모든 것은 오프체인에 남겨둘 수 있고 그래야 합니다.

### IPFS

*IPFS*는 P2P 네트워크의 피어들 사이에 저장된 객체를 분산시키는 탈중앙화된 콘텐츠 주소 지정 저장 시스템입니다. *콘텐츠 주소 지정*은 각 콘텐츠(파일)가 해시되고 해시가 해당 파일을 식별하는 데 사용된다는 것을 의미합니다. 그런 다음 해시로 요청하여 모든 IPFS 노드에서 파일을 검색할 수 있습니다.

IPFS는 웹 애플리케이션 전달을 위한 선택 프로토콜로 HTTP를 대체하는 것을 목표로 합니다. 단일 서버에 웹 애플리케이션을 저장하는 대신, 파일은 IPFS에 저장되고 모든 IPFS 노드에서 검색할 수 있습니다. 더 자세한 내용은 IPFS 문서를 읽어보세요.

### 머클 트리

흥미롭고 자주 사용되는 솔루션은 머클 트리 구조로 오프체인에 데이터를 저장하고 머클 루트만 온체인에 저장하는 것입니다. 이렇게 하면 가스비가 많이 드는 스마트 컨트랙트에 모든 데이터를 저장할 필요가 없지만, 여전히 온체인에서 어떤 종류의 검증을 수행할 수 있습니다.

> **참고**
>
> 편집자 주: 다음 코드 예제는 매우 구체적인 기술적 맥락에서 "화이트리스트"를 언급합니다. 이 용어는 문제가 있는 함축적 의미를 가지고 있지만, 업계와 문서 전반에서 널리 사용됩니다. 포용성을 크게 중시하지만, 저자들은 기술 개념의 이 프레젠테이션에서 명확성을 위해 용어를 그대로 유지하기로 했습니다.

가장 일반적인 사용 사례는 NFT 컬렉션을 만들고 공개 판매가 모든 사람에게 열리기 전에 더 낮은 가격으로 NFT를 민팅할 수 있도록 다른 주소를 화이트리스트에 추가하려는 경우입니다. 두 가지 옵션이 있습니다.

첫 번째는 스마트 컨트랙트 내에 각 주소를 불리언 값에 매핑하는 스토리지 변수를 만드는 것으로, 모든 화이트리스트 주소에 대해 true입니다. 그런 다음, 이 맵을 사용하여 특정 주소가 실제로 화이트리스트에 있는지 확인할 수 있습니다. 사용자는 민트 트랜잭션을 제출할 때 아무것도 제공할 필요가 없습니다; 컨트랙트는 단순히 `msg.sender`가 화이트리스트 맵에 포함되어 있는지 다음과 같이 확인합니다:

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.28;

// OpenZeppelin 컨트랙트 가져오기.
import "@openzeppelin/contracts/token/ERC721/ERC721.sol";
import "@openzeppelin/contracts/access/Ownable.sol";

// 화이트리스트 주소를 저장하기 위해 매핑을 사용하는 화이트리스트 민트 함수가 있는
// 단순화된 NFT 컨트랙트.
contract MyWhitelistNFT is ERC721, Ownable {
    // ... 컨트랙트의 나머지 부분

    // 화이트리스트 주소를 위한 매핑
    mapping(address => bool) public isWhitelisted;

    /**
     * @notice 화이트리스트 민트 함수.
     */
    function whitelistMint() payable {
        // ... 함수의 나머지 부분

        // 사용자가 화이트리스트에 있는지 확인.
        require(isWhitelisted[msg.sender], "You are not whitelisted");

        // NFT 민트.
        _safeMint(msg.sender, nextTokenId);
        nextTokenId++;
    }
}
```

두 번째는 오프체인에서 머클 트리를 만들고 컨트랙트에 머클 루트를 온체인에 저장하는 것입니다. 그런 다음, 각 화이트리스트 사용자에게 머클 증명을 제공합니다. 사용자는 머클 증명을 컨트랙트에 제출하고, 컨트랙트는 (보통 라이브러리를 통해) 해당 증명의 유효성을 온체인에서 다음과 같이 검증합니다:

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.28;

// OpenZeppelin 컨트랙트 가져오기.
import "@openzeppelin/contracts/token/ERC721/ERC721.sol";
import "@openzeppelin/contracts/access/Ownable.sol";
import "@openzeppelin/contracts/utils/cryptography/MerkleProof.sol";

// 화이트리스트 주소를 저장하기 위해 머클 트리를 사용하는 화이트리스트 민트 함수가 있는
// 단순화된 NFT 컨트랙트.
contract MyWhitelistNFT is ERC721, Ownable {
    // ... 컨트랙트의 나머지 부분

    // 오프체인에서 생성된 머클 트리의 머클 루트.
    bytes32 public merkleRoot;

    /**
     * @notice 화이트리스트 민트 함수.
     * @dev 사용자는 화이트리스트에 있음을 증명하기 위해 머클 증명을 제공해야 함.
     * @param _merkleProof msg.sender가 화이트리스트에 있다는 증명.
     */
    function whitelistMint(bytes32[] calldata _merkleProof) external payable {
        // ... 함수의 나머지 부분

        // 제공된 증명을 사용하여 (msg.sender)가 머클 트리에 있는지 검증.
        bytes32 leaf = keccak256(abi.encodePacked(msg.sender));
        bool isValidLeaf = MerkleProof.verify(_merkleProof, merkleRoot, leaf);
        require(isValidLeaf, "Invalid Merkle Proof: Not whitelisted");

        // NFT 민트.
        _safeMint(msg.sender, nextTokenId);
    }
}
```

두 번째 옵션은 특히 대규모 화이트리스트의 경우 첫 번째보다 훨씬 저렴하고 효율적입니다.

> **참고**
>
> 이 방법은 가스 비용을 크게 줄이지만, 트리와 증명이 감사 가능하지 않으면 부정직한 화이트리스트 생성자의 잠재적 위험을 도입합니다. 이상적으로는, 트리를 생성하는 데 사용된 원본 목록이 오픈 소스이고 접근 가능해야 누구나 결과 머클 루트의 유효성을 검증할 수 있습니다.

## 프론트엔드 (웹 사용자 인터페이스)

DApp의 프론트엔드는 React, Angular 또는 Vue와 같은 가장 잘 알려진 Web2 프레임워크를 사용하여 생성됩니다. 필요한 경우 이더리움 체인과의 상호작용은 `viem` 또는 `ethers.js`와 같은 라이브러리를 통해 추상화됩니다.

DApp 프론트엔드를 구축하는 순진한 접근 방식은 모든 구성 요소를 업데이트하기 위해 체인에서 직접 데이터만 읽는 것입니다. 예를 들어, 계정이 보유한 일부 토큰의 잔액을 표시해야 하는 경우, 블록체인을 쿼리하고 답을 받아 모든 새 블록에 대해 이 단계를 반복할 수 있습니다.

이 순진한 접근 방식의 주요 문제는 웹사이트가 정말 느려지고, 사용자가 그러한 프론트엔드와 상호작용하는 것이 매우 답답할 수 있다는 것입니다. 이것이 앞서 언급한 바와 같이 개발자가 종종 DApp 아키텍처에서 중앙화된 데이터 저장 구성 요소를 사용하여 체인과의 상호작용을 최소화하는 이유입니다: 전체 사용자 경험을 더 좋게 만듭니다. 따라서 일반적으로 일부 중앙화된 구성 요소에 의존하는 프론트엔드로 끝나지만, 블록체인에서 이중 확인하여 항상 모든 정보를 검증할 수 있습니다. 결국, 공식 프론트엔드를 신뢰하지 않거나 단순히 마음에 들지 않으면 특정 DApp에 대한 자체 대체 프론트엔드를 만들 수 있습니다.

## 기본 DApp 예제

지금까지 DApp 뒤의 기본 개념을 탐구했습니다. 이제, 소매를 걷어붙이고 직접 DApp을 구축할 시간입니다.

온라인에서 이더리움에서 처음부터 첫 번째 DApp을 구축하는 데 도움이 되는 많은 튜토리얼을 찾을 수 있지만, [Speedrun Ethereum](https://oreil.ly/Onygc)을 강력히 추천합니다. 빠르게 배우고 즉시 멋진 것을 구축하기 시작하는 가장 효과적인 방법입니다. 이더리움에서 DApp 구축에 대한 지식을 높이려면 Speedrun Ethereum에서 찾을 수 있는 모든 챌린지를 완료하고 [BuidlGuidl 커뮤니티](https://buidlguidl.com)에 참여하는 것이 좋습니다.

이 섹션에서는 매우 기본적인 탈중앙화 애플리케이션, 일종의 "Hello World" DApp을 구축할 것입니다. 이전 경험이 필요 없습니다; 컴퓨터와 인터넷 연결만 있으면 됩니다.

### 설치 요구 사항

이 튜토리얼을 따르려면 컴퓨터에 [node.js](http://node.js)와 [yarn](https://oreil.ly/dq_hw)을 설치해야 합니다. 공식 웹사이트를 참조하여 다운로드하고 설치하세요. 개발 환경을 매우 빠르게 만들 수 있는 매우 멋진 도구인 [Scaffold-ETH 2](https://scaffoldeth.io)를 사용할 것입니다.

먼저, 로컬 개발을 위한 체인을 시작해야 합니다. 사실, 최종 제품이 이더리움 메인넷에 배포된 스마트 컨트랙트를 사용하더라도, DApp을 구축하고 테스트하기 위해 실제 체인을 사용해서는 안 됩니다. 정말 느리고 많은 돈 낭비이기도 합니다. Scaffold-ETH는 로컬 개발을 위한 새 체인을 즉시 시작할 수 있는 매우 유용하고 쉬운 명령을 제공합니다. 다음을 실행하기만 하면 됩니다:

### Vercel에 배포

탈중앙화 애플리케이션에 만족하면, Vercel과 같은 프로덕션 환경에 게시할 수 있습니다. Vercel은 애플리케이션을 인터넷에 쉽게 배포할 수 있게 해주는 매우 유용한 프론트엔드-as-a-service 도구입니다. 구매한 사용자 정의 도메인을 연결하여 사람들이 도메인 이름만 입력하여 DApp에 도달할 수도 있습니다.

Scaffold-ETH는 다시 DApp을 Vercel에 즉시 배포할 수 있는 단일 명령을 제공하여 도움을 줍니다. 터미널을 열고 다음을 입력합니다:

```bash
$ yarn vercel:yolo
```

Vercel 계정을 연결하거나 (없으면 새로 만들고) 프로젝트 이름을 선택해야 합니다—그게 전부입니다. 몇 분 후, 전체 DApp이 Vercel에 배포되고 전 세계 누구나 시도해 볼 수 있습니다.

Vercel 프로필로 이동하면 새로 생성된 프로젝트를 볼 수 있습니다. 그림 12-12와 같이, Vercel이 자동 생성한 웹사이트 도메인을 찾을 수 있는 Domains 필드가 있습니다.

## DApp 추가 탈중앙화

이전 섹션에서, DApp을 Vercel에 배포했습니다. Vercel은 DApp 호스팅을 위한 가장 인기 있는 솔루션 중 하나이지만, 탈중앙화된 서비스는 아닙니다. 모든 것이 독점 서버에 있으며, 이는 Vercel이 정책에 따라 모든 사용자를 잠재적으로 검열하고 DApp과 상호작용하는 모든 사람의 IP 주소를 추적할 수 있음을 의미합니다.

DApp을 더욱 탈중앙화하기 위해, 글로벌 P2P 노드 네트워크인 IPFS와 같은 솔루션에 프론트엔드를 호스팅할 수 있습니다. 언급할 가치가 있는 신흥 서비스는 `eth.limo`로, 일반적으로 중앙화된 플랫폼을 통해 제공되는 주류 웹사이트의 사용자 경험을 IPFS 및 유사한 기술이 제공하는 견고성과 탈중앙화와 일치시키는 것을 목표로 합니다.

### 탈중앙화 웹사이트

[Eth.limo](https://eth.limo/)는 클래식 앱에서 일반적으로 접근하는 것과 동일한 방식으로 접근할 수 있는 더 나은 탈중앙화 웹사이트—*DWebsites*라고도 함—를 만들기 위한 퍼즐의 빠진 조각입니다. 이는 이더리움 주소를 `.eth` 도메인 이름으로 사용자 친화적으로 만드는 ENS 기술을 기반으로 합니다. 이더리움 공동 창립자 중 한 명인 비탈릭 부테린은 ENS를 사용하여 자신의 지갑 주소 `0xd8dA6BF26964aF9D7eEd9e03E53415D37aA96045`를 기억하기 쉬운 이름 `vitalik.eth`와 연결합니다.

ENS는 단순히 도메인을 이더리움 주소와 연결하는 것 이상입니다: IPFS 웹사이트 (실제로 콘텐츠 해시)로도 확인할 수 있습니다. `bafybeif3dy…ga4zu`와 같은 것입니다. IPFS 웹사이트와 관련된 주요 문제는 대부분의 인기 있는 웹 브라우저가 이를 적절히 확인하고 사용자에게 콘텐츠를 표시할 수 없다는 것입니다. 이것이 `eth.limo`가 등장하는 이유입니다: ENS 이름과 IPFS 콘텐츠를 위한 역방향 프록시를 운영합니다. `*.eth.limo`에 대한 모든 요청 (기본적으로 `.eth.limo`로 끝나는 모든 웹사이트)을 캡처하고 요청된 ENS 레코드의 IPFS 콘텐츠해시를 자동으로 확인하여 HTTPS를 통해 해당 정적 콘텐츠를 반환합니다. 예를 들어, [비탈릭 부테린의 공식 블로그](https://vitalik.eth.limo)로 이동하면, 내부적으로 다음과 같은 일이 일어납니다:

1. Eth.limo가 `vitalik.eth` ENS 도메인에 대한 수신 요청을 봅니다.
2. 그의 웹사이트 홈페이지를 포함하는 IPFS 콘텐츠해시 (부테린이 이전에 설정한)로 확인합니다.
3. HTTPS를 통해 해당 정적 콘텐츠를 반환합니다.

이렇게 하면, 웹 브라우저가 있는 전 세계 누구나 구성이나 설정 없이 IPFS에 저장된 콘텐츠에 쉽게 접근할 수 있습니다.

### 제한 사항

DWebsites 일반적으로—그리고 특히 `eth.limo`—는 진화하는 기술이고 상당히 빠르게 개선되고 있지만, 이 장을 작성하는 시점 (2025년 6월)에는 여전히 몇 가지 제한 사항이 있습니다. 첫째, IPFS는 정적 파일만 처리할 수 있으므로 어떤 종류의 서버 측 계산도 수행할 수 없습니다. 또한, `eth.limo`를 사용하려면 ENS를 구매하고 프론트엔드의 IPFS 콘텐츠해시에 연결해야 합니다. 그리고 항상 `*.eth.limo` 사용자 정의 도메인을 사용해야 합니다; `.limo` 최종 부분을 잘라낼 수 없습니다. 그렇지 않으면 웹 브라우저가 ENS 이름을 DApp의 IPFS 프론트엔드로 확인할 수 없습니다. 이것이 대부분의 DApp이 `eth.limo`를 사용하지 않는 이유일 것입니다.

> **팁**
>
> 대부분의 웹 브라우저가 아직 ENS와 IPFS와 호환되지 않는 것은 사실이지만, 특정 브라우저들은 이에 대한 지원을 추가하기 시작하고 있습니다. 한 예는 [Brave](https://oreil.ly/LlJT7)입니다.

`eth.limo`는 통보 없이 작동을 중지할 수 있는 또 다른 잠재적으로 중앙화된 제3자라는 점을 말해야 합니다. 그런 일이 발생하면, DApp은 여전히 IPFS를 통해 도달할 수 있지만, `.eth.limo` URL은 더 이상 사용자를 그들에게 리디렉션하지 않습니다.

이 솔루션에 관심이 있고 완전히 탈중앙화된 웹사이트 구축에 대해 자세히 알아보고 싶다면, [공식 웹사이트](https://eth.limo)에서 훨씬 더 많은 세부 정보를 찾을 수 있습니다.

### IPFS에 배포

Scaffold-ETH 2에는 DApp을 IPFS에 빠르게 푸시할 수 있는 또 다른 쉬운 명령이 있습니다. 새 터미널을 열고 다음을 입력하기만 하면 됩니다:

```bash
$ yarn ipfs
```

완료입니다! 다음과 같은 내용이 표시됩니다:

```
   Creating an optimized production build ...

 ✓ Compiled successfully
 ✓ Linting and checking validity of types

 ✓ Collecting page data

 ✓ Generating static pages (8/8)
 ✓ Collecting build traces

 ✓ Finalizing page optimization

…

🚀  Upload complete! Your site is now available at: https://community.bgipfs.com/ipfs/bafybei…
```

표시된 웹사이트로 이동하면 IPFS에 호스팅된 프론트엔드로 DApp이 잘 작동하는 것을 볼 수 있습니다. 문자열 "bafy…"는 IPFS 콘텐츠해시입니다. 개인 ENS가 있고 이 IPFS 호스팅 사이트로 리디렉션하려면 여전히 `eth.limo`를 구성해야 합니다.

이것이 이 `yarn ipfs` 명령의 내부에서 실제로 발생하는 일입니다:

1. IPFS에 업로드할 준비가 된 정적 파일을 갖기 위해 프론트엔드가 빌드됩니다.
2. 정적 파일이 BuidlGuidl (Scaffold-ETH 2 관리자) IPFS 커뮤니티 노드를 통해 IPFS에 업로드됩니다.
3. IPFS 콘텐츠에 대한 역방향 프록시로 작동하여 정적 파일로 리디렉션하는 URL이 반환됩니다 (`community.bgipfs.com/<ipfs-content-hash>`).

자체 IPFS 노드를 실행하고 클러스터를 고정하는 방법을 배우려면 [BuidlGuidl IPFS](https://www.bgipfs.com)를 참조하세요.
